## Intent

**Problem:** Every piece of on-demand hydration already ships and nothing can ask for it. `lfs::stage::materialize` publishes atomically, `WorkKind::LfsDownload` fetches, `Engine::materialize_landed` publishes what landed and repairs the index stat — but the only caller is the whole-tree arrival sweep. A human looking at a virtual path in the Files pane, or an agent at a terminal, has no verb; and under `LfsMode::PointerOnly` — the mode in which paths are virtual at all — the completion arm refuses to publish, so even a manually queued download would land the object in the store and leave the worktree holding pointer text.

**Approach:** One engine entry point, `Engine::materialize_entry(profile_id, subpath)`, with two doors onto it: `keeper-syncd materialize <profile> <subpath> [--json]` and the `sync_materialize_entry` Tauri command. It refuses a path whose worktree bytes are neither the committed pointer nor the content it names, by a typed `ContentRefusal` 56.4 extends; publishes inline through the existing `lfs::stage::materialize` when the object is already in the local store; and otherwise enqueues the existing `WorkKind::LfsDownload` through `enqueue_unique`, marked **requested** so the journal claims it ahead of background units in the same tick and so the completion arm publishes it despite `PointerOnly`.

## Boundaries & Constraints

**Always:**
- **One verb, two doors, no second materialization path** (FR-338, AD-128). `lfs::stage::materialize` stays the only publish, `git::repo::refresh_index_stat` stays the only index-stat repair, `WorkKind::LfsDownload` stays the only transfer, and `Engine::materialize_landed` stays the only completion arm. The CLI and the Tauri command both call `Engine::materialize_entry` and add no policy of their own.
- **The journal is the queue** (AD-128). A request enqueues through `db::enqueue_unique`, whose key is the serialized payload, so a repeat request for the same object returns the id of the covering unit — `covered_while_running` already makes `LfsDownload` idempotent against a *running* row. Urgency is therefore a narrow `UPDATE` on whatever id `enqueue_unique` returned (`db::label_unit`'s shape), **never** a payload field: putting it in the payload would change the dedup key and re-fetch the same bytes, which is the 106-units-for-95-objects defect `enqueue_unique`'s own doc records.
- **Urgency is one nullable integer column and one `ORDER BY` term.** `journal.urgency` added by `ensure_journal_columns`; `claim_ready` orders `COALESCE(urgency, 0) DESC, id`. `CLAIM_LIMIT` keeps its meaning (16 units per profile per tick) and background work keeps its FIFO order among itself, so nothing is starved: a requested unit takes a slot, it does not take the tick.
- **Progress rides `SyncPhase::DownloadingLfs`.** The queued branch already publishes it from `do_lfs`; the inline branch publishes one frame of the same phase with `current = Some(subpath)` around the copy, through `Engine::progress`/`publish`. No new phase, no new field, no new channel, and `phase_str` in the shell is untouched.
- **A modified worktree file is never overwritten, and the refusal is typed** (FR-338). `lfs::hydrate::ContentRefusal` — a standalone enum with a hand-written `Display`, the idiom `BrowseRefusal`/`WriteRefusal`/`ExportRefusal`/`ServeRefusal` already establish — carried on one new `SyncError::Refused(ContentRefusal)` so it survives the two exhaustive matches that must classify it (`keeper-syncd::sync_exit_code`, `keeper::sync_ipc::sync_ipc_error`) without 56.4 having to add five more `SyncError` variants.
- **Length leads, and the tie goes to not touching bytes.** A worktree file whose length equals the pointer's size and which is not pointer text is `AlreadyMaterialized` — the same length-first discipline `prune::worktree_holds_content` uses, and the direction that errs toward writing nothing. Anything else that is not the committed pointer is `LocallyModified`.
- **Containment is `browse`'s rule, not a second one.** `browse::plain_segments` refuses absolute paths, `..`, empty and non-plain segments; its `BrowseRefusal` is carried into `ContentRefusal::Escapes` unchanged (`ServeRefusal::Escapes`'s shape).
- **The repository is opened read-only.** `git::repo::open`, never `Engine::open_repo` — which clones a missing remote or adopts a plain folder, the high-severity defect 56.2's review found in a sibling verb. `refresh_index_stat` writing the index through a read-only open is the existing `repair_index_stat` precedent (`engine.rs:5774-5775`).
- **One operation at a time per profile.** The method takes `Engine::reserve`; a busy profile is `SyncError::Busy(profile.name)`, exactly as `sync_once` answers, because two writers over one index is how you get concurrent index locks.
- **The request outranks arrival policy, and only for its own unit.** `materialize_landed` gains a `requested` flag threaded from the claimed row's urgency; it bypasses the `LfsMode::Materialize` gate and nothing else. `LfsMode::Disabled`, the sparse cone, the pointer-text check and the store-contains check all still hold.
- **`--json` follows the `ls-files` contract 56.2 set**: pure renderers taking their data as parameters (never post-hoc `entry["k"] = …`), a key absent rather than null when it does not apply, and the document printed once.

**Block If:**
- The `#[cfg(not(desktop))]` twin the invocation asks for is judged mandatory for a *sync* command (see Design Notes: `mod sync_ipc` is `#[cfg(desktop)]`, no `sync_*` command has a twin, and `command-registration.test.ts` asserts mobile ⊆ desktop only — a twin would need a new home in `ipc.rs` and would be unreachable).

**Never:**
- **Not a second materialization path, and not `materialize_pending`.** The whole-tree sweep is not reused per path: its own comment records 40 hours lost to calling it per object. It is unchanged.
- **Not an arrival-behaviour change.** `VirtualPolicy` is still consulted nowhere: a request is a user overriding what may stay away, not an application of the policy. Wiring the policy into `materialize_pending` is FR-330's second half and belongs to 56.5 ("what future arrivals materialize"); recorded in `deferred-work.md`.
- **Not a release, a TTL, a pin writer or a sweep** (56.4/56.5). `ContentRefusal` is named and documented for 56.4's five refusals but grows none of them here.
- **Not a ledger-clock change.** `remember_materialized` still touches only `at_ms`; `last_used_ms`/`synced_at_ms` stay unwritten (56.5).
- **Not a UI change.** No `FilesSyncStatusVm` variant, no row action, no `Record` map, no Files-pane rendering (56.7/56.9). The frontend gets exactly one `client.ts` wrapper so the command is reachable and pinned.
- **Not a CLI progress subscription.** `keeper-syncd` has no event loop and no subscriber; a queued unit is delivered by the supervisor, and the verb says so.
- No new crate, no new dependency, no `meta` migration marker, no change to `CLAIM_LIMIT`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| The object is already in the store | committed pointer in the worktree, object present | worktree holds the real bytes, ledger row written, index stat refreshed, outcome `materialized` | No error expected |
| `git status` afterwards | the same repository, real `git` | `git status --porcelain` is empty | No error expected |
| The object is absent | pointer text, empty store | one `LfsDownload` unit, labelled with the path, urgency `requested`, outcome `queued` with its `unitId`; no bytes written | No error expected |
| A repeat request | the same path asked for twice | the same `unitId`, exactly one journal row, no second download | No error expected |
| Repeat while running | covering row already `running` | same `unitId`, no new row (`covered_while_running`) | No error expected |
| Urgency in one tick | 20 background units queued, then one requested | `claim_ready(…, 16)` returns the requested unit **first**, and 15 background units behind it in id order | No error expected |
| Urgency survives a restart | requested unit `running`, then `recover_running` | the row is pending again and still `requested` | No error expected |
| Already materialized | worktree holds the content, length equals the pointer's size | outcome `alreadyMaterialized`, no write, no unit, ledger untouched | No error expected |
| Locally modified | worktree bytes are neither the pointer nor the pointer's length | refusal `LocallyModified`, and the file's bytes are byte-for-byte unchanged | `SyncError::Refused`, `code() == "refused"`, `Permanent` |
| Pointer text for another object | worktree holds a *different* valid pointer | refusal `LocallyModified` | as above |
| A directory at the path | `40-media/clip.mp4` is a directory | refusal `LocallyModified` | as above |
| Deleted from the worktree | tracked pointer, file absent | refusal `Missing` — materializing would silently undo a deletion | `SyncError::Refused` |
| Not an LFS path | plain tracked file, or a path git does not track | refusal `NotTracked` | `SyncError::Refused` |
| Outside the profile's subpaths | `subpaths = ["docs"]`, request `40-media/clip.mp4` | refusal `OutsideSubpaths` | `SyncError::Refused` |
| Escaping subpath | `../etc/passwd`, `/etc/passwd`, `` | refusal `Escapes(BrowseRefusal)` carrying browse's own sentence | `SyncError::Refused` |
| No repository | folder with no `.git` | refusal `NotTracked`, and **no `.git` is created** | `SyncError::Refused` |
| LFS disabled | `lfs_mode == Disabled` | refusal `LfsDisabled` — nothing routes this path through LFS, so publishing content over the pointer would make the next commit rewrite the blob with the real bytes | `SyncError::Refused` |
| Profile busy | a sync tick holds the reservation | `SyncError::Busy(name)` | exit 1, `code() == "busy"` |
| Unknown profile (engine) | `materialize_entry("nope", …)` | `SyncError::Config` | exit 2 |
| Unknown profile (CLI) | `materialize nosuch a.mp4` | refusal naming the alternatives | `select`'s `SyncError::Config`, exit 2 |
| `PointerOnly` completion | requested unit lands under `lfs_mode = PointerOnly` | `materialize_landed` publishes it; a background unit for the same mode still does not | No error expected |
| A journal predating the column | pre-56.3 `journal` DDL + one pending row | `migrate` adds `urgency`, the row still claims, a second `migrate` changes nothing | No error expected |
| CLI human form | `materialize media 40-media/clip.mp4` | one line naming the outcome, the honest size and the path | No error expected |
| CLI JSON form | `--json` | keys exactly `profileId`, `profile`, `path`, `oid`, `sizeBytes`, `outcome`; `unitId` **only** when queued | No error expected |
| CLI parse | two required positionals | `materialize` with one argument is `MissingRequiredArgument` | clap, exit 2 |

**Acceptance Criteria:**

- Given a virtual path whose object this machine already holds, when either door asks for it, then the worktree holds the real bytes, the path reads clean under the real `git status`, and no second publish path exists in the tree (`lfs::stage::materialize` is still the only one).
- Given a virtual path whose object is absent, when the same path is asked for twice, then the journal holds exactly one `LfsDownload` row both times, its id is returned both times, and no second transfer is queued.
- Given a tick in which 16 background units and one requested unit are claimable, when the claim runs, then the requested unit is in the claimed batch and ahead of every background unit, `CLAIM_LIMIT` is unchanged, and the background units keep their FIFO order among themselves.
- Given a worktree file that a user has edited, when it is asked for, then the call fails with a refusal the caller can distinguish by type, the file's bytes are unchanged, and no journal row is created.
- Given `lfs_mode = PointerOnly`, when a requested download lands, then its path is published; when a background download for the same profile lands, then it is not.
- Given the `keeper` shell crate cannot be compiled on this host, when `sync_ipc.rs` and `lib.rs` are changed, then the change is written in full, `bun run test` (which includes `command-registration.test.ts`) passes, and the report names the symbols the macOS gate must confirm.

## Design Notes

**Why urgency is a column and not a second queue.** `claim_ready` is one statement over `state = 'pending' AND not_before_ms <= now`, ordered by rowid; the sort has no index behind it today, so prepending a term breaks no invariant. A separate "urgent" table or a `not_before_ms = 0` trick would both be indirections: the first duplicates the claim, the second lies about scheduling and still loses to an older background row. One nullable integer, `COALESCE(urgency, 0) DESC, id`, keeps every existing property — FIFO within a level, `CLAIM_LIMIT` per profile per tick, one bounded batch — and makes the new one assertable in a single `claim_ready` call with no clock and no sleeping.

The urgency must be written by a **separate narrow UPDATE**, not through `enqueue_unique`, and that is not a style choice: `enqueue_unique` deduplicates on the serialized payload, so an urgency field inside `WorkKind::LfsDownload` would make the requested unit a *different* unit from the background one and download the same bytes twice — the defect `enqueue_unique`'s doc records (106 units for 95 objects). `db::label_unit` is the existing shape for exactly this; urgency copies it and inverts the tie-break, because a label must not flicker (first writer wins) while a request must be able to raise a row a background scan queued (`MAX`).

**Why the completion arm needs the flag.** `materialize_landed` opens with `if profile.lfs_mode != LfsMode::Materialize { return Ok(()); }`. That is right for arrival — `PointerOnly` means "leave what arrives as pointers" — and fatal for this story, because `PointerOnly` is the mode in which paths are virtual in the first place. Without the flag, a request under `PointerOnly` would fetch the object into the store, return `Ok`, and leave the worktree holding pointer text: green tests over an inert feature. The flag is derived from the claimed row (`WorkItem.urgency`), so it is the *journal* that remembers a human asked, not a second ledger, and it bypasses exactly one gate: the sparse cone, the pointer-text check and `store.contains` still hold, because each of those is a fact about the path rather than a policy about arrival.

**Where the refusal lives, and what 56.4 inherits.** The crate has two idioms and both are used deliberately. Typed refusals are standalone enums with hand-written `Display` (`BrowseRefusal`, `WriteRefusal`, `ExportRefusal`, `ServeRefusal` — which composes `BrowseRefusal` exactly as `ContentRefusal::Escapes` does); `SyncError` is a flat transport taxonomy whose two exhaustive matches (`sync_exit_code`, `sync_ipc_error`) force a decision on every new variant. This story needs both properties, so it takes both: the vocabulary is `ContentRefusal`, and one `SyncError::Refused(ContentRefusal)` carries it. The consequence 56.4 inherits is the point — five more refusals are five more `ContentRefusal` variants and **no** further churn in the two exhaustive matches, no five new transport variants, and one `Display` to read them all.

`ContentRefusal` is named for the guarantee rather than the verb: keeper will not change the bytes at this path. That is the same sentence on both sides of the epic — materialize must not overwrite a modification, release must not delete one — which is why 56.4 extends it (`Open`, `UnprovenOnRemote`, `Pinned`, `AlreadyPointer`) instead of writing a `ReleaseRefusal` beside it.

**The length tie, stated so it is chosen.** `plan` cannot distinguish "the content is here" from "an edit that happens to be the same length" without hashing a file that may be gigabytes. It calls that case `AlreadyMaterialized` and writes nothing — the direction that cannot lose bytes — which is the same trade `prune::worktree_holds_content` already makes for the same reason. The opposite reading would have this verb overwrite a same-length edit.

**A write consults `lfs_mode`; 56.2's read must not.** `Engine::lfs_files` deliberately stopped asking the mode — a folder switched to `disabled` with pointers already committed still *has* virtual paths, and answering "no LFS paths" was the assembled-twice divergence 56.2's review fixed. Materializing is the opposite case: under `Disabled` nothing routes the path through the clean filter, so real bytes in the worktree are a content change that the next commit would publish as a new blob. So the listing reports what is there and the verb refuses to act, and the refusal names the mode rather than pretending the path is untracked.

**Why no `#[cfg(not(desktop))]` twin.** The invocation asks for one, and this is the one place the spec declines with evidence. `mod sync_ipc` is itself `#[cfg(desktop)]` (`lib.rs:55-56`); the mobile splice registers nine `ipc::notes_capture_*` commands and nothing else (`lib.rs:1086-1097`); no `sync_*` command in the tree has a twin; and `command-registration.test.ts`'s third assertion is `mobile ⊆ desktop`, explicitly documenting desktop-only commands with no twin as the normal case. A twin would need a new home in `ipc.rs`, would register as `ipc::sync_materialize_entry`, and would be unreachable from a frontend that gates on `CapabilitiesVm`. The invariant the invocation is protecting — the handler list has the same shape on every target — is satisfied by the existing mobile ⊆ desktop assertion.

**Why the CLI does not wait for a download.** `keeper-syncd` has no event subscription and no tick loop; every non-`watch` verb awaits a one-shot engine method. Draining the journal inline to deliver the object would also make urgency pointless — the whole reason a requested unit needs to outrank background work is that the *supervisor* claims it. So the verb requests, `wake_now` collapses the wait to the next tick, and the outcome word (`queued`, with its `unitId`) says what happened. `--json` therefore has a stable answer for an agent to poll `ls-files` against.

**Why the Tauri command returns nothing.** The CLI needs the outcome because it prints it; the app does not, yet — 56.7 owns the row states and 56.9 the button, and the facts a row needs already have surfaces: `Engine::lfs_files`/`browse` report whether a path is virtual or materialized, and `sync_subscribe_progress` reports `DownloadingLfs` with the path in `current`. A view model nothing renders would mean a new `keeper-core` type, a new generated binding and two uncast TypeScript fixtures to extend, all so the frontend could ignore it. `Result<(), IpcError>` is the same shape `sync_open_entry` and `sync_write_entry` already have, and the typed refusal still reaches the user as the envelope's sentence.
