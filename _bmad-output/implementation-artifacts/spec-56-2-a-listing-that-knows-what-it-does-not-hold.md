## Intent

**Problem:** A path whose worktree bytes are the committed LFS pointer renders as ~130 bytes on every keeper surface, because `browse.rs` reports `fs::metadata().len()` while the honest answer — the pointer's `size` and `oid` — is already written in `lfs::stage` and unused. Nothing states which paths are virtual, no entry carries a modification time, there is no listing a human or an agent can ask, and the `materialized` ledger has no room for the columns 56.5 needs.

**Approach:** Report the pointer's own size and oid wherever a path holds pointer text, add `EntrySyncStatus::Virtual` to the engine's existing vocabulary, carry an mtime off the `stat` the listing already pays for, add a `keeper-syncd ls-files` verb with a human form and a stable JSON form whose remote-presence key appears only when asked for, and grow the `materialized` table by the additive `ensure_*_columns` idiom. Delete the second inlined copy of the index-size derivation in `engine.rs`.

## Boundaries & Constraints

**Always:**
- **The honest size comes from the pointer, never the worktree stat** (FR-336, AD-127). A path holding pointer text reports `pointer.size` and `pointer.oid`; a plain file is untouched and still reports its `stat` length, `Some(0)` included.
- **`browse.rs` never opens a `gix::Repository`.** Its module doc forbids it in two places (`browse.rs:25-36`, `:672-676`): "opening is where trust levels, config enforcement and index refreshes live". The worktree bytes of a virtual path *are* the committed pointer byte for byte (FR-331, established by 56.1), so parsing them is the same answer without the repository — and the read is bounded to `MAX_POINTER_BYTES` and only paid for a file already known to be that small.
- **Length leads, then a bounded read.** No path costs more than the one `stat` the listing already makes unless its length is in `(0, MAX_POINTER_BYTES]`, which is `prune::worktree_holds_content`'s existing discipline (`prune.rs:110-120`) and the only reason this is free.
- **One derivation, more callers.** `Engine::removed_size` (`engine.rs:4794-4815`) is deleted and its one call site calls `lfs::stage::indexed_size`. The bulk index reader this story adds delegates to the same private `index_key`/`pointer_blob` pair the single-path helpers use — no second spelling of the forward-slash key, no second pointer-blob rule.
- **A directory keeps the module's existing honesty rule**: `size_bytes` stays `None` for a directory (`browse.rs:113-119`), and the same rule extends to the new mtime — a directory's mtime is a real fact about the directory, so it is carried; its *size* is not and stays absent.
- **The state vocabulary extends what exists** (AD-127): `browse::EntrySyncStatus` gains `Virtual`; `PendingReason::Incoming { size_bytes, replacing }` stays the inbound vocabulary. No parallel type.
- **Every exhaustive `match` over `EntrySyncStatus` is answered deliberately.** There is exactly one in the workspace — `sync_ipc::sync_mark` (`sync_ipc.rs:2125`), in the `keeper` shell crate, which does not compile on Linux. It is still written, and the report names it.
- **`Virtual` is routed onto the wire's `Synced` with a Rust-composed sentence.** `FilesDeletePlanVm::compose`'s `travels` filter already counts `Synced` (`vm.rs:4412-4422`), so no delete plan can lie about a virtual path in the interim — which is what would happen if a new wire variant were added here without 56.7's explicit classification.
- **A 64-bit field on the wire carries `#[ts(type = "number")]`** or ts-rs emits `bigint` (`sessions/vm.rs:717-722`). Bindings under `src/lib/ipc/gen/` are regenerated by the ts-rs export test and committed, never hand-edited.
- **The ledger grows by `ALTER TABLE`, not by editing the `CREATE TABLE`** (`db.rs:102-106`, `:214-247`), nullable and without a `DEFAULT`, so a fresh install and one that predates the columns reach the same schema down one path. **No `meta` marker**: `db.rs:127-131` states that a schema addition is its own idempotence.
- **`remember_materialized` must stop being `INSERT OR REPLACE`.** Under the `(profile_id, path)` primary key it deletes and re-inserts, so a re-materialization would silently wipe every column this story adds. It becomes an explicit upsert that touches only `at_ms`.
- **Remote presence costs a round trip and is absent unless asked for** (FR-337, AD-127). The flag is spelled `--remote`, exactly as `verify --remote` is (`commands.rs:256-263`), and the JSON key is absent — not null — without it.
- `keeper-syncd` may depend on `keeper-sync` and nothing else first-party, so the listing's data lives in `keeper-sync` and only its two renderings live in the daemon.

**Block If:**
- Adding `mtime_ms`/`lfs_oid` to `FilesEntryVm` is judged to require a `FilesSyncStatusVm` variant in the same story (it is argued against in Design Notes, on the invocation's explicit 56.2/56.7 split).
- The daemon verb's name must not be `ls-files` for a reason not derivable here.

**Never:**
- **Not a wire-enum change.** `FilesSyncStatusVm` (`vm.rs:3812`) does **not** gain `virtual`, `materializing` or `materialized`, the three exhaustive `Record<FilesSyncStatusVm, …>` maps (`sync-status-mark.tsx:40`, `:49`, `:71`) are untouched, and `FilesDeletePlanVm::compose`'s `travels` filter is untouched. **That is 56.7's story**, and it inherits three obligations from here: replace `sync_mark`'s `Virtual → Synced` routing with the three wire states, give each a label, a shape and a tone in all three `Record` maps, and add every new variant to `travels` **explicitly** — the `matches!` is non-exhaustive, so a new variant compiles silently into the "stays on this machine" bucket (AD-134, FR-345). Nothing here is built for 56.7 to undo; the interim routing is chosen precisely so the delete plan stays correct until 56.7 arrives.
- **Not a materialize or release verb**, no TTL, no pin *writer*, no sweep, no dehydrate (56.3/56.4/56.5). The five new ledger columns are created and read; nothing in this story writes them except `at_ms`, which was already written.
- **Not an arrival-behaviour change.** `materialize_pending` (`engine.rs:5385`) is untouched and `VirtualPolicy` is not consulted anywhere: a path is virtual because its bytes are pointer text, not because a policy authorized it. Wiring the policy into arrival is 56.3's/56.4's.
- **Not a `verify` change** (56.6) and not a copy-planner change (56.6).
- No new crate, no new `SyncError` variant, no `meta` migration marker, no new IPC command, no new frontend rendering. The Files pane gains no mtime column — FR-340 is about the listing carrying the fact; rendering it is 56.7/56.9.
- `lfs::audit::tracked_objects`' per-path index re-open is a pre-existing cost and is not refactored here.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Pointer text in the worktree | real repo, committed pointer naming 4 MiB, worktree holds the ~130-byte pointer | `browse` reports `size_bytes == Some(4 MiB)`, `lfs_oid == Some(oid)`, `sync == Virtual` | No error expected |
| A plain file is unaffected | 12-byte `notes/a.md` beside it | `size_bytes == Some(12)`, `lfs_oid == None`, `sync == Synced` | No error expected |
| An empty file is still a size | zero-byte tracked file | `Some(0)`, not `None`, not `Virtual` (`pointer_blob`'s empty-blob rule) | No error expected |
| A directory | any folder | `size_bytes == None`, `lfs_oid == None`, `mtime_ms == Some(..)` | No error expected |
| Unreadable metadata | dirent whose `stat` fails | `size_bytes == None`, `mtime_ms == None`, `lfs_oid == None` | No error, no panic |
| Not a regular file | fifo / socket / device node | `size_bytes == None` as today; never read for pointer text | No error expected |
| A file just above the pointer ceiling | 1025-byte text file | never read; `size_bytes` is its `stat` length | No error expected |
| Pointer-shaped text that is not a pointer | 200-byte file starting `version http://example/…` | `Pointer::parse` says no; `stat` length stands; `Synced` | No error expected |
| Waiting beats virtual | pointer-text path that is also in the pending list | `Waiting { reason }`, not `Virtual` — the more actionable answer, per `classify`'s documented precedence | No error expected |
| Excluded beats virtual | pointer-text path matched by a profile pattern | `Excluded` | No error expected |
| No repository | pointer text in a folder with no `.git` | `NotInRepository` | No error expected |
| mtime is free | a listing of N entries | the same syscall count as before this story; mtime read off the bound `meta` | No error expected |
| `ls-files` on a folder with LFS paths | one virtual, one materialized, one deleted-from-worktree | three rows: `virtual` / `materialized` / `absent`, each with the pointer's `oid` and `sizeBytes` | No error expected |
| `ls-files` JSON shape | any listing | keys exactly `path`, `oid`, `sizeBytes`, `state`, `mtimeMs`, `materializedAtMs`, `lastUsedMs`, `syncedAtMs`, `pinned`; document is `{"files": [...], "total": n}` per profile under `"listings"` | No error expected |
| Remote presence absent by default | `ls-files --json` without `--remote` | no `remote` key on any profile entry, and no round trip | No error expected |
| Remote presence on request | `ls-files --json --remote` | `remote` key holds the `RemoteAudit` document, exactly as `verify --remote` splices it | Round-trip failure is a `SyncError`, exit non-zero |
| Human form names the honest size | one virtual 4 MiB path | the line contains `virtual`, `4.0 MB` and the oid; it never contains the pointer's own byte count | No error expected |
| LFS disabled | `lfs_mode == Disabled` | an empty listing, not an error | No error expected |
| Folder with no LFS at all | ordinary repo | empty listing, `total: 0` | No error expected |
| Unknown profile selector | `ls-files nosuch` | refusal naming the alternatives, exit 2 | `SyncError::Config` via `select` |
| An old `materialized` row | table planted at the pre-56.2 DDL with one row, then `migrate` | the row reads back with `last_used_ms`/`synced_at_ms`/`oid`/`size_bytes` `None` and `pinned == false`; `at_ms` unchanged | No error expected |
| Re-materialization preserves state | row with `pinned = 1`, then `remember_materialized` again | `at_ms` advances; `pinned` still true and every other new column intact | No error expected |
| `migrate` twice | already-migrated connection | no error, no duplicate column | No error expected |
| `removed_size`'s caller | a deleted LFS path in a commit's activity | the activity row's `size_bytes` is unchanged from before this story | No error expected |

**Acceptance Criteria:**

- Given a keeper surface that reports a path holding pointer text, when it reports that path's size, then the number is the pointer's `size` and never the worktree's ~130 bytes — asserted through `browse`, through `Engine::lfs_files`, and through both of the daemon listing's forms.
- Given the same repository, when a plain file, an empty file and a directory are listed beside the virtual path, then their size answers are byte-identical to what they were before this story.
- Given `engine.rs`, when the tree is searched for an index-blob-size derivation, then `lfs::stage::indexed_size` is the only one and `removed_size` no longer exists, with the deleted-path activity size unchanged.
- Given a `keeper-syncd ls-files --json` invocation without `--remote`, when the document is parsed, then no profile entry carries a `remote` key and no LFS batch request was made.
- Given a `sync.db` whose `materialized` table predates this story, when it is opened, then every existing row still loads, the five new columns read as absent, and a second `migrate` on the same connection changes nothing.
- Given a `materialized` row whose new columns hold values, when the path is materialized again, then only `at_ms` moves.
- Given the `keeper` shell crate cannot be compiled on this host, when `sync_ipc.rs` is changed, then the change is written in full and the report names `sync_mark`, `sessions_sync_mark` and `files_listing_vm` as the symbols the macOS gate must confirm.

- addressed_findings:
  - `[high]` `[patch]` A listing verb could clone a repository or adopt a folder. `Engine::lfs_files` reached for `Engine::open_repo`, which is the engine's *materialize* path: for a folder with no `.git` it clones over the network, or, for one with content in it, `git init`s in place, pins repo config and runs `reconcile_sparse_cone` over the working tree. An operator or an agent asking which paths are virtual on a configured-but-never-synced profile would have pulled gigabytes down, or silently turned a plain folder into a keeper repository — from the one verb whose entire promise is that it looks. Now: no `.git` answers with an empty listing, and the open is `git::repo::open`, which opens what is there and makes nothing. ## Design Notes

**Why `browse` parses the worktree pointer instead of opening the index.** AD-127 names `indexed_size`/`indexed_pointer` as the honest answer, and they are — for a caller that already holds a `gix::Repository`. `browse.rs` deliberately does not, and says so twice: "nothing in this module touches `Engine`… Everything here is `std::fs` reads plus one marker read, and it takes a `&SyncProfile` rather than an `&Engine` precisely so it *cannot* make that mistake" (`:29-36`), and "Asking gitoxide to open the repository … is exactly what this module must not do: opening is where trust levels, config enforcement and index refreshes live" (`:672-676`). Threading an index snapshot in as a fourth parameter would change `browse`, `browse_root` and `status_of` and every caller of all three — four call sites inside the shell crate that cannot be compiled on this host — to obtain an answer that is *identical by construction*: FR-331, settled by 56.1 against a real repository, is that a virtual path's worktree bytes **are** the committed pointer byte for byte. So the pointer is read where it already is. `indexed_pointers` exists for the caller that does hold a repository — the listing — and both it and the single-path helpers go through the one `pointer_blob`/`index_key` pair, which is what "one derivation" protects.

**The positive predicate, not prune's.** `prune::worktree_holds_content` looks like the function to reuse and is not: it begins `metadata.len() != recorded.size → false`, so a *locally modified* LFS file answers "does not hold content" and would be reported virtual. `worktree_pointer` asks the opposite question directly — are these bytes pointer text — and inherits only the discipline: length leads, so nothing above `MAX_POINTER_BYTES` is ever read.

```rust
pub fn worktree_pointer(absolute: &Path, meta: &std::fs::Metadata) -> Option<Pointer> {
    if !meta.is_file() { return None; }
    let len = meta.len();
    if len == 0 || len > pointer::MAX_POINTER_BYTES as u64 { return None; }
    // Bounded by the ceiling, not by the caller's `stat`: a file that GREW
    // past 1 KiB in between would otherwise be read to EOF and discarded.
    let mut bytes = Vec::with_capacity(len as usize);
    File::open(absolute).ok()?.take(MAX_POINTER_BYTES as u64).read_to_end(&mut bytes).ok()?;
    if !pointer::is_pointer_candidate(&bytes) { return None; }
    Pointer::parse(&bytes)
}
```

**Where `Virtual` sits in `classify`, and why the size follows it.** After `Excluded`, `Unknown`, `Waiting` and the repository check — last, and lazily. Review corrected this section twice over, in the same direction both times.

The first draft asserted that `Waiting` winning "disposes of the only false positive available". It disposes of it *for the mark*, and left it in the two fields the story exists to add: an untracked or excluded file holding pointer text got the mark it deserved **and** a fabricated four-gigabyte size with no sentence on the row to account for it — the 130-byte lie inverted. So the probe is not an independent computation feeding `classify`; it is the last question `classify` asks, and its answer is what produces both the mark and the size. `lfs_oid.is_some()` therefore means exactly "this row's size came from a pointer", which is what its field doc always claimed. The deliberate cost is that a `Waiting { Incoming }` row reports the pointer text's own length — `PendingReason::Incoming` already carries the content's size, and the mark's sentence already says the bytes have not arrived.

The second correction is the reason it is a closure rather than a `bool`. Taking it by value made every caller pay a `stat` and a bounded read *always*, including the five `classify` branches that never look at it: a session tree of small transcripts opened and read one file per entry to decide marks that were `Excluded` or `Unknown` before the question arose, and a thousand-entry listing paid a thousand extra opens on precisely the network volumes this module binds its `stat` once for. `impl FnOnce() -> bool`, consulted last, means the cost is paid exactly where the answer can change — and it leaves `list_resolved` free to capture the `Pointer` itself while `status_of` takes its own `stat`.

**Why the wire enum does not grow here.** The invocation draws the line: three UI states and the delete-plan classification are 56.7's. The interim routing is not a shrug — it is chosen for one property. `FilesDeletePlanVm::compose`'s `travels` filter is a **non-exhaustive** `matches!` over `Synced | Waiting | Unknown`, so a new variant added without touching it compiles silently into the "stays on this machine" bucket and the delete confirmation starts telling users a deletion is local while it removes tracked content (AD-134). Routing `Virtual` onto `Synced` keeps that answer correct with no code in `compose` at all, while the honest facts still reach the surface: `FilesEntrySyncVm::detail` carries the Rust-composed sentence, `size` carries the pointer's size, and `lfs_oid` carries the oid. 56.7 then adds the variants *and* the `travels` arms in one story, which is the shape the epic asked for.

**`Option<i64>` for the mtime, not the 0 sentinel.** Both spellings exist in `keeper-core`: `SessionEntryVm::mtime_ms: i64` with "0 when the OS would not say", and `#[ts(type = "number | null")] mtime_ms: Option<i64>` at `sessions/vm.rs:107-108`. The Files chain takes the `Option`, because it is the chain in which `size_bytes` is already `Option<u64>` for exactly this reason — `browse.rs:113-119` and `vm.rs:4044-4056` both say an unknown fact is absent rather than plausible — and a struct carrying `size: Option<..>` beside `mtime_ms: 0` would be answering the same question two ways. Nothing renders it yet, so no frontend gate has to be chosen now.

**The upsert, not the migration, is the dangerous half.** `ALTER TABLE … ADD COLUMN` guarded by `PRAGMA table_info` is its own idempotence and `db.rs:127-131` says so in the file. What is not safe is leaving `remember_materialized` as `INSERT OR REPLACE`: under the `(profile_id, path)` primary key SQLite deletes the conflicting row and inserts a fresh one, so the first re-materialization after this story would silently blank `pinned`, `synced_at_ms` and `last_used_ms` — and 56.5's release sweep reads `pinned` as its hard floor. Fixing it belongs to the story that creates the columns, because until they exist there is nothing to lose and afterwards the loss is invisible.
