## The two decisions the story asked me to make out loud

### 1. Where the second door goes: the control becomes a dropdown

Group 3 of `NoteEditor`'s header is at exactly two controls and AD-104 says why:
six controls plus two truncating spans do not fit the 560 px quick-capture window
(`notes_window.rs` `CAPTURE_SIZE`), the row does not wrap, and the last child is
the first thing off the edge — which is how 46.5's `⋯` came to be invisible. So a
third button was never available.

A correction worth carrying, from W3Files after their 46.13 extraction landed
under this change: the actions group is deliberately **not** `shrink-0` (46.4's
corrected ruling — the row squeezes the actions rather than pushing the last one
off the right-hand edge; the fixed box is the *status* slot beside it). So "two
controls" is a statement about the **budget**, not an overflow guard: a dropdown
trigger whose label grew would give ground rather than disappear. The guard is the
squeeze. The reason a third control was still not available is that group 3's
members compete with the identity group for a 560 px row, and 46.5 already spent
that budget getting `Delete` back on screen.

`Attach a file` becomes a `DropdownMenu` trigger with two items. It is also the
literal reading of the report ("in the dropdown"), and it is the only shape that
lets the two doors *say what they do before you choose*, which the story required.
The alternatives and why not:

| Option | Verdict |
| --- | --- |
| Second source inside the existing `Actions` menu | Rejected. That menu is 46.5's home for "things that act on or show the note as an object". An attach source is a *variant of one verb*, and splitting one verb across two controls is what makes a surface unlearnable. |
| Split button (primary press = today's picker, caret = the rest) | Rejected. It makes the new door second-class and hides the copy/no-copy difference behind a caret — the one thing that must be legible before the click. |
| Dropdown | **Chosen.** Group 3 still renders exactly two `<button>`s, so `note-actions.test.tsx`'s `expect(labels).toEqual([ATTACH_FILE_LABEL, NOTE_ACTIONS_TEXT])` passes verbatim. |

The trigger keeps `ATTACH_FILE_LABEL` as its text and accessible name, so every
existing `getByRole("button", { name: ATTACH_FILE_LABEL })` still resolves; what
changed for the tests is one interaction, not a query.

Each item carries a second line. Radix names an item from its text content, which
would have made this control answer to *"From this computerA file outside this
folder is copied into attachments/."* — unspeakable by anyone using speech input
(WCAG 2.5.3). So each item gets `aria-label` (the words on the control) plus
`aria-describedby` (the hint). The hint is a description, which is what it is.

### 2. Where the file browser comes from: `notes_gallery`, not a third tree

**I did not write a tree and I did not extract one from `files-pane.tsx`.**

- `files-pane.tsx` browses the wrong thing. It is keyed on a **sync profile id**
  with profile-relative paths; a note names a **vault-relative** path in its own
  vault, and the resolution between the two identifiers is Story 45.18's and lives
  in Rust. Its tree is also 1300 lines of virtualised multi-select with create,
  delete and reveal wired through it, coupled to `panels.ts` and `files-tree.ts`
  (both W3Files' this wave) — and it would offer files in *other* synced folders,
  which this door cannot attach by reference at all.
- `notes_gallery` already **is** the vault's directory reader. It goes through
  `keeper_sync::browse`, the repo's one directory reader, so the containment test,
  the built-in noise filter, the 1000-entry cap and the folders-then-files order
  are the same ones the Files pane shows. It answers with the vault-relative
  `relPath` a note embeds and the one classifier's `kind` (AD-73), and it composes
  every path in Rust (AD-65). **Nothing was added to Rust for the browsing.**

So the dialog is `AttachToNoteDialog`'s shape with a file chooser where its note
chooser is: rows, one verb per row, the reason where the button would have been
for a row that cannot be offered, one outcome slot, breadcrumb navigation.

**It browses this note's vault, not every synced folder.** A notes vault *is* a
folder you sync. A file in a different profile is not in this vault, so it cannot
be embedded by reference — it has to be copied, and the OS picker already reaches
it and already says it copied. Offering other profiles inside a dialog whose whole
promise is "nothing is copied" would break that promise on the first click.

## The ruling, and how it is kept by construction

An in-vault attach must not copy into `attachments/`. It does not, and not because
this component is careful:

**`notes_attach_sources` is the only thing in this app that copies a file into a
vault, and `AttachFromVaultDialog` does not call it.** It cannot: that command
takes absolute paths, and every path the dialog holds is already vault-relative
because `notes_gallery` answered with vault-relative paths. There is no code path
from this dialog to a copy. The path goes straight to `planAttachments` — the same
decision the other three entry points make — so the bytes are identical.

Asserted as an absence: `expect(notesAttachSources).not.toHaveBeenCalled()` and
`expect(notesBodyWrite).not.toHaveBeenCalled()`, and mutation-proven (M5).

### Distinguishing the two paths *before* the person acts

The story required it, because a file in no vault cannot be embedded by reference
at all (`keeper-note://` will not serve it) and must still be copied. The
distinction is on the menu, not in the receipt:

- **From this computer** — *"A file outside this folder is copied into
  attachments/."*
- **From a folder you sync** — *"Linked where it already is. Nothing is copied."*

and the dialog restates it as a promise before anything is chosen:
*"These files are already in this note's folder, so keeper links them where they
are. Nothing is copied."*

## The panel widening, and the honest answer about the probe

The story's sharpest instruction: *do not pretend a syntactic test is a
containment check.* I did not. **I gave the panel a source of truth.**

`bodyEmbedTargets(body)` is pure and syntactic and knows only what the text says:
every embed whose target names a file rather than a note, deduplicated on the
folded target, in document order. **No `attachments/` prefix test** — that folder
stopped being the test, so a bare `![[photo.png]]` and a `![[photos/a.png]]` are
both now *targets*.

`notes_embed_paths(vaultId, targets) -> Vec<Option<String>>` is the `stat`. It is
`embed_path_opt`, which is **literally the function** `notes_embed_read`,
`notes_csv_read` and the `keeper-note://` protocol resolve through:
`embed::candidates` order, `contained_read` containment, `is_file`. So the panel
cannot list a file the viewer would open differently or the exporter would refuse
to carry.

### Why a batched command and not `notesEmbedRead` or `notesGallery`

| Candidate | Verdict |
| --- | --- |
| `notes_embed_read` | **No.** It opens the file as text. A 4 GB video is not text, so the panel would report every video as absent. |
| `notesGallery` per parent folder | **No.** It would be a *second* resolution rule — list a directory, match by name — which can disagree with `embed::candidates` (it finds symlinks and fifos that `contained_read` refuses, and misses anything past the 1000-entry cap). The whole point of this story is that the panel and the exporter cannot disagree. |
| The whole body over IPC to `export::plan` | **No.** It moves the reader out of the webview, and the panel reads the *unsaved* buffer, which Rust has never seen. |
| `notes_embed_paths` | **Chosen.** Rust owns candidate formation, so nothing new is mirrored; TypeScript keeps the buffer, which is the only place it exists. |

`bodyEmbedPlan(body, resolved)` joins them and is line-for-line with
`keeper_core::notes::export::plan`, which takes its own probe as
`&dyn Fn(&str) -> bool` for exactly the same reason. Three buckets, not two:

- `present` — the **resolved** path (so a bare name shows the file it actually
  shows), deduplicated after resolution as `plan` deduplicates.
- `missing` — the target as the note spells it. `plan.missing`.
- `pending` — nothing has been asked yet. The bucket `plan` has no need for,
  because `plan` runs when the disk is already there and this runs mid-IPC.

**The panel never collapses `pending` into either claim.** "This note has no
attachments" and "that file is not in this vault" are both claims, and neither is
true while keeper is still looking. In flight → `"Looking…"`. Probe rejected →
*"keeper could not check which of this note's files are in the vault"* — about
keeper, not about the note, because keeper did not find out.

The probe is keyed on `targets.join("\u0000")`, not on the body: typing prose
changes the body every keystroke and the targets on none of them.
`AttachToNoteDialog` keys its own search the same way. Mutation-proven (M18).

### `names_a_note` is now pinned, not merely cited

46.2 mirrored `export::names_a_note` in TypeScript and deliberately did *not* add
it to `attach-vectors.json`, recording the trigger: **a second caller.** This story
is that trigger twice over — `bodyEmbedTargets` reads it, and the in-vault chooser
declines to offer a file it calls a note. So it is pinned: `names_a_note` is `pub`,
`attach-vectors.json` gained a 12-vector `noteTargets` array, and both suites
assert against it. That is the story's *"keep that property, and re-verify it after
your change rather than assuming it survived"*, mechanically rather than by
reading. Mutation-proven on the Rust side (M20).

### The 46.2 edge case this story makes live, and the answer

46.2 recorded "a body attachment whose name collides with a `files:` entry" as two
rows for two files — correct then, because the two lists were in two roots and the
body list only ever held `attachments/`. Both halves stopped being true here.

**The two lists are now disjoint by construction:** a body target whose *name*
matches one of the note's `files:` entries belongs to the session list. Matched by
name, which is the join key `embedded` and `kindOf` already use, for Story 40.4's
reason (the session folder is renamed after the note is written, so
`![[old/screen.mov]]` and `![[new/screen.mov]]` are one file).

This is also what stops the panel accusing a recording note of losing a file. A
recordings destination root may be anywhere — the fixture's is `~/Movies/keeper` —
so a session embed resolves to **nothing in the vault**, and it renders anyway
because `recording-embed.ts` resolves it against the session index rather than
through `keeper-note://`. Without the exclusion, pressing the panel's own Insert
button would have made the panel immediately say the file is not in the vault.
Mutation-proven (M17), and it is what M17 catches in 43.7's own
`cannot write the same attachment twice`.

## Edge cases

- **A vault folder is mostly notes**, so "why can I not attach this" is the first
  question this surface would raise. Every non-offerable row says why *before* the
  click, which is why `wikilinkNameable` was exported rather than left to
  `planAttachments`' after-the-fact refusal.
- **An extensionless file (`LICENSE`) cannot be attached.** By `names_a_note` it is
  a note, so `export::plan` would treat `![[LICENSE]]` as a transclusion and the
  panel would not list it. Offering it would create a row nothing else agrees with.
  Consistency with the exporter beats reaching that file; the row says why.
- **`notes_gallery`'s reply is discarded when its echoed `folder` does not match**
  the folder now on screen — that is what the echo is for.
- **The dialog stays open after an attach**, and the row flips to `In the note` off
  the live buffer. Several files from one folder is a real thing to want.
- **Focus after an in-vault attach lands on the dropdown trigger, not the editor.**
  `insertAtCursor` calls `editorView.focus()`, and Radix's modal focus management
  returns focus to the trigger when the menu/dialog closes. The caret is preserved
  and the text lands; the person clicks back into the text to keep typing. Inherent
  to "the door is a menu", and the same property `AttachToNoteDialog` already has.
- **Opening the attach menu fires the editor's blur save.** New, and correct — it
  is a real focus change. It surfaced as a test fixture bug: `notesSave` was mocked
  to answer the *recording* frontmatter, so an ordinary note silently acquired a
  `session:`. Fixed in the fixture and recorded there.
- **`ATTACHMENTS_DIR` was deleted from `attach.ts`.** After the widening it had no
  consumer, and its absence is a small strengthening of AD-65: the webview no
  longer spells that folder in code at all. The word still appears in the copy
  receipt, as prose, which is Rust's fact reported by the surface.

2. That `notes_embed_paths`' `spawn_blocking` closure satisfies `Send + 'static`

   plain `serde`, and `notes_vault_active` already returns `Option<String>`.
4. That the webview's capability files permit the new command. Registration is not

5. Any layout claim. jsdom performs no layout, so nothing here measures a width —
