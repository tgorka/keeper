## Intent

**Problem:** Epic 56 can put content on a machine and has no way to let it go. `lfs::stage::materialize` publishes content over a pointer; nothing does the inverse. `lfs::prune` deletes a *store* object and its condition 2 is *"the worktree still holds the real content"* — dehydration inverts exactly that predicate, so relaxing prune would silently convert a safe operation into a deleting one. This is the story where a bug destroys the user's only copy (AD-125, the epic's own riskiest seam).

**Approach:** A new primitive `lfs::stage::dehydrate` beside `materialize`, publishing the **committed pointer blob byte for byte** through the identical `.keeper.<name>.tmp` + `rename(2)` discipline, never truncating; one engine entry point `Engine::dehydrate_entry` that refuses by five distinguishable `ContentRefusal` variants before it writes anything and proves the remote can serve the object **at the moment of deletion**; the existing per-path `refresh_index_stat` afterwards so the path reads clean; and one door, `keeper-syncd dehydrate <profile> <subpath> [--json]`.

## Boundaries & Constraints

**Always:**
- **The bytes written are the committed blob, not a re-rendered pointer** (AC 1, AD-124). `indexed_pointer` hands back a *parsed* `Pointer`, and `Pointer::render()` reproduces the input byte for byte **only when `is_canonical()`** (`pointer.rs:224-226`); a pointer committed by another git-lfs client with a legacy version URL, unsorted keys or a non-minimal `size` renders to different bytes, a different blob hash, and a phantom modification forever (`lfs/mod.rs:105-108`, quirk 12). So a new raw-blob accessor reads the index entry's own bytes and writes those.
- **Publish, never truncate** (AC 1). Sibling `.keeper.{file_name}.tmp` in `target.parent()` — tier-0 excluded at `exclude.rs:77` — mode of the replaced file read *before* the write and applied to the staging file, then `std::fs::rename`. `rename()` leaves open descriptors on the old inode intact; `set_len`/`OpenOptions::truncate(true)` on the target is forbidden, because truncating a file another process has `mmap`ed delivers SIGBUS.
- **Five refusals, five `ContentRefusal` variants, five `Err(SyncError::Refused(..))` returns, five tests** (AC 2, FR-333). `Modified`, `Open` (+ its `OpenUnknown` arm, AC 3), `UnprovenOnRemote`, `Pinned`, `AlreadyPointer`. `ContentRefusal` is extended, never forked — `hydrate.rs:19-30` and `error.rs:186-199` already say so, and the vocabulary costs no churn in `error.rs` (`retriability`/`code` match `Refused(_)` opaquely) nor in the two exhaustive classifiers (`sync_exit_code:144`, `sync_ipc_error`'s `Refused(_)` arm).
- **Modified is content identity, not a stat comparison.** The worktree file must be a regular file whose length equals the committed pointer's `size` **and** whose SHA-256 equals its `oid`. A stat-only check would pass a same-length, same-mtime edit and delete it; the file is about to lose its only local copy, so one read is the price of proof. The length compare short-circuits the same predicate, it is not a second guard.
- **`Unknown` refuses** (AC 3, AD-125). A new **provided** `SyncPlatform` method — beside `utc_offset_minutes`, the trait's one existing defaulted method (`platform.rs:57-76`) — answers `OpenFileState::{Open, Closed, Unknown}` with `Unknown` as its body. Fail-**closed**, the deliberate inverse of `free_space`'s documented fail-open (`platform.rs:78-83`), and the doc must say so. Only `TestPlatform` overrides it; `LinuxPlatform` and `ShellSyncPlatform` are untouched, which is required — the shell crate cannot be compiled on this host.
- **The remote proof is per-object, affirmative and fresh** (AC 5, NFR-40, AD-123). A `download`-operation batch for exactly this one oid; proven only when a spec **for that oid** came back with `error.is_none()`. `audit::report`'s default is "assume present when nothing came back" — right for a report, fatal for a deletion — so a new `audit::serves` requires the affirmative row. A filesystem remote has no batch API and is proved directly and per-object by `lfs::local::remote_store(url).contains(oid, size)`. Every failure to *ask* — network, auth, quota, a batch-level 404 meaning the repository is invisible (`batch.rs:347-349`) — collapses into `UnprovenOnRemote`, never into a `Retriability::Transient` fault a scheduler would re-drive against a deletion. `materialized.synced_at_ms` may be written by a proof; it is never read as one.
- **The index stat is repaired, by the existing repair** (AC 4, DW-140's shape). `git::repo::refresh_index_stat(&repo, &[rela])` on that one path after the rename — never `repair_index_stat`, the whole-repo button. Without it `is_false_modification`'s condition (a) fails and every dehydrated path reads MODIFIED forever, at the cost of a full content comparison on every status walk (`stage.rs:1421-1429`).
- **Free checks before the reservation, disk after, the two deletion proofs last.** `Engine::dehydrate_entry` mirrors `materialize_entry`'s guard order (`engine.rs:6103-6310`) exactly: `get_profile` → `plain_segments` → empty-segments → `browse::resolve` → `Paused` → `volume_ready`/`MediaAbsent` → `reserve`/`Busy` → `LfsDisabled` → `.git` exists → `indexed_pointer_blob`/`NotTracked` → `SparseCone`/`OutsideSubpaths` → `Missing`/`AlreadyPointer` → `Pinned` → `Modified` → `UnprovenOnRemote` → `Open` → write. `git::repo::open`, never `Engine::open_repo` — a release verb must not clone or adopt a folder. Every repo handle lives in a scoped block dropped before any `.await`: `gix::Repository` is `!Send` and this method is `async`.
- **The store is not a precondition, and that is deliberate.** `materialize` requires `store.contains`; `dehydrate` must not, because `lfs_prune_local` deletes the store copy precisely *when the worktree holds the content* — the common state of a materialized path. Requiring it would make the verb refuse almost always. NFR-40 therefore rests entirely on the remote proof, which is what NFR-40 says.
- **One-fact writes.** `db::forget_materialized` deletes only `(profile_id, path)`; `db::is_pinned` reads one column for one path and treats an absent row as unpinned (`db.rs:559-562`). Nothing widens `remember_materialized`, whose doc records that an `INSERT OR REPLACE` silently blanked `pinned` and that the loss was invisible (`db.rs:477-493`).
- **`--json` follows the `ls-files`/`materialize` contract**: pure renderers taking their data as parameters, a key **absent** rather than null when it does not apply, the document printed once.

**Block If:**
- A real `open_file_state` answer is judged mandatory for this story. AD-125 forbids an `lsof`-shaped snapshot ("'Open' must be a kernel fact"), `/proc/*/fd` scanning is exactly that and is unreadable for other uids besides, macOS has no `/proc` and no std-only answer, and this crate carries no `libc`/`nix`/`rustix` and denies `unsafe_code`. The consequence — the verb refuses on every production host until a platform supplies a race-free answer — is recorded, not hidden.

**Never:**
- **Not the TTL sweep.** No `synced_at_ms`/`last_used_ms` writer, no per-profile TTL field, no per-pass budget, no call on the `mark_synced` success edge, no `prune_lfs_store` change. **That is story 56.5 and explicitly not this story** (AC 6).
- **Not a pin writer.** 56.4 *reads* `materialized.pinned`; FR-334's writer is 56.2/56.5's and the row action is 56.7's. The refusal is therefore not yet reachable in production; the test sets the column directly, as `db.rs:2607` already does.
- **Not a relaxed `prune`.** `prune.rs` is unmodified and uncalled. Its condition-3 prose names the *upload* batch as proof; this story chooses the *download* batch, with AD-125 and `audit.rs:36-38` behind it, and says so rather than leaving two authorities disagreeing.
- **Not an app door and not a UI change.** No Tauri command, no `client.ts` wrapper, no `SyncProfile`/`SyncProfileReq` field, no `FilesSyncStatusVm` variant, no row action. `src-tauri/crates/keeper/**` is **untouched**, so nothing in this story needs the macOS gate. FR-332/FR-333 name no app surface; 56.7 owns the Release row action and needs its states first.
- **Not a `VirtualPolicy` consumer.** A human asking to release one path is overriding what may stay away, not applying a policy (AD-123: the policy never authorizes a deletion).
- No new crate, no new dependency, no `meta` migration marker, no ts-rs type.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| The happy release | materialized path, remote proves the object | worktree holds the committed blob byte for byte, inode changed, ledger row gone, outcome `released` with the pointer's oid and size | No error expected |
| `git status` afterwards | the same repository, real `git`, index stamped forward | `git status --porcelain` is empty | No error expected |
| A non-canonical committed pointer | index blob spells `size` non-minimally | the worktree bytes equal the **blob**, and differ from `Pointer::render()` | No error expected |
| A reader holds it open | `File` kept open across the call, capability says `Closed` | the open descriptor still reads the original content; the path's inode changed; the path now holds pointer text | No error expected |
| Modified, same length | bytes replaced with different bytes of identical length and the mtime restored | refusal `Modified`; bytes byte-for-byte unchanged; ledger row intact | `SyncError::Refused`, `code() == "refused"`, `Permanent` |
| Modified, ordinary edit | an editor save | refusal `Modified` | as above |
| Something holds it open | capability answers `Open` | refusal `Open`; nothing written | `SyncError::Refused` |
| No race-free answer | capability answers `Unknown` (the trait default) | refusal `OpenUnknown`; nothing written | `SyncError::Refused` |
| Remote cannot serve it | filesystem remote whose store lacks the object | refusal `UnprovenOnRemote`; nothing written | `SyncError::Refused` |
| Remote cannot be asked | unreachable URL remote | refusal `UnprovenOnRemote`, **not** `Network` | `SyncError::Refused` |
| Remote answered about another oid | batch returns no spec for this oid | refusal `UnprovenOnRemote` — silence is not proof | `SyncError::Refused` |
| Pinned | `materialized.pinned = 1` | refusal `Pinned`; the row survives | `SyncError::Refused` |
| Already a pointer | worktree holds the committed pointer | refusal `AlreadyPointer`; the CLI reports it as a no-op and **exits 0** | `SyncError::Refused`, exit 0 at the door |
| Deleted from the worktree | tracked pointer, file absent | refusal `Missing` | `SyncError::Refused` |
| Not an LFS path | plain tracked file, or untracked | refusal `NotTracked`; no `.git` is created | `SyncError::Refused` |
| Outside the cone | `subpaths = ["docs"]`, ask for `40-media/clip.mp4` | refusal `OutsideSubpaths` | `SyncError::Refused` |
| Escaping subpath | `../etc/passwd`, `/etc/passwd`, ``, a symlinked parent | refusal `Escapes(BrowseRefusal)` | `SyncError::Refused` |
| Paused / LFS disabled / absent volume | folder paused, `lfs_mode = Disabled`, unplugged removable | `Paused`, `LfsDisabled`, `SyncError::MediaAbsent` | refusals / `MediaAbsent` |
| Profile busy | a sync tick holds the reservation | `SyncError::Busy(name)` → CLI exit 1 with a sentence | `Operational` at the door |
| Unknown / ambiguous profile | `dehydrate nope a.mp4`; a name matching two folders | `SyncError::Config` naming the alternatives / asking for the id | exit 2 |
| Length moved under the read | file grows between the hash and the rename | `SyncError::Integrity`, nothing published, no staging file left | propagated |
| CLI JSON | `--json` released | keys exactly `profileId, profile, path, oid, sizeBytes, outcome` | No error expected |
| CLI JSON | `--json` already a pointer | keys exactly `profileId, profile, path, outcome`; `oid`/`sizeBytes` **absent** | No error expected |
| CLI parse | two required positionals | `dehydrate` with one argument is `MissingRequiredArgument` | clap, exit 2 |

**Acceptance Criteria:**

- Given a materialized path whose object the remote provably holds, when it is released, then the worktree bytes are **byte-identical to the committed blob**, the path reads **clean** under the real `git status` with the index stamped forward, the `materialized` row is gone, and the path's inode changed — proving a rename rather than a truncation.

- Given each of the five refusals in turn, when the release is asked for, then it fails with a `ContentRefusal` variant the caller distinguishes **by type**, `code() == "refused"`, nothing on disk changes, and **the same test fails when that guard is removed** — proven by mutation for all five plus the index-stat repair, verified by reading `git diff` rather than by recollection.
- Given a platform with no race-free open-file answer, when the release is asked for, then it refuses; and given the `SyncPlatform` trait default, then that answer is `Unknown`.
- Given a remote that cannot be asked or that answers about no such object, when the release is asked for, then it refuses `UnprovenOnRemote` rather than raising a transient fault, and no deletion is authorized by an age, a pattern, a ref comparison or a stored `synced_at_ms`.
- Given `keeper-syncd dehydrate <profile> <subpath> [--json]`, when the path is already a pointer, then the exit status is 0 and the document says `alreadyPointer` with no `oid` key; for every other refusal the exit status is 1.
- Given the shell crate cannot be compiled here, when this story lands, then `src-tauri/crates/keeper/**` is unchanged and the macOS gate has nothing new to confirm.

## Design Notes

**Why the modified check hashes.** `is_false_modification` (`stage.rs:1078`) is the tree's existing "is this materialized path in agreement with the index" predicate and its condition (a) is a stat comparison. A stat comparison is the right *cost* optimisation for a status walk and the wrong *proof* for a deletion: a same-length edit written back with the original mtime passes it, and the release then destroys the edit with a green suite. Content identity — length, then SHA-256 against the committed `oid` — is one predicate that cannot be fooled, and it also removes any need to reason about git's racily-clean rule, which stat comparisons must. The file is about to lose its only local copy; reading it once is the price of being allowed to.

**Why the store is not a precondition, and `materialize`'s mirror is not symmetric here.** `materialize` refuses unless `store.contains(oid, size)` — it is copying *from* the store, so absence is fatal. `dehydrate` is not copying from the store, and requiring the store to hold the object would refuse in the most common state of all: `lfs_prune_local` releases the redundant store copy exactly when *"the worktree still holds the real content"* (`prune.rs:28-33`), which is the definition of a materialized path. So the local store says nothing here, and NFR-40 rests where NFR-40 puts it — on a per-object remote proof taken at the moment of deletion.

**Why the proof is the `download` batch and not the `upload` batch.** `prune.rs:34-39` names the upload batch (an object with neither `actions` nor `error` means the server already has the content). `audit.rs:36-38` and AD-125 name the download batch (a per-object 404 is the server saying *"I cannot serve this"*). They are different questions: upload asks *may I send this*, download asks *can you give me this*, and only the second is the question a reader of a released file will later ask. This story chooses download and says so, because leaving `prune`'s paragraph as the last word would make the next reader think the choice was an oversight.

**Why every failure to ask is a refusal, not an error.** `BatchClient` maps a transport failure to `SyncError::Network` (`Retriability::Transient`), a batch-level 404 to `SyncError::Config`, and an unauthenticated answer to `SyncError::Auth`. Propagating any of them from a release turns "I could not establish that these bytes exist elsewhere" into a fault a scheduler is entitled to retry — and 56.5 will drive this verb from a sweep. Collapsing them all into `UnprovenOnRemote` (`Permanent`, `needs_user_action() == false`) preserves the only sentence that matters: keeper will not delete these bytes. The reason is logged `warn!`, so an operator can still tell an unreachable server from an absent object.

**Why a filesystem remote is proved directly.** `audit_remote_objects` reports a filesystem remote intact **without asking anything** (`engine.rs:5949-5956`), which is defensible for a report and would be a fabricated authorisation for a deletion. A filesystem remote's LFS store is a real directory in the client layout (`lfs/local.rs`), so `remote_store(url).contains(oid, size)` is a genuine, per-object, size-verified proof — strictly better evidence than a batch answer, and it is what makes the happy path of this story assertable in an integration test with no network at all.

**Why `AlreadyPointer` is a refusal that the door reports as success.** Both halves of the acceptance are literal: it must be "a distinguishable typed error a caller can branch on", and saying it "is not an error the caller must handle as a failure". Making it an outcome (56.3's `AlreadyMaterialized` shape) satisfies the second and abandons the first; making it a refusal the engine swallows satisfies neither. So `Engine::dehydrate_entry` returns `Ok` only when it released something — one uniform contract, five refusals with five identical test shapes — and `cmd_dehydrate` *demonstrates* the branch: `nothing_to_release` matches that one variant and renders a no-op at exit 0, while every other refusal exits 1. The branch is a pure function with its own test, which is the strongest available evidence that the five errors really are distinguishable.

**Why the verb refuses on every real host today, and why that is the honest answer.** `open_file_state`'s default is `Unknown` and nothing overrides it outside `TestPlatform`. On Linux the only std-only answer is a `/proc/*/fd` scan — which is an `lsof` snapshot, TOCTOU by construction, and unreadable for other uids; AD-125 refuses it by name. macOS has no `/proc` and no std-only answer at all, and this crate carries no `libc`, `nix` or `rustix` and the workspace denies `unsafe_code`. Guessing here is the one guess that deletes data, so the trait states its ignorance and the operation refuses. The consequence is that `dehydrate` — and therefore 56.5's sweep — releases nothing until a platform supplies a race-free answer; that is recorded as deferred work, stated in `docs/sync.md`, and reported rather than discovered.

**Why no app door.** 56.3 added a Tauri command because FR-338 says "from the daemon **or the app**". FR-332/FR-333 name no app surface, 56.7 owns the Release row action and needs its row states first, and `src-tauri/crates/keeper/**` cannot be compiled on this host. Leaving the shell untouched is the risk reduction available to the one story in this epic where a mistake destroys data: nothing here needs the macOS gate, and no `SyncProfile` field is added, so `sync_ipc.rs`'s `EXPRESSED`/`PRESERVED` classification is untouched.

### Residual risks

- **The verb refuses on every production host today, by design.** `open_file_state`'s default is `Unknown` and nothing overrides it outside `TestPlatform`: on Linux the only std-only answer is a `/proc/*/fd` scan, which is the `lsof` snapshot AD-125 refuses by name and is unreadable for other uids; macOS has no std-only answer at all; and this crate carries no `libc`/`nix`/`rustix` while the workspace denies `unsafe_code`. Guessing here is the one guess that deletes data. Stated in `docs/sync.md` and on the trait, and it means 56.5's sweep will release nothing until a platform supplies a race-free answer.
- **A release also requires `LfsMode::PointerOnly`,** because `materialize_pending` puts the content straight back in any other mode. This is a mode gate rather than a limit: it lifts when the virtualization policy reaches the arrival sweep, which 56.3 recorded as 56.5's half of FR-330.
- **The `Pinned` refusal is not yet reachable in production.** 56.4 reads `materialized.pinned`; FR-334's writer is 56.2/56.5's and the row action is 56.7's. The test plants the column directly, as `db.rs`'s own pin test does.
- **git's racy-clean second** — for up to one second after a release, `git status` compares content rather than the refreshed stat. Pre-existing, shared with the materialize direction; the tests stamp the index forward rather than sleeping.
