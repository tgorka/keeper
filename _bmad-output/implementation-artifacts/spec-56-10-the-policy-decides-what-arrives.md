## Intent

**Problem:** Epic 56 shipped nine stories and `VirtualPolicy` has exactly **one** production consumer — `Engine::verify` (`engine.rs:8055`), which only *excuses* a pointer whose object is absent. The arrival path, `Engine::materialize_pending` (`engine.rs:6063`), still branches solely on `profile.lfs_mode == LfsMode::PointerOnly` (`:6095`, `:6124`), so `virtualPatterns` cannot keep one single path virtual: the only way to get pointer text is to set the whole profile to `PointerOnly`, which makes *everything* virtual. FR-328 says a folder may declare "which paths are allowed to stay unmaterialized **after a pull**" and that half was never built — the same function's `PointerOnly` branch fetches nothing, so the path's object is not downloaded either, which is the half of the ask the owner can actually see. And `release_mode_gate` (`engine.rs:9099`) returns `Ok` **only** for `PointerOnly`, so on a default `Materialize` folder 56.5's whole TTL sweep is dead in production: `release_expired` (`:6557`) declines before it reads a clock. `dehydrate_entry`'s own doc already names this story: *"The gate lifts when the virtualization policy reaches the arrival sweep and the two verbs stop disagreeing about what a folder holds"* (`:7424-7426`).

**Approach:** Compile the `VirtualPolicy` **once** per call at the three decision points it was written for and let it answer per path, at the **pointer's declared size** — the only place the true size is known before content exists. `Virtualization::Virtual` on arrival means: leave the committed pointer where it is, publish nothing out of the store, and plan no transfer. On release it means: the folder's profile-wide mode stops being the whole answer, so a path the policy authorizes is *eligible* under `Materialize` too — after which every one of 56.4's per-path refusals still runs, unchanged, because AD-123 is that the policy authorizes hydration decisions and only per-object proof authorizes deletion.

## Boundaries & Constraints

**Always:**
- **Compiled once per call, never per path.** `VirtualPolicy`'s own doc forbids building a `GlobSet` in a walk (`virtual_policy.rs:126-129`). `materialize_pending` compiles before its loop; `release_expired` compiles once per pass, before the mode gate; `dehydrate_entry` compiles once per call; `Engine::release_schedules` compiles once per listing.
- **Resolved at the pointer's declared size, never the worktree stat.** `smudge.pointer.size` on arrival; the **committed** pointer's `size` (`indexed_pointer_blob`) on release. A virtual path's worktree file is ~130 bytes, so a `virtualOverBytes` floor compared against the stat would answer `Materialize` for every path it exists to keep away. This is the story's sharpest defect and it carries its own mutation proof.
- **`Virtual` on arrival is three refusals, not one.** Do not `materialize` even when `store.contains` already answers true; do not enqueue a `WorkKind::LfsDownload`; do not write a `materialized` ledger row. One `continue` ahead of both existing branches, so the two can never drift.
- **`LfsMode` keeps its meaning.** `PointerOnly` stays the whole-profile lever and the policy is **not consulted** in it — everything arrives as a pointer there exactly as today, and everything is releasable there exactly as today. `Disabled` still returns early on arrival and still refuses a release with `ContentRefusal::LfsDisabled`. The policy is the per-path lever beside them, the way `subpaths[]` already is.
- **A malformed policy refuses; it is never read as permissive (FR-329).** `VirtualPolicy::compile` already raises `SyncError::Config` naming the source and quoting the line as typed. **Decision, taken deliberately here: a pull with an unparseable policy materializes nothing and surfaces that error.** `sync_once` (`:6316`) propagates it, so an explicit "Sync now" reports the quoted pattern; the supervisor's own call (`:8776`) already logs it as one `warn!` and the sync continues. Nothing is fetched, nothing is published, nothing is deleted. The permissive reading is the one answer unavailable: it would materialize the gigabytes the policy exists to keep away, on a metered link, with no way to undo the bandwidth — and it is the direction `verify` already takes with the same call.
- **The release gate is two tiers, because one tier costs the common case.** `release_mode_gate(profile, policy)` stays a **folder** question in its existing position (ahead of the due gate, so an ordinary folder arms no window and pays no repo open): `PointerOnly` → `Ok`, `Disabled` → `LfsDisabled`, `Materialize` → `Ok` iff `policy.tier() != VirtualPolicyTier::Unset`. The per-path answer is `release_path_gate(profile, policy, rela, size)` inside `release_resolved`, immediately after the sparse-cone check — the first point at which the committed pointer, and therefore the honest size, is in hand.
- **The policy makes a path eligible and authorizes nothing else (AD-123, NFR-40).** `release_path_gate` sits *before* the five refusals and replaces none of them. Every guard in `release_resolved`'s stated order — `Missing`, `Modified`, `AlreadyPointer`, `Pinned` (twice), content identity, `UnprovenOnRemote`, `Open`/`OpenUnknown` — runs unchanged, in the same order, for a policy-authorized path.
- **The surface must not contradict the sweep.** `release_schedule` says `ModeKeeps` — *"This folder is set to keep large-file content on this computer"* — for every `Materialize` row. Once such a folder releases, that sentence is false for the rows that will be released, so `release_schedule` gains the policy's answer and `Engine::release_schedules` compiles the policy once per call. The enum, its words, `keeper-core`'s `FilesReleaseVm` and every generated binding are **unchanged**.
- **Real repository, real `git`, real bytes.** The arrival claims are asserted through `Engine::sync_once` against a real bare remote, a real index and the real `git` binary, in the manner of `tests/release_sweep.rs`. `git status --porcelain` must read **empty** for a virtual path (FR-331): a test that only reads the file back would pass over an index whose stat says the path is modified forever.
- **Every new condition is proven to bite.** For each of the three holes: the test is written first, run against unmodified code, and its failure text recorded; then the implementation; then the condition is mutated away and the test must fail again.

**Block If:**
- Making the release gate per-path would force `release_resolved`'s guard order to change for a folder that has **no** policy — i.e. if an existing 56.4 refusal changed identity. (It cannot: with `tier() == Unset` the folder gate refuses exactly as today, so no `Materialize` folder without a policy reaches `release_resolved` at all.)
- The pointer's declared size is not available at a decision point without extra I/O. (It is: `pending_smudges` carries `smudge.pointer.size`, and `release_resolved` already reads `indexed_pointer_blob` before any guard.)

**Never:**
- **No new UI, no new IPC command, no new `SyncProfile` field, no new binding.** `virtualPatterns`, `virtualOverBytes` and `releaseTtlMs` already exist and are already in `PRESERVED`; the form that would edit them is not this story's ask. Nothing in `src/`, nothing in `keeper-core`, nothing in the `keeper` shell crate.
- **No on-read hydration** (AD-128). Nothing here makes a `git checkout`, a `grep -r` or a `du` materialize anything.
- **No new `EntrySyncStatus` / `FilesSyncStatusVm` variant**, no change to `browse::classify`, `lfs::listing`, `Engine::verify`, `copy`, the delete plan or `docs/sync.md`.
- **The policy never deletes, prunes, truncates or rewrites a worktree byte** (AD-123). It changes an answer, never a file.
- **No policy consult on a *requested* download, and none in `materialize_landed` at all.** 56.3's explicit verb is a human's authorization and outranks the policy, so `materialize_entry` is untouched. `materialize_landed` is untouched too: a **background** arrival publishes only the path the journal row is labelled with, and the only production planner that labels a row is `materialize_pending`, which no longer labels a path it left virtual. A policy edited between an enqueue and its completion therefore publishes a *past* arrival, which AD-123 answers by making it eligible rather than by un-publishing it — and the sweep this story revives is what then applies 56.4's refusals to it. A compile per background LFS completion to guard an unreachable race is not a trade this epic makes.
- No `unwrap_or(true)`, no `is_ok()` on a compile, no silent fallback to "nothing is virtual" anywhere.
- No sleeping test, no hand-written pointer standing in for an index read, no assertion made only through a pure function.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Arrival, policy-virtual, object already local | `Materialize`, `.keepervirtual` covers the path, `store.contains` true | worktree keeps the committed pointer byte for byte; no `materialized` row; `git status` clean | No error expected |
| Arrival, policy-virtual, object absent | same, store empty | **no** `WorkKind::LfsDownload` queued for that oid; `db::queued_downloads` holds nothing for it | No error expected |
| Arrival, policy says materialize | `Materialize`, path not matched | today's behaviour exactly: publish from the store, or queue the download | No error expected |
| Arrival under the size floor | `virtualOverBytes` > the **pointer's** size | materializes — the floor is a floor | No error expected |
| Arrival above the size floor, tiny worktree file | `virtualOverBytes` between the ~130-byte stat and the pointer's size | stays virtual: the pointer's declared size is what is compared | No error expected |
| Arrival, protected by a `!` line | `.keepervirtual` names the path and negates it | materializes — a protection wins unconditionally | No error expected |
| Arrival, policy edited to authorize | the pattern removed, next sync | materializes on that pull; nothing was deleted in between (FR-330) | No error expected |
| Arrival, malformed policy | a line `PatternSet::anchored` refuses | `sync_once` returns `SyncError::Config` quoting the line; nothing fetched, published or deleted | surfaced, never swallowed into "permissive" |
| Arrival, `PointerOnly` | any policy, any path | unchanged: pointer text, no publish, no fetch | No error expected |
| Arrival, `Disabled` | any policy | unchanged: `materialize_pending` returns before anything | No error expected |
| Background arrival at a co-located virtual path | one oid committed at a materialize path and a virtual path | only the labelled path publishes — unreachable for a virtual one, because the planner never labels a path it left virtual | No error expected |
| Requested arrival at a virtual path | 56.3's verb, urgency `Requested` | publishes — the request outranks the policy (AD-128, FR-330) | No error expected |
| Release, `Materialize` + policy authorizes | folder gate passes, path resolves `Virtual` | reaches 56.4's guards and releases on the success edge | No error expected |
| Release, `Materialize` + policy silent | `tier() == Unset` | `ContentRefusal::AlwaysMaterializes` before anything is read — unchanged | refused by name |
| Release, `Materialize` + policy set, path not matched | folder gate passes, path resolves `Materialize` | `ContentRefusal::AlwaysMaterializes`, nothing written | refused by name |
| Release, `Disabled` + policy authorizes | any policy | `ContentRefusal::LfsDisabled` — the policy cannot lift this | refused by name |
| Release, policy authorizes but the path is pinned / open / modified / unproven | any | that refusal, in 56.4's order; the policy only made it eligible | refused by name |
| Release sweep, malformed policy | unparseable `.keepervirtual` | the pass releases nothing; `mark_synced` logs one `warn!` and the sync still succeeds | never fails the sync |
| A row a `Materialize` folder will release | policy authorizes, TTL live | `release_schedule` answers `Due { at_ms }`, not `ModeKeeps` | No error expected |
| A row a `Materialize` folder will not release | policy silent or path unmatched | `ModeKeeps`, with its existing sentence | No error expected |

Every unit queued before this story shipped has the same shape on upgrade. And with no policy edit at all, a *requested* delivery fans out to every indexed path sharing the delivered oid, publishing siblings in the authorized zone that nobody asked for. This spec had argued the case away in a `Never` bullet on the grounds that the sweep would make such a path eligible again; that argument was wrong, because the sweep needs a TTL, a window, remote proof and an `OpenFileState::Closed` the trait default refuses on every real host. The delivery arm now compiles the policy lazily and skips a `Virtual` candidate, exempting only the labelled path of a requested unit; the `Never` bullet and the Design Note were corrected to say so.

This spec's own in-code comment claimed the supervisor "logs it as one `warn!` and carries on", which is true of `scan_and_enqueue` and false of `sync_once`. The fault is now held and raised **after** the drain and push, so the arrival still refuses with the line quoted and `mark_synced` still does not fire, while the person's commits reach the remote.

Added `ContentRefusal::NotVirtual { path }`, which names the path and names `.keepervirtual` as the thing to add a line to; `AlwaysMaterializes` is left to the genuinely folder-wide case. The test asserts the sentence, not only the variant.

An authorized path could take hundreds of syncs while the surface showed its deadline long past. The policy is now a pre-filter on the candidate set, at `size_bytes.unwrap_or(u64::MAX)` so the filter can only ever be wrong in the direction of letting a row through; the authority stays on the committed pointer inside `release_resolved`.
  - `[medium]` `[patch]` **A size-less ledger row read as `ModeKeeps` while the sweep released it.** `release_schedules` resolved at `unwrap_or(0)`, so every row written before story 56.5 fell under a `virtualOverBytes` floor and the Files pane said *this folder is set to keep large-file content* — then the sweep, which asks the committed pointer, released it with no countdown ever shown. Of the two ways to be wrong, only one is safe: promising a release that is refused disappoints, promising the content is kept and then losing it surprises.   - `[medium]` `[patch]` **Every folder paid a `.keepervirtual` read on every successful sync**, and a push-only profile with an unparseable one warned on every pass forever with no other symptom. The sweep's gate moved **behind** `release_is_due`, so the read and the warning are paced by `RELEASE_LOOK_EVERY_MS` instead of by the sync rate; the only cost is that a folder with nothing to sweep arms a window before declining, which is the direction such a folder wants.

## Design Notes

**Why the arrival check is one `continue` and not two.** `materialize_pending` has two branches for one path — publish from the store, or queue the object — and they are the two halves of "the content arrives". A policy consulted separately in each would be one edit away from authorizing the worktree half and not the transfer half, which is the exact shape of the defect this story exists to fix: the owner's first ask is *"it is not downloaded on this clone"*, and a virtual path whose object was fetched into `.git/lfs` anyway satisfies nothing.

```rust
for smudge in &pending {
    // Ahead of BOTH branches below, because a `Virtual` answer refuses the
    // publish and the transfer with one sentence: the content may live in the
    // object store and nowhere else (FR-328, AD-122). Resolved at the
    // POINTER's declared size — the worktree file is ~130 bytes, so a size
    // floor compared against the stat answers `Materialize` for every path it
    // exists to keep away.
    if policy.resolve(&smudge.path, smudge.pointer.size) == Virtualization::Virtual {
        continue;
    }
    if store.contains(&smudge.pointer.oid, smudge.pointer.size) { /* … */ }
    if profile.lfs_mode == LfsMode::PointerOnly { continue; }
    /* enqueue */
}
```

**Why the release gate splits into a folder question and a path question.** The obvious move — make `release_mode_gate` per-path and call it where the pointer is in hand — would delete the sweep's early-out. `release_expired` runs on every successful sync of every folder, and every arrival writes a `materialized` row, so an ordinary `Materialize` folder would go from one `match` and a return to opening its repository and resolving `release_target` for every candidate row, forever, to be told no. So the folder tier stays where it is and answers the cheap question `tier() == Unset`, which is the same shape `Engine::verify` already uses for `excusable` (`engine.rs:8067`); the per-path answer moves to `release_resolved`, where `indexed_pointer_blob` has just been read and the honest size costs nothing.

**Why the per-path gate is before `Missing` and not after.** It is free, it is a question about the path's frame rather than about the file's contents — the same class as the sparse cone it follows — and its refusal is the *useful* one: telling the owner of an unmatched path that his file is `Modified` would send him looking for an edit. The one consequence, stated rather than discovered: under `Materialize`, a stale ledger row for an unmatched path is no longer retracted by the sweep's `AlreadyPointer` arm. That is not a regression, because before this story no `Materialize` folder reached `release_resolved` at all.

**Why the policy cannot lift `Disabled`.** `LfsMode::Disabled` means nothing routes through the clean filter, so real bytes in the worktree would become an ordinary git blob on the next commit. A folder in that mode has no LFS pointers for a policy to have an opinion about, and `release_path_gate` is exhaustive over the mode so a fourth one has to decide rather than inherit.

**Why `materialize_landed` is not changed.** The obvious symmetry — the completion arm should ask the policy too — buys nothing, and reading it is what shows why. `wanted` is the labelled path alone for a background arrival; the index scan that finds an object's other paths is inside `if requested`. The only production planner that labels an `LfsDownload` is `materialize_pending`, and after this story it never labels a path it left virtual, so a background completion cannot reach a virtual path at all. The one state left is a policy edited between an enqueue and its delivery, which publishes a past arrival — and AD-123's answer to a past arrival is to make it *eligible*, not to un-publish it, which is exactly what the sweep now does. A `VirtualPolicy::compile` per background LFS completion to guard that is a file read per object for a self-healing race. The requested arm, separately, must never ask: AD-128 makes hydration an explicit verb and FR-330 makes a policy edit reversible, and both rest on the request door staying open.
