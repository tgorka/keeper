## Intent

**Problem:** Running 0.8.24, the owner reported: *"nie mogle kliknac na element z task list i
zobaczyc szczegolow w nowym tabie."* Clicking a row works and is tested — it selects, and the
pane's own sibling detail region draws the task — but nothing can be opened in a **tab**. The
refusal is recorded at `app-shell.tsx:342-350`: *"a task is not a document … That refusal stands
and Story 59.1 kept it — **but it is scope rather than teeth**"*. The owner has now asked for the
thing that comment declined, which is the same shape as Story 59.4 overturning this epic's own
refusal of multi-select once its consumer existed.

**Approach:** One new `PanelTargetVm` variant keyed by the task's id, the gesture pair every other
surface already answers to (single click previews via `setActiveTarget`, double click opens beside
via `openPanel`), a `PanelStrip` beside `TasksPane`, and a panel body that **reuses `TaskDetail`**
— the pane's own component — in a read-only host. The refusal comment is amended to record its own
retirement and the reason, not deleted.

## Boundaries & Constraints

**Always:**
- A panel target is an **identity resolved on every render**, never cached facts (`panels.rs`
  module doc). A task target carries `taskId` and nothing else; the id is a task's primary key,
  cannot be edited after creation (the epic's own constraint — task runs join on it), and is the
  handle every task verb already takes.
- The panel reuses `TaskDetail`. Two renderings of one task that could word it differently is the
  defect shape this codebase keeps closing.
- The pane stays the **only writer**. `formSaving` is pane-wide precisely because *"a Forget
  confirmed mid-save deletes a row the settling save then re-inserts"* (`tasks-pane.tsx:1818-1829`);
  a second host with its own in-flight flags cannot see the pane's, so a task panel reads and does
  not write.
- Selection is untouched: single selection with `aria-selected`, Cmd/Ctrl toggles, Shift ranges,
  and no IPC issued by a selection gesture.
- A modified click (Cmd/Ctrl/Shift) is a selection gesture only and never touches the panel —
  `files-pane.tsx:2120-2131`'s rule, verbatim.

**Block If:** nothing. Every decision here is derivable from precedent already in the tree.

**Never:** no second selection idiom; no cached task facts inside the target; no write verbs in
the panel; no removal of the pane's detail region; no hand-edit of `src/lib/ipc/gen/**`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Preview | Unmodified click on a task row | Row selected; active panel shows that task; list does not grow | No error expected |
| Open beside | Double click on a task row | Panel appended beside and focused; what the preceding single click displaced is put back | No error expected |
| Modified click | Cmd/Ctrl or Shift click | Selection changes only; no panel gains or changes a target | No error expected |
| Rehydration, task gone | Persisted `{kind:"task",taskId:"nightly"}`, listing has no `nightly` | Panel keeps its place and says `keeper could not find a task called nightly in the task record any more.` | The sentence IS the handling |
| Rehydration, unreadable row | `taskId` present only in `listing.unknown` | Panel says the row was written by a newer keeper, quoting Rust's own reason | The sentence IS the handling |
| Listing refuses | `sync_tasks` rejects | Panel renders the refusal sentence, keeps its place | Rejection message rendered verbatim |
| Empty id | Cookie holds `{kind:"task",taskId:""}` | Entry dropped by `isRestorableTarget`, panel not restored | Silent drop, the cookie reader's existing rule |

## Design Notes

**Why read-only, in one line the next reader can check:** the pane holds `formSaving`, `deleting`
and `running` pane-wide *because* two write surfaces over one task undo each other — `upsert_task`
inserts when the id is absent, so a Forget confirmed while a save is in flight is silently undone.
A second host cannot see the first's flags. Runs stay: `syncTaskHistory` is a read, and a panel
that could not show a task's runs would be a strictly poorer detail than the region it copies.

**Why the shared component is the whole answer to duplication:** the pane's detail region and a
task panel are two *hosts*, one *rendering*. `TaskDetail` is already a pure function of its props;
its write half becomes one nullable `verbs` object rather than nine dummy props, so a read-only
host is a `null` and not a set of no-ops that could drift.

**Why the strip does not replace the pane's detail region:** the region is Story 59.1's level 2 and
59 assertions rest on it. Single click keeps region and panel on the same task; only the explicit
open-beside gesture makes them differ. That invariant is what makes two hosts safe.
