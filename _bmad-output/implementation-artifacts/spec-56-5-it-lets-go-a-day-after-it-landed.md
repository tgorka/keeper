## Intent

**Problem:** Epic 56 can put content on a machine (56.3) and let one path go on request (56.4), and nothing decides *when*. The five columns 56.2 added to `materialized` — `last_used_ms`, `synced_at_ms`, `pinned`, `oid`, `size_bytes` — have **no writer anywhere**; `db::is_pinned` reads a column nothing sets, so 56.4's pin refusal is unreachable in production; and the owner's own ask ("24 h after a positive sync, for content created or modified locally") has no clock, because the ledger records when content *landed* and nothing records when a path was *confirmed upstream*.

**Approach:** Two release clocks selected by provenance, not configuration (AD-131 narrowing AD-126): a path that arrived from the remote keys off `last_used_ms`; a path this clone created or modified keys off `synced_at_ms` and is **not eligible at any age** while that is `NULL`. Write both clocks where the fact is already known — a use keeper can observe, an arrival, the upload unit's completion, `lfs::audit`'s per-object affirmative — add the pin writer and its CLI verbs, add a per-profile/per-folder-TOML `releaseTtlMs` (default 24 h, `0` disables, malformed refuses at startup), and run a **budgeted** release sweep on the `mark_synced` success edge where `prune_lfs_store` already fires. No new timer, no new thread, no `.timer` unit.

## Boundaries & Constraints

**Always:**
- **Provenance is a stored fact, not an inference** (AD-131). `materialized` gains a sixth late column, `local_origin INTEGER`, by the same additive `ensure_materialized_columns` idiom 56.2 used. `NULL`/`0` = *arrived from the remote*; `1` = *this clone created or modified the content now at this path*. `NULL` meaning "remote" is not a guess: the only two writers of this table before this story are `materialize_landed` and `materialize_pending`, both of which publish content **over a pointer**, so every row that can already exist was written by an arrival. The alternative encodings are both wrong and must be named as rejected: `max(last_used_ms, synced_at_ms)` collapses the two clocks into one and lets a *use* make an unconfirmed locally-authored path eligible, which is the exact data-loss shape AD-131 exists to prevent; and `last_used_ms IS NULL` as a provenance proxy fails the moment the owner opens their own file.
- **The eligibility decision is one pure function**, `release_due_at(row: &db::MaterializedRow, ttl_ms: u64) -> Option<i64>`, answering the instant a row becomes releasable or `None` for *never*: the pin returns `None` first, then `local_origin` selects `row.synced_at_ms?` (the `?` **is** FR-341 — `NULL` is never eligible, at any age) or `row.last_used_ms.unwrap_or(row.at_ms)`. `at_ms` is the fallback so that a folder whose rows predate this story is not inert — `at_ms` is NOT NULL and is a real instant content was here.
- **Every clock write is one fact, in `remember_materialized`'s discipline** (`db.rs:479-493`: an `INSERT OR REPLACE` silently blanked `pinned` and the loss was invisible). Five new `db` writers, each naming the columns of exactly one fact, none folded into `remember_materialized`: `note_use` (`last_used_ms`), `note_arrival` (`last_used_ms` + `local_origin = 0`), `note_local_authorship` (upsert: `local_origin = 1` **and** `synced_at_ms = NULL`, because a local modification invalidates any prior confirmation — the new bytes are not upstream), `note_synced` (`synced_at_ms`), `set_pinned` (`pinned`). `note_use`/`note_arrival`/`note_synced` are **UPDATE-only**: a fact about a path this clone holds no materialization row for is a fact this table cannot hold (`at_ms` is `NOT NULL` and means *content landed here*).
- **Ledger keys are git's spelling, from `lfs::stage::index_key`.** The three existing `remember_materialized` call sites pass `smudge.path.to_string_lossy()`, which is `\`-joined on Windows while 56.4's release keys rows through `index_key`. Left alone, an arrival's row and the sweep's release would key different rows on Windows and nothing would ever be released. Corrected at all three sites in the same statement pair.
- **The sweep rides `mark_synced`** (`engine.rs:3290`), inside the reservation the tick already holds, beside `prune_lfs_store`, in the identical shape: `if let Err(err) = … { tracing::warn!(…) }`. `mark_synced` becomes `async fn` — the per-object remote proof is a round trip — and all three call sites (`:3238`, `:3243`, `:5757`) `.await` it; the `status` lock is scoped so no `MutexGuard` crosses an `.await`. `SyncPhase`/`ProfileState` gain nothing.
- **The sweep never calls `reserve`.** All three `mark_synced` call sites already hold the profile's reservation, so `dehydrate_entry`'s door guards (`reserve`, `volume_ready`, `enabled`) must not run again. 56.4's release core is therefore extracted, unchanged, into `release_resolved(&self, profile, rela, path)` — everything from the mode gate to the post-rename bookkeeping — with `dehydrate_entry` keeping its lexical guards ahead of the reservation exactly as it has them, and both callers sharing `release_target` (`plain_segments` → empty → the backslash-alias refusal → `browse::resolve` → `index_key`) and `release_mode_gate`.
- **Every 56.4 refusal applies to a sweep-initiated release, unchanged.** The sweep is not a privileged caller: the same content-identity hash, the same per-object remote proof taken at the moment of deletion, the same `open_file_state` fail-closed, the same double pin read, the same `AlreadyPointer` no-op. On a real host today every sweep release therefore refuses `OpenUnknown`, which is 56.4's recorded and deliberate consequence.
- **A refusal is not a failure and does not stop the pass.** Inside the sweep, `SyncError::Refused(_)` is logged `debug!` and the loop continues (refusal is the *expected* answer for most candidates); any other error propagates out of the sweep, is logged `warn!` at `mark_synced` and never fails the sync — `prune_lfs_store`'s contract verbatim (`engine.rs:3288-3289`, `docs/sync.md:367-368`).
- **Budgeted on both dimensions** (AD-126). `RELEASE_BUDGET_OBJECTS` bounds the count for `CLAIM_LIMIT`'s stated reason (a pass must not hold the profile's reservation for minutes); `RELEASE_BUDGET_BYTES` bounds the bytes because the content-identity proof **reads every byte** of every candidate, so a policy edit making 40 000 paths eligible would otherwise turn one sync into an hour of hashing. The count is checked before a candidate is attempted; the byte total is accumulated from the pointer size and stops the pass at the first candidate that would cross the ceiling, so one oversized object still gets one attempt rather than being unreleasable forever.
- **`0` disables entirely, and it disables before the clock is read.** `release_is_due` returns `false` on a zero TTL *without* touching `next_release_ms`, so a disabled folder never arms a window that would fire after the operator re-enables it. This is a deliberate divergence from `poll_interval_ms`, whose zero is floored (`profile/mod.rs:1014`) and whose own test pins "a zero is floored, never refused" — the `lfs.pruneoffsetdays` convention is that zero disables the condition, and the divergence needs its own test saying so.
- **A malformed TTL refuses at startup, both sides.** Non-numeric or negative is refused by serde in `keeper-syncd::config::parse_profile` with its `[[profile]] #N (name):` prefix, already; a non-zero value below `MIN_RELEASE_TTL_MS` and any value above `RELEASE_TTL_CEILING_MS` are refused by `SyncProfile::validate`, beside the `settle_ms` ceiling (`profile/mod.rs:1100`). The ceiling is load-bearing, not decorative: `release_ttl_ms as i64` for a `u64` above `i64::MAX` wraps negative and makes every row instantly eligible. `validate()` and not a clamp, because this field never existed before this release, so every out-of-range value is one a person typed (`profile/mod.rs:299-307`, `:1543-1547`).
- **`releaseTtlMs` is a folder-tier `Allowed` field** (FR-344, AD-132), beside `virtualOverBytes` under "Repository policy": how long this repository's content may stay is a fact about the repository, and the app and the daemon share no profile store.
- **The shell crate is touched, minimally and by name.** `releaseTtlMs` joins `PRESERVED` (`sync_ipc.rs:3586`, `[&str; 8]` → `[&str; 9]`) — no form control exists for it in this story — and `a_save_cannot_move_a_field_no_request_can_express`'s `prior` fixture (`:3673`) sets it to a value a fresh profile never has, or the preservation assertion passes however `parse_req` behaves. The macOS gate failed twice on exactly this. Beyond that the shell gains only one-line `engine.note_use(&id, &subpath)` calls: every rule stays in `keeper-sync`, because a rule written in a crate that cannot be compiled here is a rule nobody can exercise.
- **`last_used_ms` is keeper's own timestamp, never `atime`** (AD-126; Linux has defaulted to `relatime` since 2.6.30). Written at every materialize and at every use keeper can observe: `sync_open_entry`, `sync_read_document`, `sync_read_text`, `sync_export_entry` and the `keeper-file://` media protocol. The media protocol stamps only a request with no `Range` or a range starting at byte 0 — a seek is a continuation of one use, not a new one, and a scrub would otherwise write dozens of rows a second.
- **The pin verb refuses a path this folder does not track** (`NotTracked`), so a pin is never recorded against a path nothing will ever consult, and pinning does **not** require the content to be present — a pin is a standing instruction, and 56.4's refusal is what enforces it.

**Block If:**
- A second clock, a thread, a `tokio::time::interval` or a systemd `.timer` is judged necessary. AD-62 forbids it absolutely ("two schedulers over one git repository is how you get concurrent index locks"), the scheduler is Epic 57's, and this epic's only obligation to Epic 57 is that automatic release be one of three modes rather than the only one.

**Never:**
- **No task record and no scheduler.** No `tasks`/`task_runs` table, no schedule string, no last-run time, no lease, no Tasks view, no `tasks` CLI verb, no timer unit. FR-346…FR-352 and NFR-42/NFR-43 are Epic 57's.
- **`synced_at_ms` is never written at `mark_synced`** (AD-131): that edge is per *profile* and says nothing about one path. It is written only where the per-path proof already exists.
- **A stored `synced_at_ms` never authorizes a deletion.** It authorizes *eligibility*. `remote_serves`'s own doc already says so (`engine.rs:5977`), and 56.4's proof is taken fresh at the moment of deletion, unchanged. NFR-40 is unmoved.
- **No UI.** No `FilesSyncStatusVm` variant, no `releases_after_ms` on the wire, no ts-rs type, no generated binding, no row action, no countdown — 56.7 owns the states and 56.9 owns the deadline and the button. `git status --porcelain -- src/lib/ipc/gen` must stay empty.
- **No new Tauri command.** The pin verb's door is the CLI, consistent with 56.4's; `src/test/command-registration.test.ts` is untouched.
- **No change to `prune_lfs_store`, `lfs::prune`, `lfs::audit::serves`, `lfs::stage::dehydrate`, `platform.rs` or the `ContentRefusal` vocabulary.** The sweep reuses 56.4 as it stands.
- **No `RemoteAudit` shape change**, and no memo from the filesystem short-circuit or the `LfsMode::Disabled` early return — neither asked the server anything.
- No new crate, no new dependency, no `meta` migration marker.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Remote-origin clock | arrived path, `last_used_ms` older than the TTL, clock advanced | released on the next successful sync; worktree holds the committed blob; ledger row gone | No error expected |
| Remote-origin, not yet due | `last_used_ms` one ms inside the TTL | not a candidate; nothing read, nothing written | No error expected |
| Remote-origin, pre-story row | `last_used_ms` `NULL`, `at_ms` older than the TTL | eligible off `at_ms` | No error expected |
| **Locally authored, unconfirmed** | `local_origin = 1`, `synced_at_ms` `NULL`, clock advanced 100 × TTL | **absent from the candidate set** — not refused later; content untouched | No error expected |
| Locally authored, confirmed | `synced_at_ms` set, clock advanced past it | released a TTL after that instant | No error expected |
| Locally authored, confirmed, then re-modified | `note_local_authorship` runs again | `synced_at_ms` back to `NULL`; not eligible at any age | No error expected |
| A use does not rescue an unconfirmed local path | `local_origin = 1`, `synced_at_ms` `NULL`, `last_used_ms` recent | still absent from the candidate set | No error expected |
| Pinned | `pinned = 1`, any age, either clock | never a candidate; ledger row intact; content intact | No error expected |
| TTL `0` | `release_ttl_ms = 0`, eligible rows present, clock advanced | sweep never runs; `next_release_ms` has no entry for the profile | No error expected |
| Malformed TTL, numeric | `releaseTtlMs = 500` | `SyncProfile::validate` refuses, naming the floor and that `0` is how to disable | `SyncError::Config` at startup |
| Malformed TTL, out of range | `releaseTtlMs = u64::MAX` | refused, naming the ceiling | `SyncError::Config` at startup |
| Malformed TTL, not a number | `release_ttl_ms = "soon"` in `config.toml` | daemon refuses at startup with the `[[profile]] #N (name):` prefix | `SyncError::Config`, exit non-zero |
| Folder TOML tier | `[folder] release_ttl_ms = 3600000` | in force over the profile record; a save from the app does not erase it | No error expected |
| Budget, objects | `RELEASE_BUDGET_OBJECTS + 1` eligible candidates | exactly the budget released this pass; the remainder on the next one | No error expected |
| Budget, bytes | candidates summing past `RELEASE_BUDGET_BYTES` | the pass stops at the crossing candidate | No error expected |
| A sweep failure | one candidate's content unreadable (mode 000) | error logged; `sync_once` returns `Ok`; `last_sync_ms` still moved | swallowed at `mark_synced` |
| A sweep refusal | candidate refuses `OpenUnknown` / `UnprovenOnRemote` / `Modified` | logged `debug!`, pass continues, next candidate attempted | not an error |
| Not on a timer | eligible candidate, clock advanced far past the TTL, no sync | nothing released until a successful sync happens | No error expected |
| A folder that never syncs | paused profile, eligible rows | never released — the correct direction | No error expected |
| `LfsMode::Materialize` | eligible rows, default mode | sweep releases nothing (56.4's mode gate), no per-candidate work | No error expected |
| Upload confirmation | a locally authored object's upload unit completes | `synced_at_ms` set for the path the unit was labelled with | No error expected |
| Shared object, two paths | one upload unit covers both | the labelled path is confirmed; the other stays `NULL` and unreleasable | No error expected |
| Audit memo | `verify --remote` over a live server | every object `audit::serves` affirms stamps `synced_at_ms` for each of its paths | best-effort, logged |
| Audit, filesystem remote | no `.lfsconfig`, path remote | **nothing memoized** — the short-circuit asked nothing | No error expected |
| `note_use` on an unknown path | a path with no ledger row | no row inserted, no error | best-effort, logged |
| CLI pin | `keeper-syncd pin media 40-media/clip.mp4 [--json]` | `pinned = 1`; JSON keys exactly `profileId, profile, path, pinned` | exit 0 |
| CLI unpin | `keeper-syncd unpin media 40-media/clip.mp4` | `pinned = 0`; the path becomes a candidate again | exit 0 |
| CLI pin, untracked | a plain tracked file, or untracked | refusal `NotTracked`; no `.git` created; nothing written | `SyncError::Refused`, exit 1 |
| CLI pin, escaping subpath | `../etc/passwd`, ``, a symlinked parent | refusal `Escapes` | exit 1 |
| CLI parse | `pin` with one argument | `MissingRequiredArgument` | clap, exit 2 |

**Acceptance Criteria:**

- Given a path that arrived from the remote and was never modified here, when its `last_used_ms` is older than the TTL and a sync succeeds, then it is released; and given a path this clone created, when it has never been confirmed upstream, then it is **absent from the sweep's candidate set at any age** — asserted on the candidate set itself, not on the absence of a release — and given the same path once `synced_at_ms` is set, then it is released a TTL after that instant.
- Given the `synced_at_ms IS NULL` eligibility guard, the pin check, the per-pass budget and the never-fails-the-sync swallow, when each is removed or inverted in turn, then that guard's own test **FAILS**, and the restore is verified by reading `git diff` rather than from memory.
- Given a pinned path, when any clock says it is due at any age, then it is never released and its ledger row is intact; and given `releaseTtlMs = 0`, when a sync succeeds with eligible rows present, then nothing is released and no due window is armed.
- Given a `releaseTtlMs` that is malformed — non-numeric, below the floor, or above the ceiling — when the profile is loaded, then it is refused at startup with the value and the reason named, and `0` is accepted as the documented way to disable.
- Given more eligible candidates than the per-pass budget allows, when the sweep runs, then exactly the budget is released and the remainder is released by a later pass; and given one candidate whose release raises a real error, then the error is logged and the sync still reports success.
- Given the sweep, when the clock is advanced far past the TTL with no sync happening, then nothing is released; and no `tokio::time::interval`, no thread, no timer unit and no second scheduler is added — the invocation point is `mark_synced`, and a test asserts it behaviourally.
- Given a real `git status` after a sweep-initiated release, then the released path reads **clean**; and given the shell crate cannot be compiled here, then `releaseTtlMs` is named in `PRESERVED` and carries a distinctive value in the `prior` fixture, so the macOS gate has one classification to confirm and no surprise.

## Design Notes

**Why provenance is a column and not a derivation.** AD-131 says the selector "is a fact the ledger already has to know", and the honest reading is that the ledger has to *record* it, because nothing else can. Every candidate derivation fails on a case that loses data or makes the feature inert. `max(last_used_ms, synced_at_ms)` is one clock wearing two names: the owner opens their own unconfirmed file, `last_used_ms` moves, the path becomes eligible, and the whole barrier is 56.4's remote proof again — the exact single-guard reliance AD-131 exists to remove. `last_used_ms IS NULL` as a proxy fails for the same reason and in the same instant. Defaulting the unknown to *local* would be safe and would also make the sweep release nothing on any existing folder, because every row that can already exist has a `NULL` in the new column. That last fact is what settles it: **the only two writers of this table today are arrival paths**, so `NULL` = remote is not a default, it is the truth of the existing data, and it is stated in the column's own doc so the next reader does not have to re-derive it.

**Why the eligibility predicate is a free function.** `release_due_at(&MaterializedRow, u64) -> Option<i64>` has no `self`, no I/O and no clock; the sweep reads rows, asks it, and compares to `now`. That makes both safety guards — the pin and the `synced_at_ms?` — one line each, unit-testable over hand-built rows, and mutation-provable in isolation. It also means the sweep's *candidate set* is a value a test can assert on, which is what AC 2 asks for: an unconfirmed locally-authored path must not be *considered*, and "was not released" would also be true if it had been considered and refused.

```rust
pub(crate) fn release_due_at(row: &db::MaterializedRow, ttl_ms: u64) -> Option<i64> {
    if row.pinned {
        return None;                      // the hard floor, before any clock
    }
    let since = if row.local_origin {
        row.synced_at_ms?                 // never confirmed ⇒ never eligible, at any age
    } else {
        row.last_used_ms.unwrap_or(row.at_ms)
    };
    Some(since.saturating_add(ttl_ms as i64))
}
```

**Why `mark_synced` becomes `async` instead of the sweep being called beside it.** Calling `release_expired` at each of the three sites after `mark_synced` would work and would quietly abandon the property `mark_synced`'s own doc is built on: it is "the single point every path agrees means it worked", and the reason `prune_lfs_store` lives there rather than at `sync_once`'s tail is that the ordinary watch-driven flow never reaches that tail. Three call sites is three places to forget one. All three are already `async`, so the change is mechanical; the only care needed is that the `status` `MutexGuard` is scoped before the `.await`.

**Why the sweep reuses 56.4 rather than re-deriving it.** The sweep is the caller AD-125's five refusals were designed for, and the temptation is to let it skip the expensive ones — the whole-file hash and the round trip — because "the sweep already checked the ledger". That is exactly backwards: the ledger's `synced_at_ms` is a *memo*, taken at some earlier instant, and NFR-40 requires per-object proof **at the moment of deletion**. `remote_serves`' own doc already says a stored `synced_at_ms` authorizes nothing. So the extraction is a refactor with no behaviour change: `release_resolved` is `dehydrate_entry`'s body from the `.git` check down, moved and not edited, and the door keeps its guards in the order its doc calls "the contract".

**Why the budget has two dimensions.** Every ceiling in this crate is one-dimensional, and a count alone is the wrong one here: the content-identity proof reads every byte of every candidate, so 32 four-gigabyte files is 128 GB of hashing in a pass that is supposed to be housekeeping. A byte ceiling bounds the actual cost; the count ceiling bounds the reservation hold for `CLAIM_LIMIT`'s reason. The byte check stops the pass at the first candidate that would cross the ceiling rather than skipping it, so an object larger than the whole budget still gets its one attempt per pass instead of becoming permanently unreleasable — the failure mode a naive `if bytes + size > BUDGET { continue }` would create.

**Why `0` is checked before the due map is touched.** `scan_is_due` and `sweep_is_due` both stamp a next-due instant as a side effect of being asked. If a disabled TTL asked the gate, it would arm a window; re-enabling the TTL an hour later would then find the window already open and release on the very next sync, which is the opposite of what the operator expects from a knob they just turned on. Zero returns `false` before `now_ms()` is read, and the test asserts the map stays empty — the assertion that the side effect did not happen, not just that the answer was `false`.

**Why the media protocol stamps only the head of a range.** A video scrub issues a Range request per seek. Each one is a genuine read, and treating each as a distinct "use" would write dozens of rows a second through the engine's single db mutex, contending with the sync loop for no benefit — a TTL measured in days cannot tell them apart. A request with no `Range`, or one starting at byte 0, is the start of a playback, and that is the event worth recording. It is also the only piece of judgement this story puts in the shell, and it is three lines with the reason on them.

**Why the pin verb does not require the content to be present.** A pin is a standing instruction about a path, and 56.4's refusal is what enforces it at the moment it matters. Requiring the content would mean a user cannot pre-pin a path they are about to materialize, and would put a whole guard chain behind a single `UPDATE`. It does require the path to be a *tracked LFS path*, so a pin is never recorded against something no sweep will ever look at — and that check is one index read.

**What is deliberately left as recorded deferred work.** 56.3 recorded that `materialize_entry`'s already-held arm writes no ledger row, so a path materialized by `git lfs pull` or a pre-ledger keeper is invisible to these clocks; `note_use`'s UPDATE-only shape inherits that, in the conservative direction (no row, no candidate). 56.4 recorded that a release `DELETE`s the row and discards both clocks. Neither is widened here: both want the released-marker shape that entry names, which is a change to what the table *means* rather than to what this story writes.
