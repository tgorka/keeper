## The one sentence

**A field that says it searches the files and searches a snippet, rows that cannot say what matched, an editor that flashes and forgets, and a bar that spells out every toggle in the space the tags need: the list learns to find the words, mark them where they are, hide the files that are not notes, and speak in icons.**

## Decisions this epic takes

- **AD-261 — A derived, disposable search index lives beside the model, in `<vault>/.keeper/search.db`.** **Binds:** FR-568, FR-569, NFR-63, NFR-68, NFR-70; Stories 76.1, 76.6; D-21. **Prevents:** a second model of the vault that can disagree with the first; a search that lies after a `VACUUM` (DW-48); a cache that survives a schema bump or a vault swap; anything in it reaching a commit; a rebuild that leaves a stale index behind. **Rule:** One SQLite file per vault, opened with the house pattern (`bots/store.rs:76-99`: WAL, busy timeout, idempotent DDL, FKs on, no JSON blobs), written **only** by that vault's reconciler task — the same single mutator that owns the `IndexBuilder` (`notes_vault.rs:695-698`) — and read through a fresh read-only connection per query, the archive's shape (`archive/db.rs:222-225`, `archive/fts.rs:11-13`). The FTS5 table **owns its text** (the `recordings_fts` pattern with an explicit `INTEGER PRIMARY KEY`, `recordings_fts.rs:21-31,273-296`), never external-content, because an external-content table desynchronises silently when a rowid is renumbered. A `meta` row carries `schema` and `vault_id`; a mismatch on open discards the file and cold-scans, exactly as `adopt_cache` treats `index.json` (`notes_vault.rs:1229-1232`). `notes_index_rebuild` (`notes_ipc.rs:1128` → `notes_vault::rebuild`, `:510`) deletes `search.db` together with `index.json` and nothing else in `.keeper/` — the trash and the folder's own settings live there too. `.keeper/` is Tier-0 excluded by keeper-sync (`notes_vault.rs:70-72`, FR-121), so the file is sync-invisible by construction. The index holds **nothing that is not derivable from the files**: chunk text, folded text, offsets, and vectors keyed by chunk and model. The vector half (AD-264) is the one thing that is expensive to re-derive — a provider round trip per chunk — and is the reason this is a file and not a rebuild-at-boot structure. Research §2, §4, §5, §7.

  *The recorded position, and why it is overturned here and nowhere else.* AD-57 (`ARCHITECTURE-NOTES-PHASE5.md:218`) and the module doc at `index.rs:1-10` reject "a SQLite table beside `sync.db`" for the **index of the vault** — the thing that answers "which notes exist, with which titles, tags, links and dates" — and `docs/notes.md:255-257` keeps "a full-text search engine" out of scope because "the bounded parallel scan is never stale". Both stay true for the model: the in-memory `IndexSnapshot` remains the only model of the vault, published over its `watch` channel, cached only advisorily in `index.json`. The staleness argument was that "every external write by Obsidian, an agent or a `git checkout` happens behind its back" and would rot a second store. It is answered three ways, none of them new: (1) the search index is fed by the **same reconciler deltas** — `Work::Touched` and `Work::Rescan` (`notes_vault.rs:176-182`) — through the same `(size, mtime_ns, ino)` revalidation that decides whether a path is re-read (`index.rs:74-82`), so it cannot be more stale than the list is; (2) it is **disposable** — a rebuild deletes it, a schema or vault mismatch deletes it, and nothing the user did is lost when it goes, because it holds no user state; (3) **a mismatch is a rescan, never an error** — AD-57's own sentence, applied to one more file. What the overturn buys is what the scan cannot give: a rank, a match position and a vector, none of which a bounded scan of ten thousand files at every keystroke can compute in the 100 ms the owner's eye allows (research §10). What it costs is one more file to keep consistent, and the reconciler already pays that bill for `index.json`.

- **AD-262 — Notes are chunked heading-first, paragraph-buffered, without overlap, with byte offsets kept.** **Binds:** FR-568; Story 76.1. **Prevents:** a chunk that does not know which note or heading it came from; near-duplicate hits from overlapping windows; a paragraph split mid-fence; a hit whose position in the body cannot be recovered. **Rule:** The reference is pi-knowledge's `chunkMarkdown` (research §3.1): split on ATX headings, keep a heading breadcrumb, buffer paragraphs greedily to a target, **no overlap** — its own dogfood found overlap "produced near-duplicate retrieval units". Constants: target ~1 200 characters (≈300 tokens, so that a chunk plus its title prefix fits the 512-token window of the smallest sensible model, research §6, §9), hard maximum 4 000 characters (an oversized paragraph is sliced), minimum 50 characters unless it is the note's only chunk. One refinement over the reference, which is fence-blind: a fenced code block is one paragraph, never split on the blank lines inside it. Each chunk row stores `note_id`, `ordinal`, `byte_start`, `byte_end` — offsets into the **body**, the editor's buffer, i.e. the second half of `split_note` (`notes_ipc.rs:231-234`), so that a chunk's position and a cursor's position are the same coordinate system (`vm.rs:640-647`) — `heading` (the breadcrumb `A › B`), `text` (raw, for snippets), `text_hash` (so an edit to one paragraph re-embeds one chunk, not the note, research §3.6), and the folded text in the FTS table (AD-263). Chunk ordinal 0 is the note's **head chunk**: title, path, tags and non-reserved frontmatter values, with an empty body range — so the one ranking function covers everything `matches_text` covers today and `matches_text` retires from the search path. The embedding text is `<title> › <breadcrumb>\n\n<text>` (pi-knowledge's contextual prefix, research §3.1 — "the single highest-leverage idea in the package for a notes app where a chunk without its title is meaningless"); the stored text is raw. Bodies over `MAX_INDEXED_BODY` (`notes_vault.rs:95`) are chunked head-only, as the index already treats them.

- **AD-263 — Lexical is FTS5 `bm25` over keeper-folded text; marks come from keeper's own matcher, never from `highlight()`.** **Binds:** FR-563, FR-564, NFR-64; Stories 76.1, 76.2. **Prevents:** `ł` and `l` being different letters to the list and the same letter to ⌘⇧F; a highlight that disagrees with the matcher the sessions surface shares (AD-20); a query word parsed as an FTS operator; a second folding rule; an English stemmer applied to Polish. **Rule:** The FTS5 table has two columns, `title` (folded title and breadcrumb) and `text` (folded chunk text), tokenised with `unicode61` — the folded text is ASCII-ish, so the tokenizer has nothing to fold — because `unicode61`'s own diacritic table folds ą ć ę ń ó ś ź ż **but not ł** (U+0142 lies outside its `ĺ ļ ľ` range, research §4), and keeper's `search::fold_str` does (`search.rs:262-300`, AD-55). The query is folded by the same function, so index and query can never disagree on a letter. Ranking is `ORDER BY bm25(chunks_fts, 4.0, 1.0)` — FTS5's scores are negative, better is lower (research §4); a title hit outweighs a single body mention but not a paragraph that says the word four times; the weight is re-tuned in 76.1's spec against the owner's vault and recorded there. The query is built the way the archive builds its `MATCH` argument (`archive/fts.rs:191-197`): every whitespace-separated word becomes a **quoted phrase** with embedded `"` doubled, the **last word is a prefix** (`"foo"*`, the `*` outside the quotes as §3.3 requires) for type-ahead, phrases joined by implicit AND, and an OR fallback when AND matches nothing (pi-knowledge's builder, research §3.2). Marks are **not** FTS5's `highlight()` or `snippet()`: those re-tokenise the *folded* column and would emit offsets into text the user never sees (research §4, §3.2). Match runs for a row's snippet and for the editor body are computed in Rust by `search::find` (`search.rs:39-69`) per query word over the **raw** text — the same substring-over-folded-bytes rule ⌘⇧F and a space's `text:` use (`query.rs:1265-1267`: "so a space and the search surface can never disagree") — with overlapping runs merged. A word admitted by prefix (`not` → `notatka`) is therefore also marked where it occurs mid-word; that is the matcher's rule everywhere and is accepted rather than special-cased. No stemming: Snowball has a Polish algorithm and `frostem` exposes it, but its quality is unmeasured (research §4, §12) — DW-260.

- **AD-264 — Vectors come from the provider you already configured, never from a model keeper ships or downloads (D-4).** **Binds:** FR-566, FR-567, FR-576, FR-577, NFR-65, NFR-66, NFR-67, NFR-68; Story 76.6. **Prevents:** a new egress destination (huggingface.co, cdn.pyke.io); bundled weights and their dataset terms (D-5's refusal, `docs/decisions.md:150-156`); an ONNX runtime with no `x86_64-apple-darwin` prebuilt (research §5); a Gemma-licensed model behind a permissive-only `deny.toml` (`deny.toml:3-19`, research §6); a search that silently stops being hybrid; a backfill that starves the lexical index or the UI. **Rule:** A new key `notes.embedding_model` (`Scope::UserGlobal`, `Shape::Json` holding `{"provider": <bot_providers.id>, "model": <tag>}`, default `""` meaning *none*, `Settable::Never` because it names a provider row by id that only Settings can pick — recorded so the reason is not mistaken for an omission, `keys.rs:31-36`) names one model from the user's own provider rows. The Settings picker offers only models whose discovery said `embedding`: `capability_flags` (`discover.rs:387-400`) gains a fourth tri-state, `BotModelVm` (`vm.rs:5420-5461`) carries `embedding: Option<bool>`, and the AD-151 rule applies verbatim — `Some(true)` offers, `None` offers **with a warning** (the `image_offer` shape, `deliverable.rs:186-190`), `Some(false)` hides. The route is `POST /v1/embeddings` on the OpenAI-compatible wire keeper already speaks (`Endpoint::url`, `bots/mod.rs:297-301`; client policy `http.rs:24-160`, unchanged): Ollama documents it (research §6); Hermes does not, so `Quirks` (`quirks.rs:61-78,198-216`) gains `embeddings: Support` — Ollama `Yes`, Hermes `Unknown` — and a provider that answers anything but a well-formed embedding list is **refused with a sentence** shown in Settings and in the bar's status line, never skipped silently. Vectors are L2-normalised in Rust (so cosine is a dot product, research §3.3), stored as f32 BLOBs in `search.db` keyed by `(chunk_id, model)`; **a model change deletes every vector**. The backfill hangs off the reconciler and the existing ~1 Hz supervisor tick (`notes_vault.rs:29-31`; G4 §6 — "no second clock, no notes scheduler"), embeds in batches of at most 32 inputs (research §6: 16–64 is the community's memory-bound range), yields to `Touched` work between batches so the lexical index is never behind a vector, and publishes `NoteEmbeddingProgressVm { vault_id, embedded, total, model, state: idle | running | refused, refusal }` over a `watch` channel like `NoteIndexProgressVm` (`notes_vault.rs:698`, `vm.rs:1090`). At query time the query vector is fetched once per `(model, folded query)` and memoised for the session; if the provider takes longer than 1 s (Nielsen's flow-of-thought bound, research §10) the answer for that query is lexical and the status line says so. **With no model set, search is lexical only and the bar says so in one sentence** — vector search is an addition, not a gate.

- **AD-265 — Hybrid fusion is a normalised convex combination with a lexical anchor and a confidence floor.** **Binds:** FR-566; Story 76.6. **Prevents:** an ANN dependency for a vault that will never need one; a "confidently wrong" semantic-only hit at the top of a list of ten; a list padded with weak matches to look full; term marks painted on a hit that has none. **Rule:** The vector leg is brute-force cosine in Rust over every chunk vector of the model in use — 10 000 notes × ~5 chunks × 768 dimensions is single-digit milliseconds with a scalar loop (research §7: sqlite-vec measures 100 k × 384-d under 75 ms *from disk*; usearch 10 k × 1024-d exact in 2.54 ms) — no sqlite-vec, no HNSW (DW-262 names the threshold). Two candidate pools: lexical top-200 chunks by `bm25` (`MAX_SEARCH_HITS`'s number, `notes_ipc.rs:83-84`) and vector top-50 by cosine (pi-knowledge's `candidateMin`, research §3.4). Each pool is min-max normalised; `score = 0.45·lex + 0.55·vec`, plus 0.15 when a chunk is in both — pi-knowledge's weights (research §3.4), and Bruch, Gai & Ingber 2023's finding that a convex combination of min-max-normalised scores beats RRF on every dataset they tried while RRF is sensitive to its `k` (research §8). The **lexical anchor**: every chunk in the lexical pool is admitted. The **confidence floor**: a chunk in the vector pool only is admitted if its fused score is at least 0.18 (pi-knowledge's balanced default) and is labelled **matched by meaning** — a semantic hit carries a label, not term marks, which is what every surveyed product does (Smart Connections' score, Apple's "Top Hits", Notion's provenance labels, research §10). 0.18 is pool-relative, not a probability (research §3.4's own caveat); 76.6 measures it against the owner's vault with the model actually chosen and records the number in its spec — the invariant is that the gate exists and that nothing below it is shown, not the constant. Best chunk per note; the note's score is that chunk's; results below the floor are **dropped, not padded**. With no vectors (no model, or a chunk the backfill has not reached) the vector pool is empty and the ranking is the lexical one unchanged.

- **AD-266 — Offsets that cross IPC for highlighting are UTF-16 code units; the list in search mode is ordered by score.** **Binds:** FR-563, FR-564, FR-565; Stories 76.2, 76.3. **Prevents:** a mark that lands one character off after every `ł`; a Rust byte range sliced by a JavaScript string; a highlight that fades on its own while the query stands; a find-panel search state hijacked to paint marks; a pinned note that outranks the note that actually says the word. **Rule:** Rust computes byte ranges (`search::Hit.span`) and converts them **once**, at the boundary, to UTF-16 code units — the coordinate system of `String.prototype.slice` and of CodeMirror positions. `NoteRowVm` (`vm.rs:110`) gains `hit: Option<NoteHitVm { snippet, marks: Vec<[u32; 2]>, why: "words" | "meaning" | "both", score }>` where `marks` index into `hit.snippet` — a match-anchored window of `SNIPPET_CHARS` scalars (`notes_vault.rs:98`) centred on the first run in the best chunk, markdown-stripped by `snippet::prose` **before** the runs are computed over the final string, so an offset never points into text that was stripped; `row.snippet` keeps meaning what it means today for an empty query. A new command `notes_note_marks(vault_id, note_id, query) -> NoteMarksVm { rev, ranges: Vec<[u32; 2]> }`, beside `notes_open` (`notes_ipc.rs:3076`), returns runs into the **body** the editor holds (the second half of `split_note`, `:231-234`), stamped with the `rev` of the `NoteBodyBatch::Reset` it was computed against (`vm.rs:601`) so the editor discards ranges for a body it no longer shows. The editor paints them through a **persistent `searchMarks` StateField** — a sibling of `flashExternal` (`live-preview.ts:1220-1225`), not a reuse of it (it fades) and not the find panel's `setSearchQuery` (`find-panel.tsx:88-89`; CodeMirror would re-match with its own folding and disagree with Rust on `ł`) — styled by the existing `--search-highlight` pair (`index.css:179-180,287-288`), never by `--mark`, which is `==highlight==`'s (`index.css:186-187`). Marks clear when the query is cleared, when the note changes, or on Esc in the editor. In search mode (a non-empty query) the list is ordered by score, ties by `updated_ms` — a search is a question, not a shelf, and **pinned does not jump the queue**; with an empty query nothing about today's ordering (`notes_ipc.rs:420-423`) changes. ## What stays out

- **⌘⇧F search-everywhere and the sessions matcher.** `notes_search` (`notes_ipc.rs:3390`) keeps reading the files; `sessions/search.rs` keeps importing `notes::search::find` (`:24`, AD-20). The matcher is shared and untouched; only new callers are added.
- **Space `text:` semantics.** A space is a filter, not a ranking: `query::eval_text` (`query.rs:1262-1270`) keeps its title-then-body read and its "can never disagree" guarantee. A space with a `text:` term still shows its notes in the space's sort, not by score.
- **Any new dependency in `keeper-core`.** No `tauri`, no `gix`, no ML crate, no sqlite-vec, no tantivy (research §5: a second engine outside SQLite transactions, ~40 crates, its own consistency problem — for a substring-and-rank problem FTS5 already solves in the file we have). The only new persistence is `search.db`.

## The failure shape this epic must not repeat

Two, and they are the two this surface family has already produced.

**The risk lives in the impure shell, which cannot compile on this host.** The pure halves — the chunker, the index, the query builder, the fuser, the fold — are keeper-core and are proved on Linux by real-SQLite tests in the archive's shape. The wiring that makes them true for a user is in `notes_vault.rs` (the reconciler that writes `search.db`, the backfill, the rebuild path) and `notes_ipc.rs` (`notes_list`'s new branches, `notes_note_marks`, the setting pairs, the subscribe command), and the shell crate does not build here. Every story that touches them says **"by inspection, awaits CI macOS"** in its acceptance, names the hesperia measurement that turns the NFR's target into a number, and does not close until the macOS job is green and the number is in the spec. Epic 74 shipped two real-browser gates as "NOT RUN" and the owner's first note on that surface was exactly the gap they would have caught; 76.1's cold-build time and 76.5's 240 px measurement are the two gates here that must not ship unrun.

**The normal state read as a fault.** This bar has a caption that states a posture ("Searching the files, not an index") the code never had, exported "kept verbatim" so a test could pin it, and three text buttons whose *names* are the contract (`note-filter-bar.test.tsx:153-189`) while their *rendering* is incidental. When 76.5 turns the buttons into icons and removes the caption, `getByText("Save as space")` (`:109,113`) fires — that is a text query pinning a rendering, and it moves to a role + name query; the role + name toggle tests must pass **without edits**, because the accessible names are the thing AD-268 promises not to change. Any test that pins the caption or a button's visible text is a test of the old rendering and must move in 76.5, not be re-pinned to the new one. Likewise in 76.4: the hide toggle is on by default, so an empty list with `hidden > 0` is a normal state and `emptyFilterReason` must say so — a list that is empty because it is doing what it was asked is not a fault, and a sentence that implies one ("no notes match") would be this failure in a new coat.

```markdown
## D-21 — A search index is derived and disposable; the model is still the files

keeper's notes surface gains a per-vault search index — SQLite with FTS5 and f32 vectors, in
`<vault>/.keeper/search.db` — and the in-memory index of the vault stays what it has been since
epic 35: the only model, published over a `watch` channel, cached only advisorily. This is
recorded here because it overturns a written position: AD-57 and `index.rs:1-10` rejected "a
SQLite table beside `sync.db`" as "a cache-invalidation bug forever", and `docs/notes.md`
listed "a full-text search engine" as deliberately out of scope because "the bounded parallel
scan is never stale". Epic 76's triage of the owner's ask — rank by body, mark the words, find
by meaning — found that none of the three can be computed by a bounded scan of ten thousand
files inside the hundred milliseconds a keystroke allows, and this is the answer.

- **What the index buys, for this owner:** a rank (FTS5 `bm25`), a match position (keeper's
  own matcher over the raw text, so `ł` is `l` everywhere), a vector per chunk from the
  provider the owner already runs, and a hybrid of the two with a floor under the semantic
  half — none of which the scan can give and all of which the list needs to say *why* a note
  is in it. (AD-261…AD-266; FR-563…FR-569; research §2, §3, §7, §8)
- **What it costs, stated so nobody re-discovers it:** one more file the reconciler must keep
  consistent with the files; a chunk table that is re-derived for every changed note; a vector
  per chunk that is a provider round trip to re-derive after a model change; and the standing
  rule that anything it says which the files do not is a bug in the reconciler, never a fact.
  (`notes_vault.rs`; NFR-63, NFR-66, NFR-70)
- **Why the staleness argument does not apply:** the index is fed by the same `Touched` and
  `Rescan` deltas as the model, through the same `(size, mtime_ns, ino)` revalidation, so it
  cannot be more stale than the list; it holds nothing a user did, so discarding it loses
  nothing; and a schema or vault mismatch, or a rebuild, deletes it — a mismatch is a rescan,
  never an error, which is AD-57's own rule applied to one more file. (AD-261)
- **What stays where it was:** ⌘⇧F keeps reading the files; a space's `text:` keeps its
  title-then-body read; the sessions surface keeps the shared matcher; `.keeper/` keeps its
  Tier-0 exclusion so the index never reaches a commit. (AD-20, FR-121; DW-261)
- **The assumptions this rests on, each falsifiable:** a personal vault stays under ~10⁵
  chunks, so brute-force cosine is milliseconds (DW-262 names the threshold); the owner's
  provider answers `/v1/embeddings` on a loopback host, so no egress row is added (D-4,
  NFR-67); the reconciler remains the single writer per vault; the chunker's offsets are into
  the editor's body, so a mark and a cursor share one coordinate system.
- **Revisit triggers — any one reopens the store question, none reopens it otherwise:** a
  vault past 10⁵ chunks with NFR-65 failing; a second writer to `search.db`; a provider kind
  whose embeddings route is not OpenAI-shaped; a measured need for stemming (DW-260) that the
  fold cannot meet; the owner asking for the search index to become the model (it must not,
  and this entry says why).
- **Status / owner:** decided. Owner is the architect; Epic 76 implements it; NFR-63…NFR-70
  are the bars, measured on hesperia before any story closes.
```
