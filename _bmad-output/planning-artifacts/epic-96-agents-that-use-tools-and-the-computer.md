## The one sentence

**An agent can read and write files in its drives, but it cannot run a test, use a tool someone else built, look at a screen or press a key — and keeper refused all four for good reasons.** The fix keeps every reason and adds four doors, each behind epic 93's approval:
- **`run`** — an argv, never a shell string, in an OS sandbox whose only lasting writable place is the session's `workspace/` (the run's own empty `HOME` and `TMPDIR` are created for it and removed after it); with network it sees nothing but that workspace.
- **MCP** — the servers the host's own person names, their results treated as outside content, their own descriptions of their tools trusted only when the person says so.
- **Paseo** — coding as a request to a broker that owns the repository credentials; starting work is always a person's decision.
- **The screen and the KVM** — Peekaboo on hesperia for the Mac, a KVM for another machine, each action at its tier, each decided on the screen it will act on.

## Open questions for the coordinator

Each has the reading this plan builds to, marked as such, so no lane is blocked. None is resolved silently. The coordinator accepted every reading below as ruling R24 (`agents-coordinator-decisions-2026-10-02.md`); the 2026-10-02 reviews then changed Q1's Paseo default (S-29), Q2's grammar (S-14, F15), Q4's annotation rule (S-14), Q7's preview (S-18), Q10's declassified object (S-03) and Q12's first run (S-21). Each change is marked where it lands.

- **Q1. An MCP or KVM call is a sink of audience `*`, which no session label can satisfy.** AD-391 sets the audience of "an MCP call, `run` with network, a KVM action" to `*` and blocks a sink whose audience is not within the label's readers. A session's readers are always a finite set (its opening label is the home drive's readers), so every MCP call — Paseo's `list_agents`, Peekaboo's screenshot, a KVM snapshot — would be blocked, while AD-407/AD-408/AD-409 make those very calls T0 and automatic.
  - **Plan's reading (accepted, R24(1); Paseo's default changed by S-29):** a configured MCP server or KVM has an audience the person declares in the host's configuration, `readers` (Matrix user ids, or `["*"]`, the default). Peekaboo on the person's own Mac and the owner's KVM are configured with the principal's readers; a public server stays `*`. A `role = "paseo"` server also defaults to `["*"]`: the pull request it opens is read by the repository's audience, so its T3 card is a declassification of the prompt (S-29, 96.3 #7). `check_sink` reads that audience: epic 92's plan lands `check_sink` with a fixed `Sink::External` meaning `*` (its 92.1 *Files*), so 96.2 gives that arm the configured readers, `*` remaining the default. `run` with network stays `*` (Q10).
- **Q2. `[[mcp]]` in `agentd.toml` needs four more keys.** The architecture shows `name`, `url`, `credential` (`ARCHITECTURE-AGENTS.md:623-626`). AD-406 also allows the child-process transport, Q1 and Q4 need an audience and a role, and AD-409 pins self-signed certificates.
  - **Plan's reading (accepted, R24(4); amended by S-14 and F15):** `[[mcp]]` gains `command = [argv…]` (exactly one of `url` or `command`; `command` refused on a host that may not spawn), `readers` (Q1), `role` (`"paseo" | "screen" | "kvm:<id>"`, absent for an ordinary server; Q4, 96.4, 96.5), `fingerprint` (`sha256:…`) for a self-signed server (AD-409's pinning), and two keys only a person writes: `trust_annotations` (default `false`) and `[[mcp.tier]]` rows (`tool`, `tier = "T0"…"T5"`) (S-14, Q4). A `role = "kvm:<id>"` entry names a `[[kvm]] id = "<id>"` entry, which owns that KVM's `readers`, `fingerprint` and `credential`; the `[[mcp]]` entry carries none of the three (F15, 96.5). The desktop keeps the same table device-local (UX-DR140), never in the account's synced settings: a command line that syncs would execute on every device.
- **Q3. AD-397's closed tool vocabulary has no name for the classic NanoKVM's WebSocket path.** The NanoKVM-Go path is MCP (`mcp:<server>/<tool>`); the classic path is keeper's own client over `keeper-ported::nanokvm`.
  - **Plan's reading (accepted, R24(3)):** two names join the vocabulary, `kvm_snapshot(kvm)` and `kvm_act(kvm, actions)`. The KVMs an agent may use are the `kvm:<id>` entries of its `[host].needs`, which the grammar already has. **Rejected:** exposing the classic path as an in-process MCP server — it keeps the vocabulary closed but puts an MCP *server* in keeper's code, blurring DW-215's line.
- **Q4. Paseo's broker publishes no tool annotations** (`paseo-mcp.py:859-869`), so AD-406's rule ("unknown or destructive ⇒ T3") makes all four verbs T3, while AD-407 makes `list_agents` and `get_agent_status` T0.
  - **Plan's reading (accepted, R24(2); the annotation half superseded by S-14):** a server configured with `role = "paseo"` is classified by four rows in the tier table — the two reads T0, `create_agent` and `send_agent_prompt` T3 — and any other tool it lists is refused ("the broker has exactly four verbs", AD-407). For every other server the order is: the role's own table (`screen`, 96.4; `kvm:<id>`, 96.5), then a `[[mcp.tier]]` row the person wrote for that tool, then the server's annotations — read only when the person set `trust_annotations = true` (`readOnlyHint: true` without `destructiveHint` or `openWorldHint` gives T0, anything else T3) — and otherwise T3. Annotations are what a server says about itself; the MCP specification calls them untrusted hints, so a lying or compromised server lowers nothing the person did not vouch for. A `command` server's tools are never below T2, whatever a row or an annotation says (S-14).
- **Q5. Landlock restricts TCP only.** Its network rights (ABI 4+) are TCP bind and connect; UDP and raw sockets are not covered `[UNVERIFIED in the research; the kernel's Landlock documentation]`, so "network denied" needs a second mechanism on Linux.
  - **Plan's reading (accepted, R24(5)):** in a run without network, a seccomp filter (`seccompiler`, Apache-2.0, pure Rust, from Firecracker) refuses `socket(2)` for every family but `AF_UNIX`. 96.1 #4(g) proves it with a UDP send. In every run the same filter refuses the calls that reach into another process — `ptrace`, `process_vm_readv`, `process_vm_writev`, `kcmp`, `pidfd_getfd`, `perf_event_open` — and landlock denies `/proc` (S-07, 96.1 #4(i)(j)). **Rejected:** a network namespace — unprivileged user namespaces are restricted on current Ubuntu `[UNVERIFIED]`, and the host must not need privileges.
- **Q6. "Everything else denied" leaves toolchains unreachable.** `cargo`, `rustup`, `node` and friends live under a user's home or `/opt`, which AD-405's sandbox denies.
  - **Plan's reading:** the host's configuration names extra read-and-execute paths (`[sandbox] read_exec = [...]` in `agentd.toml`, the same list device-local on the desktop); the default is the system's (`/usr`, `/bin`, `/sbin`, `/lib*`, `/etc`, `/System`, `/Library/Developer/CommandLineTools` on macOS). No path inside a drive and no path holding the host's secrets is accepted there (refused at parse).
- **Q7. A pixel hash of the screen always drifts.** AD-408/AD-409 put "the screen hash" in an approval's preconditions; the menu-bar clock and a blinking caret change a screenshot's SHA-256 within a minute, so every approval would fail its re-check.
  - **Plan's reading (accepted, R24(6); the preview's place set by S-18):** an action on an element is pinned by the element's accessibility path, role, title and frame (Peekaboo's element ids, §7.2); an action at coordinates, and every KVM action, is pinned by a 64-bit difference hash of the target region with a Hamming bound fixed by fixtures (96.4 #5, 96.5 #6). The record keeps the preview's SHA-256 for audit. The image itself lives under the zone's `.keeper/previews/`, is never committed, and reaches a person only as the card's encrypted Matrix attachment (S-18, 96.4 #4).
- **Q8. MCP tool names cannot travel as `mcp:<server>/<tool>`.** OpenAI-compatible function names allow `a-z A-Z 0-9 _ -` and at most 64 characters `[UNVERIFIED in this program's research; the OpenAI API reference's function-name rule]`.
  - **Plan's reading (accepted, R24(7)):** the wire name is `mcp__<server>__<tool>`; the log, the config and the approval card keep `mcp:<server>/<tool>`. A tool whose wire name would exceed 64 characters or hold another character is not offered and is listed with its reason.
- **Q9. The epic map says no story here touches the shell crate.** AD-406 names "Settings on the desktop" as where the Mac's MCP servers are configured, which needs commands and a Settings section.
  - **Plan's reading (accepted, R24(8); the architecture's epic map is corrected):** 96.2 touches the shell — the Mac's device-local server table, three commands, their registration and the Settings section (96.2 *Files*), gated on the macOS job. Everything else stays in `keeper-core` and `keeper-agent`.
- **Q10. `run` with network meets NFR-121.** A command with network may reach any host its argv names, which nobody configured in advance.
  - **Plan's reading (accepted, R24(15); the declassified object changed by S-03):** a networked `run` is approved per run, at T3, and that approval is the person configuring that one destination; `docs/egress.md` gains a row saying so. A networked run mounts only the session's `workspace/` — no drive, no `.keeper/` — so the only bytes it can send are the argv's and the workspace's. Its approval therefore declassifies the workspace exactly as the card showed it: the record carries the SHA-256 set of `workspace/` (every file's relative path and hash), which is recomputed at consume and re-checked as a precondition (S-03). One approval, not two. A per-host allow-list is deferred (DW-398); a run that needs a drive's file and the network copies the file into its workspace first, in a separate step (DW-451).
- **Q11. Who holds the Screen Recording grant when keeper starts Peekaboo.** macOS attributes a child's TCC requests to the responsible app; if keeper.app launched Peekaboo as a child, keeper would need the grants AD-408 says it must not hold `[UNVERIFIED]`.
  - **Plan's reading:** Peekaboo runs as its own app in the person's GUI session (its Bridge host, §7.2) and keeper connects to it as a `url` server, never as a `command` child `[UNVERIFIED: whether Peekaboo's MCP server speaks streamable HTTP; §7.2]`; 96.4's device run verifies on hesperia that keeper.app appears in neither the Screen Recording nor the Accessibility list. A `command` screen server would also keep S-14's T2 floor, so even its screenshots would ask.
- **Q12. How the coding agent "follows status"** (AD-407). A coding run takes minutes to hours; a turn cannot wait that long.
  - **Plan's reading (accepted; the first run gated by S-21):** after an approved `create_agent`, the coding agent's host writes a follow card with `schedule: every 10m` (92.3) whose run calls `get_agent_status` (T0, raised once to T1 for being unattended — still automatic). An agent user wrote that schedule, so the card shows *scheduled by <agent>* and its first run waits for a person's tick (S-21, 92.3's `scheduled_by:`); the `create_agent` card says so. ## The failure shape this epic must not repeat

**A boundary that is a sentence.** "In-process guardrails do not hold" (research §3.9). A review that finds any of the following is a blocker:
- a `run` that executes before the sandbox is applied, or falls back to running unsandboxed when the probe fails;
- a networked `run` whose sandbox can read a drive or a `.keeper/` directory, or a networked approval that releases anything but the workspace set the card showed;
- a sandboxed child that can read `/proc` or reach into another process (`ptrace`, `process_vm_*`, `kcmp`, `pidfd_getfd`, `perf_event_open`, `process-info*` on macOS), or whose `HOME` lies in the workspace;
- a code path that builds a shell command line from model text;
- an MCP call, `run` with network or KVM action that reaches its server before `check_sink` answered;
- a TLS verifier that accepts what it cannot pin;
- an approval record whose precondition the consume path does not re-read, or an effect that starts before the server acknowledged the `approval.consumed` event;
- a screenshot or KVM frame written under a session's folder or into a commit.

**Power without a person.** A review that finds any of the following is a blocker:
- a KVM input below T4, or with `scopes` containing `session`;
- a `create_agent` approved for more than one call;
- a screen action consumed against a screen nobody re-read;
- an MCP tool lowered below T3 by annotations the person did not trust, or a `command` server's tool below T2;
- an approval summary that carries text the model wrote;
- a T4 screen or KVM action decided from the process that hosts it.
