## The one sentence

**An agent can read and write files in its drives, but it cannot run a test, use a tool someone else built, look at a screen or press a key — and keeper refused all four for good reasons.** The fix keeps every reason and adds four doors, each behind epic 93's approval:
- **`run`** — an argv, never a shell string, in an OS sandbox whose only lasting writable place is the session's `workspace/` (the run's own empty `HOME` and `TMPDIR` are created for it and removed after it); with network it sees nothing but that workspace.
- **MCP** — the servers the host's own person names, their results treated as outside content, their own descriptions of their tools trusted only when the person says so.
- **Paseo** — coding as a request to a broker that owns the repository credentials; starting work is always a person's decision.
- **The screen and the KVM** — Peekaboo on hesperia for the Mac, a KVM for another machine, each action at its tier, each decided on the screen it will act on.

## Open questions for the coordinator

Each has the reading this plan builds to, marked as such, so no lane is blocked. None is resolved silently. The coordinator accepted every reading below as ruling R24 (`agents-coordinator-decisions-2026-10-02.md`); the 2026-10-02 reviews then changed Q1's Paseo default (S-29), Q2's grammar (S-14, F15), Q4's annotation rule (S-14), Q7's preview (S-18), Q10's declassified object (S-03) and Q12's first run (S-21). Each change is marked where it lands.

- **Q1. An MCP or KVM call is a sink of audience `*`, which no session label can satisfy.** AD-391 sets the audience of "an MCP call, `run` with network, a KVM action" to `*` and blocks a sink whose audience is not within the label's readers. A session's readers are always a finite set (its opening label is the home drive's readers), so every MCP call — Paseo's `list_agents`, Peekaboo's screenshot, a KVM snapshot — would be blocked, while AD-407/AD-408/AD-409 make those very calls T0 and automatic.
  - **Plan's reading (accepted, R24(1); Paseo's default changed by S-29):** a configured MCP server or KVM has an audience the person declares in the host's configuration, `readers` (Matrix user ids, or `["*"]`, the default). Peekaboo on the person's own Mac and the owner's KVM are configured with the principal's readers; a public server stays `*`. A `role = "paseo"` server also defaults to `["*"]`: the pull request it opens is read by the repository's audience, so its T3 card is a declassification of the prompt (S-29, 96.3 #7). `check_sink` reads that audience: epic 92's plan lands `check_sink` with a fixed `Sink::External` meaning `*` (its 92.1 *Files*), so 96.2 gives that arm the configured readers, `*` remaining the default. `run` with network stays `*` (Q10).
- **Q2. `[[mcp]]` in `agentd.toml` needs four more keys.** The architecture shows `name`, `url`, `credential` (`ARCHITECTURE-AGENTS.md:623-626`). AD-406 also allows the child-process transport, Q1 and Q4 need an audience and a role, and AD-409 pins self-signed certificates.
  - **Plan's reading (accepted, R24(4); amended by S-14 and F15):** `[[mcp]]` gains `command = [argv…]` (exactly one of `url` or `command`; `command` refused on a host that may not spawn), `readers` (Q1), `role` (`"paseo" | "screen" | "kvm:<id>"`, absent for an ordinary server; Q4, 96.4, 96.5), `fingerprint` (`sha256:…`) for a self-signed server (AD-409's pinning), and two keys only a person writes: `trust_annotations` (default `false`) and `[[mcp.tier]]` rows (`tool`, `tier = "T0"…"T5"`) (S-14, Q4). A `role = "kvm:<id>"` entry names a `[[kvm]] id = "<id>"` entry, which owns that KVM's `readers`, `fingerprint` and `credential`; the `[[mcp]]` entry carries none of the three (F15, 96.5). The desktop keeps the same table device-local (UX-DR140), never in the account's synced settings: a command line that syncs would execute on every device.
- **Q3. AD-397's closed tool vocabulary has no name for the classic NanoKVM's WebSocket path.** The NanoKVM-Go path is MCP (`mcp:<server>/<tool>`); the classic path is keeper's own client over `keeper-ported::nanokvm`.
  - **Plan's reading (accepted, R24(3)):** two names join the vocabulary, `kvm_snapshot(kvm)` and `kvm_act(kvm, actions)`. The KVMs an agent may use are the `kvm:<id>` entries of its `[host].needs`, which the grammar already has. **Rejected:** exposing the classic path as an in-process MCP server — it keeps the vocabulary closed but puts an MCP *server* in keeper's code, blurring DW-215's line.
- **Q4. Paseo's broker publishes no tool annotations** (`paseo-mcp.py:859-869`), so AD-406's rule ("unknown or destructive ⇒ T3") makes all four verbs T3, while AD-407 makes `list_agents` and `get_agent_status` T0.
  - **Plan's reading (accepted, R24(2); the annotation half superseded by S-14):** a server configured with `role = "paseo"` is classified by four rows in the tier table — the two reads T0, `create_agent` and `send_agent_prompt` T3 — and any other tool it lists is refused ("the broker has exactly four verbs", AD-407). For every other server the order is: the role's own table (`screen`, 96.4; `kvm:<id>`, 96.5), then a `[[mcp.tier]]` row the person wrote for that tool, then the server's annotations — read only when the person set `trust_annotations = true` (`readOnlyHint: true` without `destructiveHint` or `openWorldHint` gives T0, anything else T3) — and otherwise T3. Annotations are what a server says about itself; the MCP specification calls them untrusted hints, so a lying or compromised server lowers nothing the person did not vouch for. A `command` server's tools are never below T2, whatever a row or an annotation says (S-14).
- **Q5. Landlock restricts TCP only.** Its network rights (ABI 4+) are TCP bind and connect; UDP and raw sockets are not covered `[UNVERIFIED in the research; the kernel's Landlock documentation]`, so "network denied" needs a second mechanism on Linux.
  - **Plan's reading (accepted, R24(5)):** in a run without network, a seccomp filter (`seccompiler`, Apache-2.0, pure Rust, from Firecracker) refuses `socket(2)` for every family but `AF_UNIX`. 96.1 #4(g) proves it with a UDP send. In every run the same filter refuses the calls that reach into another process — `ptrace`, `process_vm_readv`, `process_vm_writev`, `kcmp`, `pidfd_getfd`, `perf_event_open` — and landlock denies `/proc` (S-07, 96.1 #4(i)(j)). **Rejected:** a network namespace — unprivileged user namespaces are restricted on current Ubuntu `[UNVERIFIED]`, and the host must not need privileges.
- **Q6. "Everything else denied" leaves toolchains unreachable.** `cargo`, `rustup`, `node` and friends live under a user's home or `/opt`, which AD-405's sandbox denies.
  - **Plan's reading:** the host's configuration names extra read-and-execute paths (`[sandbox] read_exec = [...]` in `agentd.toml`, the same list device-local on the desktop); the default is the system's (`/usr`, `/bin`, `/sbin`, `/lib*`, `/etc`, `/System`, `/Library/Developer/CommandLineTools` on macOS). No path inside a drive and no path holding the host's secrets is accepted there (refused at parse).
- **Q7. A pixel hash of the screen always drifts.** AD-408/AD-409 put "the screen hash" in an approval's preconditions; the menu-bar clock and a blinking caret change a screenshot's SHA-256 within a minute, so every approval would fail its re-check.
  - **Plan's reading (accepted, R24(6); the preview's place set by S-18):** an action on an element is pinned by the element's accessibility path, role, title and frame (Peekaboo's element ids, §7.2); an action at coordinates, and every KVM action, is pinned by a 64-bit difference hash of the target region with a Hamming bound fixed by fixtures (96.4 #5, 96.5 #6). The record keeps the preview's SHA-256 for audit. The image itself lives under the zone's `.keeper/previews/`, is never committed, and reaches a person only as the card's encrypted Matrix attachment (S-18, 96.4 #4).
- **Q8. MCP tool names cannot travel as `mcp:<server>/<tool>`.** OpenAI-compatible function names allow `a-z A-Z 0-9 _ -` and at most 64 characters `[UNVERIFIED in this program's research; the OpenAI API reference's function-name rule]`.
  - **Plan's reading (accepted, R24(7)):** the wire name is `mcp__<server>__<tool>`; the log, the config and the approval card keep `mcp:<server>/<tool>`. A tool whose wire name would exceed 64 characters or hold another character is not offered and is listed with its reason.
- **Q9. The epic map says no story here touches the shell crate.** AD-406 names "Settings on the desktop" as where the Mac's MCP servers are configured, which needs commands and a Settings section.
  - **Plan's reading (accepted, R24(8); the architecture's epic map is corrected):** 96.2 touches the shell — the Mac's device-local server table, three commands, their registration and the Settings section (96.2 *Files*), gated on the macOS job. Everything else stays in `keeper-core` and `keeper-agent`.
- **Q10. `run` with network meets NFR-121.** A command with network may reach any host its argv names, which nobody configured in advance.
  - **Plan's reading (accepted, R24(15); the declassified object changed by S-03):** a networked `run` is approved per run, at T3, and that approval is the person configuring that one destination; `docs/egress.md` gains a row saying so. A networked run mounts only the session's `workspace/` — no drive, no `.keeper/` — so the only bytes it can send are the argv's and the workspace's. Its approval therefore declassifies the workspace exactly as the card showed it: the record carries the SHA-256 set of `workspace/` (every file's relative path and hash), which is recomputed at consume and re-checked as a precondition (S-03). One approval, not two. A per-host allow-list is deferred (DW-398); a run that needs a drive's file and the network copies the file into its workspace first, in a separate step (DW-451).
- **Q11. Who holds the Screen Recording grant when keeper starts Peekaboo.** macOS attributes a child's TCC requests to the responsible app; if keeper.app launched Peekaboo as a child, keeper would need the grants AD-408 says it must not hold `[UNVERIFIED]`.
  - **Plan's reading:** Peekaboo runs as its own app in the person's GUI session (its Bridge host, §7.2) and keeper connects to it as a `url` server, never as a `command` child `[UNVERIFIED: whether Peekaboo's MCP server speaks streamable HTTP; §7.2]`; 96.4's device run verifies on hesperia that keeper.app appears in neither the Screen Recording nor the Accessibility list. A `command` screen server would also keep S-14's T2 floor, so even its screenshots would ask.
- **Q12. How the coding agent "follows status"** (AD-407). A coding run takes minutes to hours; a turn cannot wait that long.
  - **Plan's reading (accepted; the first run gated by S-21):** after an approved `create_agent`, the coding agent's host writes a follow card with `schedule: every 10m` (92.3) whose run calls `get_agent_status` (T0, raised once to T1 for being unattended — still automatic). An agent user wrote that schedule, so the card shows *scheduled by <agent>* and its first run waits for a person's tick (S-21, 92.3's `scheduled_by:`); the `create_agent` card says so. **Intent:** "different persons will hav diffrent tools to use (and/or … the whole computer)"; "heavy bots (like language server, debugger tools for coding)"; "connectors for dangerous actions before proceed". **Rung:** **epic96-run**. AD-405; AD-392's `run` rows; AD-393's execution binding; AD-391's `*` sink; D-33; S-03, S-07, S-08 (ruling R28).

**Files:**
- `keeper-core/src/agents/run.rs` (new, pure): `RunRequest { argv, cwd, network, timeout_s }` and its validation; the refusal table (shells with `-c`, privilege tools); `SandboxPlan { read_write, read_only, read_exec, network }` composed from facts — read-write: the session's `workspace/` and the run's own `HOME` and `TMPDIR` directories (S-08); read-only: the drives in scope only when `network` is false, while a networked plan mounts no drive and no `.keeper/` (S-03); the host's `read_exec`; the environment allow-list (#8); `ExecBinding` (the argv as run, cwd, env subset, executable path and SHA-256, operand hashes — an interpreter's script operand, the workspace root's dotfiles and git's runnable hooks (S-08) — and, for a networked run, the workspace's SHA-256 set (S-03)); the result's label (#14); the approval's summary (#16); `sbpl(plan) -> String`, the macOS profile as text, with `(deny process-info*)` and `(deny mach-lookup)` (S-07).
- `keeper-core/src/agents/tier.rs` (93.1's module): the `run` rows.
- `keeper-agent/src/run/` (new): `mod.rs` (resolve the executable on the fixed `PATH`, hash it, create the run's empty `HOME` and `TMPDIR` outside the workspace and remove them at the end, insert `-c core.hooksPath=/dev/null` after a `git` program, spawn in its own process group, timeout, bounded capture), `linux.rs` (landlock, granting nothing under `/proc`, and the seccomp filter — `socket(2)` for every family but `AF_UNIX` when without network, and `ptrace`, `process_vm_readv`, `process_vm_writev`, `kcmp`, `pidfd_getfd` and `perf_event_open` in every run (S-07) — applied in the child before `exec`), `macos.rs` (`/usr/bin/sandbox-exec -p <profile> -- <argv>`), `probe.rs` (the host's `sandbox` capability).

**Acceptance:**
1. **Never a shell string.** `run` refuses an argv whose program is a shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`) given `-c` or `--command`, or given no script operand (it would read a script from standard input) — directly or behind `env`, `nice`, `nohup`, `timeout`, `xargs`, `stdbuf`, `command`. The sentence names D-33. Test: `run_refuses_a_shell_string_in_every_disguise` (pure, keeper-core), a table of at least twenty argvs, each wrapper at least once. Risk: a wrapper the table forgot — mutation-proved by deleting each wrapper row.
2. **The tier rows.** No network and nothing below: T2. `network: true`: T3. Inline code (`python -c`, `python3 -c`, `node -e`/`--eval`, `perl -e`/`-E`, `ruby -e`, `osascript -e`, `deno eval`) and code the session holds: T4, the code or each held file's SHA-256 in the payload and in `exec_binding.operands`. Code the session holds is the executable, or an interpreter's script operand, resolving inside `workspace/`; any file or directory at the workspace's root whose name starts with `.` (a `.npmrc`, a `.cargo/config.toml`, a `.gitconfig`), hashed file by file; and any hook git would run in a `.git/hooks/` under `workspace/` — a file there whose name does not end in `.sample` (S-08). `git push --force`/`--force-with-lease`/`-f`: T4. `sudo`, `doas`, `su`, `pkexec`: T5, refused and handed to the person. The one raise (delegated, unattended, `untrusted`) applies once. Test: `run_tier_table` (pure), one row per case — including a workspace holding only `repo/.git/hooks/pre-commit.sample` (T2) and one holding `repo/.git/hooks/pre-commit` (T4) — plus `run_raise_is_applied_once`.
3. **The request is bounded.** `argv` 1–256 elements, each ≤ 32 KiB, no NUL; `cwd` relative, inside `workspace/` after canonicalisation (a symlink in `workspace/` pointing at the drive's `.git` is refused); `timeout_s` 1–1800, default 120. Test: `run_request_validation` (pure) and `run_cwd_symlink_escape_is_refused` (keeper-agent, a real symlink in a temp tree). Risk: a real symlink, not a lexical check (§13 #15's lesson).
4. **The Linux sandbox, against real files and a real kernel** (`keeper-agent/tests/run_linux.rs`, `cfg(target_os = "linux")`, temp trees for a drive, a session, a fake home and a fake secrets directory):
   - (a) `/bin/cat workspace/a.txt` succeeds; (b) without network, reading `<drive>/10-notes/x.md` succeeds, and with network it fails (S-03); (c) writing it fails with `EACCES` and its bytes are unchanged; (d) reading `<drive>/.git/config` fails; (e) reading `<home>/.ssh/id_ed25519` fails; (f) reading `<state>/keeper-agentd/secrets/x` and `$CREDENTIALS_DIRECTORY/x` fails;
   - (g) without network, a TCP connect to a listener the test opens on `127.0.0.1` fails, and a UDP send to the test's UDP socket never arrives (Q5); with network, both succeed;
   - (h) the drive's `.keeper/` is unreadable, with and without network;
   - (i) with `KEEPER_AGENTD_SECRET_X` planted in the test's own environment, reading `/proc/<ppid>/environ` and `/proc/<ppid>/mem` fails (landlock grants nothing under `/proc`, S-07);
   - (j) a helper binary the test builds calls `ptrace(PTRACE_ATTACH, <ppid>)`, `process_vm_readv` on the parent, `kcmp`, `pidfd_getfd` and `perf_event_open`, and each fails with `EPERM` (the seccomp filter, S-07).
   Risk: the real landlock ABI of the host; a test host whose kernel lacks ABI 4 fails these tests loudly — it never skips.
5. **The macOS sandbox, against real files** (`keeper-agent/tests/run_macos.rs`, `cfg(target_os = "macos")`): cases (a)–(h) through `/usr/bin/sandbox-exec`; for S-07, with `KEEPER_AGENTD_SECRET_X` planted in the test's environment, `/bin/ps -E -o command= -p <ppid>` inside the sandbox never prints it (`(deny process-info*)`), and a helper binary that looks up the `com.apple.SecurityServer` Mach service (the keychain's) fails (`(deny mach-lookup)`). Runs in CI's macOS Rust job (`ci.yml:30`) and on hesperia. The profile text for a fixture plan is a golden test that runs everywhere (`sbpl_golden`, pure), including a drive path with a space and a double quote, escaped, both deny rules, and a networked plan that names no drive path. Risk: `sandbox-exec`'s deprecation status (`[UNVERIFIED]`, §14) — if Apple removes it, the macOS host stops offering `sandbox` (#11), never runs unsandboxed.
6. **Time is bounded and the whole process group dies.** A fixture that forks a grandchild and sleeps, run with `timeout_s = 1`, leaves no process of its group alive one second later (checked by group id); the result says `timed out after 1 s`. Test: `run_timeout_kills_the_process_group` (Linux and macOS).
7. **Output is bounded and the bound disclosed.** `/usr/bin/yes` under a 1 s timeout returns 65 536 bytes of stdout and `truncated: {shown: 65536, total: <n>}` with `n > 65536`; stderr has its own 64 KiB. Test: `run_output_is_capped_and_says_so`.
8. **No credential is passed, and nothing in the workspace configures the program** (S-08). The child's environment is exactly `PATH` (the fixed system path plus the host's `read_exec` bins), `HOME` = an empty directory the host creates for this run outside the workspace and the drives, `TMPDIR` = a second such directory (both removed when the run ends), `LANG=C.UTF-8`, `TERM=dumb`, `NO_COLOR=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`. For a `git` program the host inserts `-c core.hooksPath=/dev/null` after it; the card and the digest show the argv as it runs. Tests: `run_environment_is_the_allow_list`, with `KEEPER_AGENTD_SECRET_X` and `AWS_SECRET_ACCESS_KEY` planted in the parent, reading `/usr/bin/env`'s output, listing `$HOME` (empty, not under `workspace/`) and finding both directories gone after the run; `run_git_runs_no_hook_and_reads_no_workspace_config` — a fixture repository `workspace/repo/` with an executable `pre-commit` hook that writes a marker, and a `workspace/.gitconfig`: the approved (T4, #2) `git -C repo -c user.name=t -c user.email=t@example.org commit --allow-empty -m x` succeeds and leaves no marker, and `git -C repo config --show-origin --list` names no file but `repo/.git/config`.
9. **The approval binds the binary.** With epic 93 beneath: a T3 `run` is approved; before it is consumed the test replaces the executable at the resolved path (a copied binary in a temp `read_exec` directory) — the re-check finds the SHA-256 changed, logs the drift and refuses, and the room holds no `dev.keeper.agent.approval.consumed` event for that record: the consumed event is sent only once every precondition holds, and the program starts only after the server has acknowledged it (93.2, S-01). Test: `run_exec_binding_drift_refuses` (keeper-agent, real files, 93.2's consume path). Risk: AD-394's consume-before-effect seam.
10. **Never a task, never a ⌘9 tool.** `TaskKind`'s round-trip test (`every_stored_spelling_round_trips`, `tasks.rs:1868`) and its drift guard against `TASK_KINDS` (`tasks.rs:2076-2240`) stay green and untouched — neither `tasks.rs` nor `src/lib/stores/sync.ts` is in this rung's diff (checked in review); `offer_tools` (`bots/tools.rs:613`) offers no `run` to any provider kind — test `bots_never_offer_run` (keeper-core).
11. **A host offers `sandbox` only when it can enforce it.** agentd probes at start: landlock ABI ≥ 4 and the seccomp filter loads; the desktop: `/usr/bin/sandbox-exec` exists and a probe `run` of `/usr/bin/true` exits 0. Without it the manifest omits `sandbox`, `keeper-agentd status` says `sandbox: unavailable — <reason>`, and an agent needing `sandbox` shows `waiting:` (90.6). Test: `sandbox_capability_follows_the_probe` (manifest builder over a faked probe) and `status_names_the_missing_sandbox`.
12. **Network is a send to anyone, of the workspace and nothing else.** `check_sink` for `run` with `network: true` is audience `*`: refused in a session with finite readers unless the run's own T3 approval carries the declassification. The declassified object is the SHA-256 set of `workspace/` — every file's relative path and hash — written into the record when the card is raised and recomputed at consume as a precondition (S-03): a workspace that changed between the card and the consume refuses as drift and asks again. Tests: `run_with_network_is_a_send_to_anyone` (pure, keeper-core) and `networked_run_releases_only_the_workspace_it_showed` (keeper-agent, with epic 93 beneath: a file added to `workspace/` after the decision makes the consume refuse with no `approval.consumed` event; an unchanged workspace runs, and its sandbox reads no drive, #4(b)).
13. **Docs.** `docs/agents.md` § *Running a command* (the argv rule; the sandbox's zones — `workspace/` read-write, the run's own `HOME` and `TMPDIR`, the drives read-only only without network; tiers and code the session holds; the bounds; the host capability; what a networked approval releases); `docs/egress.md` gains the row "a host an approved `run` with network names — only after you approve that run, which sees only its workspace"; the coordinator adds DW-213's resolution line.
14. **The result is labelled by what the run could read.** A `run`'s result joins the session's label with readers = the join of the drives its plan mounted (none when networked) and integrity `untrusted` when the run had network or mounted any drive — every drive carries `[integrity] untrusted` globs (89.2, S-02) and landlock cannot leave a glob out — else `agent` (the workspace alone, without network) (AD-405, AD-390). Test: `run_result_label` (pure, one row per case).
15. **A secret in the output is not logged.** A run `cat`s a workspace fixture holding an AWS-shaped key; the session log's `tool_result` line carries `[REDACTED secret-like: sha256:<12 hex>]` where the key was, and the key's bytes appear in no file under `log/` (89.5's `redact_secrets` in `ChunkWriter::append`, S-17). Test: `run_output_secret_is_redacted_in_the_log` (keeper-agent).
16. **The card's words are keeper's.** The approval's `summary` for `run` is composed by keeper from the request alone — *Run `<program>` in `workspace/<cwd>`*, plus *with network* when asked and *with code the session holds* at T4 — and never carries text the model wrote (S-10). Test: `run_summary_is_composed_from_the_request` (pure: equal requests give equal summaries; an argv element holding a newline or a right-to-left override is shown escaped).
17. **The new crates pass the licence firewall.** `cargo deny check licenses bans sources` (`ci.yml:109`) passes with `landlock` and `seccompiler` in the Linux target table; their licences, as `cargo deny` reads them, are quoted in the PR (NFR-119, F15).

## The failure shape this epic must not repeat

**A boundary that is a sentence.** "In-process guardrails do not hold" (research §3.9). A review that finds any of the following is a blocker:
- a `run` that executes before the sandbox is applied, or falls back to running unsandboxed when the probe fails;
- a networked `run` whose sandbox can read a drive or a `.keeper/` directory, or a networked approval that releases anything but the workspace set the card showed;
- a sandboxed child that can read `/proc` or reach into another process (`ptrace`, `process_vm_*`, `kcmp`, `pidfd_getfd`, `perf_event_open`, `process-info*` on macOS), or whose `HOME` lies in the workspace;
- a code path that builds a shell command line from model text;
- an MCP call, `run` with network or KVM action that reaches its server before `check_sink` answered;
- a TLS verifier that accepts what it cannot pin;
- an approval record whose precondition the consume path does not re-read, or an effect that starts before the server acknowledged the `approval.consumed` event;
- a screenshot or KVM frame written under a session's folder or into a commit.

**Power without a person.** A review that finds any of the following is a blocker:
- a KVM input below T4, or with `scopes` containing `session`;
- a `create_agent` approved for more than one call;
- a screen action consumed against a screen nobody re-read;
- an MCP tool lowered below T3 by annotations the person did not trust, or a `command` server's tool below T2;
- an approval summary that carries text the model wrote;
- a T4 screen or KVM action decided from the process that hosts it.
