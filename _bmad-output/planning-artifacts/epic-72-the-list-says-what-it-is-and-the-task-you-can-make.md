## What was measured

The owner's nine claims, verified against `a8eb9c2` (the tree 0.8.29 was cut from). Verdict vocabulary: **broken** (does not work), **unreachable** (works, no UI path), **deliberate** (a recorded decision, quoted), **absent** (never existed).

1. **"spaces list — first make All — sort by date, newest above"** — *absent* (the row) + *deliberate* (the order). `notes_spaces` (`keeper/src/notes_ipc.rs:1486-1542`) emits one row per space note plus the synthetic `Uncategorized` (`:1531`), sorted by `sort::rail_order` = `keeper.order` then **name** (`keeper-core/src/notes/sort.rs:105-112`). The scope an `All` row would select already exists and is the default (`src/lib/stores/notes-filters.ts:53-73` `ALL_NOTES_SCOPE`); the only ways back to it are toggling the active space off and the empty state's "Show all notes" (`space-list.tsx:376`). Inbox/Journal/Pinned are **not** built-ins: they are ordinary notes seeded once (`keeper-core/src/notes/default_spaces.rs:5-9`, AD-79). `NoteSpaceVm` (`keeper-core/src/notes/vm.rs:284-360`) carries no timestamp of any kind — but the entry the mapper already holds does (`notes/index.rs:113-131`), so a date key costs **zero** extra I/O.
2. **"every list item should show, after a moment, a tooltip with the name (and the description if it makes sense — markdown rendered — at least the beginning), especially when the name does not fit"** — *broken* for space rows and note rows (no hover text at all: `space-list.tsx:236`, `note-row.tsx:273-275` truncate with nothing behind them), *deliberate* for files rows (Story 44.12 replaced `title=` with a click-to-open `FullValueButton`, `files-pane.tsx:1075-1124`). The shadcn `Tooltip` exists and a root `TooltipProvider` is mounted (`src/components/ui/tooltip.tsx`, `app-shell.tsx:295`) — with `delayDuration = 0`, so even where a tooltip exists "after a moment" is unmet. No markdown renderer exists in the frontend; `NoteRowVm.snippet` crosses IPC as **raw markdown** and is drawn verbatim as the row's second line, which is why the owner's screenshot reads `# Company wiki — update log ## 2026-09-13 * **…`.
3. **"same tooltip on all the icons"** — *broken*. ≈30 icon-only controls carry neither `title=` nor a `Tooltip`, and no shared wrapper exists to make the answer uniform.
4. **"in spaces and elsewhere the row shading does not cover the part with the icons"** — *broken*, and exactly as visible as it looks: the hover/selected background sits on the inner `flex-1` row button (`space-list.tsx:238-240`) while the three action buttons are its **siblings** inside `<li className="group flex items-start">` (`:224`, `:285-337`). Same shape in `session-spaces.tsx:932-947`.
5. **"notes could have back and forward buttons, like in browsers, with the whole history back and forward — when I move note to note through links"** — *absent*. Link following works (Story 45.18) and every one of the ten note-opening call sites funnels through two verbs on one store — `panelsStore.setActiveTarget` (`src/lib/stores/panels.ts:565`) and `openPanel` (`:613`) — which replace the panel's target with no stack. `note-history-panel.tsx` is *revision* history (git commits), not navigation history. Since 46.12 removed `NOTE_PANEL_LIMIT`, two editors can be open at once, so there is no "the" history.
6. **"in tasks, when I click a task the UI falls apart completely; those long descriptions are unnecessary (or could be in a tooltip)"** — *broken*, and the header prose is the **victim**, not the cause. One click does two things: `select(id, "replace")` reveals a `shrink-0` cluster (count badge + `Enable selected` + `Disable selected` + `Forget selected` + `Add a task` + `Refresh` ≈ 685 px, `tasks-pane.tsx:542-544`, `:2899`, `:2917`) and `setActiveTarget` mounts the 280 px panel strip (`app-shell.tsx:473-475`), cutting the pane from ~1344 px to ~832 px. Header content = 832 − 48 padding − 685 unsqueezable ≈ **100 px**, and the only element that may shrink is the `min-w-0` prose div (`:2889`) — the screenshot's two words per line over twelve lines. The Tasks pane is the only major surface that hand-rolls its header instead of using `PaneHeader`, whose `paneHeaderActionsBudget` (`pane-header.tsx:181-201`) is the in-repo fix for precisely this class. Nothing violates Story 59.13's floors; they all hold.
7. **"recording content does not take the window's width like other elements"** — *deliberate*. `recording-pane.tsx:312` is `mx-auto w-full max-w-[720px]`, the UX-DR29 readability measure minted for the conversation pane's text; the header above it (`:201`) and Settings/Files (`settings-pane.tsx:35-36`, `files-pane.tsx:3262-3263`) are full-bleed. `sync-pane.tsx:876-882` is the in-repo compromise: full-bleed body, the measure on form cards only.
8. **"tasks does not seem to show the scheduled tasks that exist (sync, deep sync, etc — there is only gc, and it always says it never ran)"** — two different verdicts. The missing rows: *absent by omission* — `TaskKind` already has `Sync | Release | Verify | Bot | Gc` (`keeper-sync/src/tasks.rs:171-268`) and only `Gc` is ever **seeded** (`db.rs:4360-4413` `seed_gc_task`, called per folder at open, `engine.rs:1995-2019`); no Sync or Verify row is written, and nothing filters them out — they do not exist. "gc always says never run": *not a defect* — the write and the read are the same table and the same row id (`db.rs:4056`/`:4220` vs `sync_ipc.rs:2199-2205`), and `seed_gc_task` stores `next_due_ms: None`, which the first tick arms at `now + 7d` (`GC_TASK_SCHEDULE`, `db.rs:4316`). The owner's install has simply not reached its first window; the pane's `never run` is true and reads like a fault.
9. **"a new task is not possible at all (from the UI's perspective)"** — *broken*, and the cause is one default. The chain is complete: button (`tasks-pane.tsx:2975`) → form (`task-form.tsx:513-527`) → `syncTaskSave` (`client.ts:6654`) → `sync_task_save` (`sync_ipc.rs:2418`) → `upsert_task` (`db.rs:3444`). The add form seeds `mode: "scheduled"` with `schedule: ""`, which the store refuses — *"task '{id}' is scheduled with no schedule: it would report itself enabled and never run"* (`db.rs:3454-3459`) — while the form's own note says "Leave it empty to store no schedule" with no clause that a scheduled task needs one, and the refusal renders at the foot of a ten-row form inside a 360 px-floor region. Story 59.13 could not see this: `dev/mock-shell.ts:3416-3490` mirrors two of `upsert_task`'s refusals and **not** this one, so the probe's `create.row_in_list=yes` was true of the mock and false of Rust.
10. **the two new kinds the owner asked for** — `TaskKind::Bot` exists (Story 69.4, `backlog`) and is unfinished on three independent sides, each alone fatal: `upsert_task`'s INSERT/UPDATE never writes `bot_id`/`prompt_subpath`/`model` (`db.rs:3546-3574`), no host implements `SyncPlatform::bot_task_runner` (default `None`, `platform.rs:442-444`, so every run records `Deferred`), and the form cannot offer it (`NEVER_OFFERED = ["bot"]`, `tasks.rs:2200`). A local↔local copy is **not** the sync engine — sync is git+LFS with a mandatory `remote_url` (`profile/mod.rs:766`) — it is `keeper_sync::copy::copy_verified` (`copy.rs:234-249`), which the Sync pane already hosts as "Copy files once" (`sync-pane.tsx:570-642` → `copy_ipc.rs:243-343`), with its own hash-on-write, atomic rename and refusals. No mtime predicate exists anywhere in `keeper-sync`; the site for one is `copy.rs:970-1037` `classify`, which already holds the `Metadata`.

## The one sentence

**Nine complaints, one shape: keeper knows the answer and does not put it where the pointer is** — the scope it would filter by has no row, the name it truncates has no hint, the prose it prints has no budget, the kinds it runs have no seeder and no form, and the one form it does have is seeded with a request its own store refuses.

## Decisions this epic takes

- **AD-237 — The rail opens on everything, then leads with the newest.** `notes_spaces` composes a second synthetic row beside `Uncategorized`: `All notes` (`ALL_SPACE_ID`), pinned **first** for the same reason `Uncategorized` is pinned last — its order is not a position anybody chose, so it must not compete with the ones that are. `NoteSpaceVm` gains `updated_ms: Option<i64>`, read from the `IndexEntry` the mapper already holds (no new I/O, no stat walk), and `sort::rail_order`'s **name** tie-break becomes **`updated_ms` descending, then name**. Explicit `keeper.order` positions stay authoritative and untouched: a rail somebody has positioned does not move. This amends 44.4's "an un-ordered rail is still the alphabetical rail it has always been" — deliberately, on the owner's word, because alphabetical order of a rail whose contents change daily is a stale rail; the escape hatch (a number in the space editor) is unchanged and now outranks the date.
- **AD-238 — A preview is prose, and Rust makes it so.** `NoteRowVm.snippet` is composed from the note's body with markdown **markup** removed — ATX/setext headings, emphasis and strong marks, inline code fences and backticks, link/image syntax reduced to their text, list bullets and blockquote marks — in `keeper-core`, where the frontmatter parser and the ATX rule already live (`notes/frontmatter.rs:165-179`, `notes/naming.rs:167-190`). Character budgets count `char`s, never UTF-16 units. The frontend gains no markdown renderer: "markdown rendered" is answered by sending prose, which fixes the list row and the hint with one change.
- **AD-239 — A hint is delayed, bounded, keyboard-reachable, and never the only way to read something.** One wrapper pair in `src/components/ui/tooltip.tsx` — `HoverHint` (name + optional prose detail, `line-clamp`ed) and `IconHint` (the control's own accessible name) — with `HOVER_HINT_DELAY_MS = 500`, `max-w-xs`, at most three lines of detail, `side` defaulting to the reading direction of the rail it hangs off. This **answers** AD-83/44.12 rather than overturning it: 44.12's objection was to `title=`, "a tooltip that does not exist for a keyboard, does not exist for a touch screen, cannot be scrolled, and appears after a delay nobody chose" — a Radix hint shows on focus, has a delay we chose, and is **additive**: the files pane keeps its `FullValueButton`, which stays the readable, scrollable, touchable path. Two carve-outs, both recorded: a folded avatar rail gets no hint (45.20 — the avatar already carries the name and a long-press owns the gesture), and no hint ever carries information that is not also reachable without a mouse.
- **AD-240 — A pane header has a budget, and prose is not a layout member.** The Tasks pane adopts `PaneHeader`'s identity/status/actions budget (`pane-header.tsx:181-201`, `priority-actions.tsx`), so its verb cluster demotes into `⋯` instead of crushing its neighbour; `TASKS_PANE_SUBTITLE` and `TASKS_RUN_NOW_SENTENCE` move out of the header flow into an `IconHint` on the header's info control. The siting note that put them there ("this is one fact about the verb … said in words rather than left to be inferred from an absence") was precedent, not an invariant; the owner's report overturns it. CI owns the arithmetic: a header whose unsqueezable cluster exceeds `pane floor − PANE_HEADER_IDENTITY_MIN_PX` fails a test derived from the constants, the way `src/lib/window-minimum.test.ts:43-83` already derives the window minimum. **One implementation note, because a reviewer will ask:** the `⋯` control is always rendered — `PriorityActions` measures its width to know the budget in the first place — and the promoted controls are icon-only, so the menu carries the pane's two standing verbs (`Add a task`, `Refresh`) **in words** at every width, beside whatever actually demoted. A menu that emptied itself when nothing demoted would be a trigger that opens onto nothing, which is worse than a verb a person can reach two ways.
- **AD-241 — Navigation history is per panel, and it belongs to the viewer.** The back/forward stacks live on `Panel` in `src/lib/stores/panels.ts`, beside `Panel.replaced`, and are pushed **inside** `setActiveTarget` — the one verb all ten opening call sites already funnel through — so no call site learns anything new and nothing can open a note without being remembered. `openPanel` starts a new panel with its own empty stacks (two editors, two histories, per 46.12). `back`/`forward` do not record; a new target truncates the forward stack; the stacks are capped (`PANEL_HISTORY_CAP = 50`) and are not persisted — this is "a lens the viewer arranged rather than a fact Rust has any use for" (`panels.ts:30-36`). The *verbs* are Rust: `notes-back` and `notes-forward` are registered in `keeper-core/src/palette.rs`'s notes category so the palette, the cheat sheet and the menu bar all learn them from one place, with handlers in `src/components/command-palette/actions.ts`.
- **AD-242 — The clock work keeper does is listed where its schedule is set, and it still has one driver.** The machine is seeded, once, with a host-wide `Sync` row and a host-wide `Verify` row (`profile_id: None`, `mode: Scheduled`, **`enabled: false`**, Sync at the 1 h watcher backstop the engine already keeps, Verify weekly as a proposal it does not) beside the per-folder `Gc` rows that already exist — so the owner sees the work that exists and holds the switch for it. **Amended during implementation, and the reason is worth keeping:** the first shape seeded a row per folder, and measurement showed that a folder-tier row shadows the host-wide tier by design (`mine.or(host_wide)`), so per-folder proposals would have made a host-wide scheduled Sync task — a configuration the form offers as "the whole machine" — impossible to honour for any folder, forever. The same measurement found a **pre-existing defect** the seed would have made universal: governance folds the rows of one tier by *least* rank after mapping a disabled row to `Off`, so one row that cannot run vetoed a sibling that can — a hand-authored disabled Sync row already cancelled the governance of an enabled one (proved by throwaway test before the fix). Inside a tier, Sync now folds by *greatest* rank: the question is whether any task here governs, and a switched-off row answers nothing rather than answering no. `Release` keeps its least-rank fold, quoted and untouched, because "the safe reading of two rows disagreeing about a deletion is the one that deletes less". The enabled→`Off` mapping and folder-over-host precedence are unchanged, so a fresh install behaves byte-identically: the proposals fold to `Off`, and the paced poll runs exactly as today. AD-141 keeps its teeth — a seeded row is a remembered schedule, never a second driver; enabling the Sync row stands the paced scan poll down through Story 58.8's existing governance and nothing is migrated out of "Also paced by this host".
- **AD-243 — An add form is seeded with a request the store accepts, and a refusal is visible where it happened.** The add form seeds `mode: "manual"` — which is what `keeper-syncd` itself defaults to when no schedule is given (`commands.rs:4082-4083`) — the schedule note says plainly that a scheduled task needs a schedule, and the refusal `role="alert"` is rendered **above** the controls and scrolled into view when it appears. Story 58.1's boundary is kept: TypeScript never re-implements or pre-validates a Rust rule; the sentence the user reads is Rust's. `dev/mock-shell.ts` mirrors `upsert_task`'s scheduled-with-no-schedule refusal, so the probe can fail where the app fails.
- **AD-244 — A bot task runs with nobody there: it reads under the grants that exist and writes only where one already says yes.** `ShellSyncPlatform::bot_task_runner` builds a turn the way `open_turn` does, minus the session, the channel and the voice — and with `approve: None`, which the drive host already documents as "declines every ask" (`bots_tools.rs:97-98`). So `grant::decide` runs at every tool call as always: reads proceed under a live read-or-write grant, a write inside an approved **subtree** proceeds, and every `Ask` becomes a refusal with its audit row closed `Refused` and the denial reported to the model. Nothing is pre-approved by a schedule, no grant is widened, and the run continues after a refusal. The prompt is **any** `.md` under one of keeper's folders, resolved by `browse::resolve` — no new path arithmetic (AD-65/AD-159) — with the frontmatter and the leading ATX heading stripped by the runner (`keeper-core`'s parsers), which amends AD-224's `<zone>/<session>/prompts/` siting: that rule was never implemented and the engine already accepts any resolved path. A run without a `model` is refused with a sentence, never guessed. The kind is listed on every tier and runs only where `bot_tools` is true (desktop **and** `sync`); a phone lists the row and the Mac runs it (AD-226).
- **AD-245 — A copy task is a schedule over a job, and the date window belongs to the job.** `TaskKind::Copy` carries two absolute paths from native pickers — verbatim, the way `copy_start` already takes them (`copy_ipc.rs:246-259`) — plus `replace_existing` and optional `modified_after_ms`/`modified_before_ms`, and each run is `copy_verified` with its own report and its own copy log in the destination. AD-C1 holds: no profile row, no journal row, no relationship, no deletion propagation, no convergence — the word is **copy**, not sync. The date bounds enter at `copy.rs:970-1037` `classify`, which already holds the `Metadata`, and a bounded-out file is a named `Skipped` item in the plan, never a silent omission. The same bounds appear on the Sync pane's one-time copy card. **The owner's "add it to sync too" is refused, deliberately:** an mtime window on a git pass cannot be what AD-45 requires an exclusion to be — "not staged, not queued, not counted, never reported as pending" — because the file is tracked, stays dirty in the index, is re-walked every pass and would be committed by the next pass without the filter; and a pull from a peer consults no local mtime at all (§4 completeness, §5 "convergence never waits on a prompt"). A date-bounded sync is a copy with a schedule, which is what this epic ships.
- **UX-DR93 — The Recording pane's body fills the pane.** `recording-pane.tsx:312` drops `mx-auto max-w-[720px]`; the cards inside keep their own measure where a form needs one, which is `sync-pane.tsx`'s shape already. UX-DR29 keeps the conversation pane it was minted for; Recording is not a reading column, it is a form and a status card that the owner reads beside the rest of the app. Safe on the phone tier by construction: the constraint is inert below 720 px and `phone-shell.tsx` mounts no recording surface.
