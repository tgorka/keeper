# Epic 73 — The ledger tells the truth, and a folder that cannot converge says so

created: '2026-09-17'
source: two things at once. (1) A field investigation of the owner's own Mac on 2026-09-17: three live sync profiles (`neuradrive`, `tgdrive` on a removable volume, `tgdrive-light` on the internal disk, the last two clones of one repository), measured from `sync.db`, the 68 000-line debug log and the repositories themselves. It found one folder that had not committed for 22 hours, one that had been deadlocked for 75 minutes, and one LFS object that existed nowhere the other clone could reach — recorded as DW-252…DW-255. (2) A full triage of the deferred-work ledger: six read-only lanes verified **274 open entries** against the tree, because a ledger nobody has checked in five months is a list of worries, not of work.
binds: FR-544…FR-552 (allocated here); AD-246…AD-249 (new); makes AD-45 real on the commit path (an exclusion must be invisible), extends AD-228's "offline is a word the folder reaches" to "a folder that cannot converge is a state the folder reaches", keeps AD-231 (prune only what the remote holds) and turns its completeness rule around to publish, keeps AD-230 (a control file is never a pointer) and closes the hole its escape hatch cannot reach.
see-also: epic 70 (the pass that costs what changed — this epic closes four of its leftovers and corrects two of its ledger entries), epic 72 (the field report before this one), `docs/sync.md` §§13-14, §20-21.

## What was measured

All of it on hesperia, 2026-09-17, against keeper 0.8.29/0.8.30.

1. **A folder that had not committed in 22 hours while reporting itself dirty.** `tgdrive`'s status walk read `entries=1 scanned=156941 modified=1` on every poll, ~once a minute, for 15 consecutive paced passes after 07:59Z — and committed nothing. The one modified path was `10-notes/.keeper/index.json`: keeper's own notes index cache, **tracked in git** on the drive it syncs. keeper excludes `.keeper/` from sync, so the commit leg skipped it; git kept reporting it, so the walk kept counting it and the pane kept showing "1 modified". Its untracked neighbour `.keeper/trash/` was correctly invisible (`untracked=0`) — which is the proof that the exclusion works right up to the moment git carries the path.
2. **A folder deadlocked for 75 minutes, retrying an operation whose precondition it never re-established.** `tgdrive-light` logged, every few minutes from 23:55Z: `remote polled: the remote branch moved fast_forward=true received_pack=true` → `sync retrying … git merge --ff-only failed (exit 1): error: Your local changes to the following files would be overwritten by merge: 10-notes/.keeper/index.json` → `sync warning … sync has failed 3 times in a row`. The blocking path was the same excluded-but-tracked cache, which makes the deadlock **total**: keeper cannot commit it (the exclusion) and cannot merge past it (git refuses), so the folder can never converge again by itself. Nothing in the UI said so; the only trace was a WARN in a log that is off by default.
3. **A commit whose LFS object reached no remote.** `tgdrive` committed `3bc392792` at 07:59:39Z with `lfs=1`. The commit reached the server — the second clone had it — but object `86ac462d…` (1089 B) existed only in `/Volumes/merope/tgdrive/.git/lfs/objects/`. The server answered `unknown host does not have LFS object …` to every fetch, so `tgdrive-light` parked 15 `lfsDownload` rows and retried them for ~14 hours (16 failures in one hour of log), leaving the working file as a 129-byte pointer nobody could read. `lfs prune: nothing to release` proves prune did not delete it: the upload leg simply never ran. Repaired by hand (`git lfs push --object-id`), after which keeper hydrated the file on its next pass.
4. **The file that became a pointer should never have been one.** It was a 1 KB recording manifest conflict copy, routed by `*.json filter=lfs` at line 179 of `.gitattributes` — **inside keeper's own managed block** (line 1: `# keeper-sync: managed LFS rules — edit above this line`). Git history shows the owner removing that rule by hand on 2026-08-27 (`a04c21f30 chore(lfs): stop routing text through LFS`) and **keeper putting it back** on 2026-09-10 (`bb013cc88`, a transcript batch in which `seg-0000.json` was stored as a pointer). A local repro against the owner's real `.gitattributes` and real 18-glob `lfsNever` shows the retirement code *works*: `ensure_attributes` drops `*.json` in one pass. So the routing was not a broken retirement — it was a `lfsNever` that was not yet in effect, and **there is no supported way to put one into effect on a folder that already exists**: `--lfs-never` is an `add`-time flag only (`keeper-syncd/src/commands.rs:857`), there is no edit verb, and `grep lfsNever src/` finds no UI. The documented escape hatch cannot be applied to the folder that needs it.
5. **The two clones' policies disagree, on one shared file.** `tgdrive` carried an 18-glob `lfsNever`; `tgdrive-light` carried none, on the same repository — so what one clone refuses to route, the other routes, into a `.gitattributes` they both commit. Equalised by hand; nothing in keeper would have noticed.
6. **The ledger's own state.** 274 open entries; six lanes verified each against the tree. **≈18 are already fixed** and were never marked (one of them, DW-N4, is "the updater channel is broken" — closed by yesterday's release), **≈18 are moot or superseded**, **≈15 are blocked** on something unbuilt (five of them only because the Tauri shell crate does not link on Linux), **≈21 need a human decision**, **≈21 need a device or a running app to settle**, and **≈187 are real and buildable today**. Six cohesive bundles were proposed by the lanes, the largest being `drafts-outbox-persistence` (8 entries) and `tray-write-discipline` (6).

## The one sentence

**Two folders on one machine could not converge and said nothing about it, because an exclusion keeps being counted, a refusal keeps being retried, an object gets published without its bytes, and the one setting that would have prevented it cannot be changed after the folder exists — and the ledger that should have carried all four had 274 open entries nobody had checked.**

## Decisions this epic takes

- **AD-246 — An exclusion is invisible on the commit path too, and a tracked one is said out loud once.** A path the profile excludes is subtracted from the walk's counters and from the pending figure the pane reads, so a folder whose only "modified" file is excluded reads **clean**, which is what AD-45 has said since epic 23 and what the commit leg has always done. Silence is not enough, though: a tracked-and-excluded path can never be committed and can block a merge (AD-247), so keeper raises **one** anomaly per pass naming up to a handful of such paths and telling the person the one thing that fixes it — untrack them. The anomaly is a standing fact reported once, never an event per walk (epic 70's 1.2 GB log is the reason that distinction is a rule).
- **AD-247 — A fast-forward that cannot start is a verdict, not a retry.** `git merge --ff-only`'s "Your local changes to the following files would be overwritten by merge" is classified as its own refusal, with the paths parsed out of git's own output and carried in the error. Two arms, and the split is the point: if **every** blocking path is one keeper excludes from sync, keeper resolves it itself — those bytes are keeper's or the machine's, never the user's shared content, and the fast-forward is the only thing that can make the folder converge again — and it says in the log which paths it discarded. If **any** blocking path is user content, keeper stops, reports `NeedsAttention` with the paths in the sentence, and **stops re-arming the same pull** until something changes; a retry that cannot alter its own precondition is a loop, and the folder has to be able to tell a person that only they can move it.
- **AD-248 — A push does not report success while an object it published is missing from the remote.** The completeness rule AD-231 applies to prune ("release only what the remote is known to hold") is turned around: before a push reports success, every LFS object referenced by the commits it pushed must be present remotely — by upload in this pass, or by a `synced_at_ms` memo from an earlier one. An object that cannot be uploaded fails the push with a sentence naming the oid and the path, and the commit stays local and retryable, which is the state it was always safe in. On the reading side, `lfsDownload` distinguishes **"the remote does not have it"** from a transport failure: the former is a stated fact about the folder, surfaced once with the path and the oid, not a WARN retried every few minutes for fourteen hours; the latter keeps its backoff. A journal row whose object has since arrived in the local store retires instead of parking forever.
- **AD-249 — Every routing setting a folder has can be changed after the folder exists, and changing one repairs the managed block at once.** `lfsNever`, `excludes` and the LFS threshold gain an edit verb: `keeper-syncd folders set --lfs-never …` (repeatable, replacing the stored list), the IPC command behind it, and a field in the Sync pane. Writing one runs the managed-block repair immediately instead of waiting for the next commit that happens to stage something — measurement showed a stale `*.json` rule surviving weeks of commits because the folder had no reason to stage an LFS candidate. Two clones of one repository whose `lfsNever` lists differ is a state keeper reports as an anomaly on the folder, because the shared file they both commit can only carry one answer.

## Stories

### 73.1 — An excluded path is not counted, and a tracked one is named
AD-246. The walk's counters and the pending figure subtract excluded paths; one anomaly per pass names tracked-and-excluded paths and says to untrack them; `docs/sync.md` §20 records the rule.
**Acceptance:** a fixture with one tracked, excluded, modified path reads `modified=0` from the walk and `clean` from the durable status, and the same fixture with one tracked, excluded, modified path **and** one ordinary modified path reads `modified=1` and commits exactly the ordinary one; the anomaly fires once per pass and names the path; a fixture with an untracked excluded path raises no anomaly (it is already invisible); the pane's pending count for the first fixture is zero.
**binds:** FR-544, FR-545, AD-246, AD-45

### 73.2 — A fast-forward that cannot start says which paths hold it, and stops looping
AD-247. Classify the refusal, parse the paths from git's output, resolve it when every path is excluded, refuse with `NeedsAttention` and stop re-arming when any path is not.
**Acceptance:** a fixture whose only blocking path is excluded-and-tracked converges by itself, and the log names what it discarded; a fixture whose blocking path is user content ends `NeedsAttention` with the path in the sentence and does **not** attempt the same pull again until the tree changes (a counter test over three ticks); the real hesperia string (`error: Your local changes to the following files would be overwritten by merge:\n\t10-notes/.keeper/index.json`) is a test vector and classifies as this refusal rather than as `GitCommand`/transient; a merge that fails for any other reason keeps its current behaviour.
**binds:** FR-546, FR-547, AD-247, AD-228

### 73.3 — Nothing is published without its bytes, and a missing object is a fact, not a retry
AD-248. The publish-side completeness gate; the oid/path sentence; `lfsDownload`'s remote-does-not-have-it verdict; a parked row retiring when the object is already in the store.
**Acceptance:** a fixture whose LFS upload is refused fails the push with the oid and the path in the sentence and leaves the commit local (and a following pass succeeds once the upload does); a fixture whose object is already memoised as synced pushes without re-uploading (counter test); a download against a remote that answers "does not have it" records one stated fact with the path and oid rather than N retries, and the same row retires without a network call when the object is found in the local store; the hesperia sentence `unknown host does not have LFS object 86ac462d…` is a test vector.
**binds:** FR-548, FR-549, AD-248, AD-231

### 73.4 — A folder's routing settings can be changed after it exists
AD-249. `folders set` in the CLI for `--lfs-never`/`--exclude`/`--lfs-threshold-bytes`, the IPC command, the Sync pane field, the immediate managed-block repair, and the anomaly for two clones of one repository whose lists disagree.
**Acceptance:** the CLI sets `lfsNever` on an existing folder and the stored profile reads it back; writing it repairs the managed block in the same call (a fixture seeded with `*.json` below the marker loses it without any commit happening); a second clone of the same repository with a different list raises the anomaly naming both folders; the CLI-vs-`docs/sync.md` guard covers the new verb. The Sync pane field and its IPC command are gated by the macOS job — this crate does not link on the Linux dev host.
**binds:** FR-550, FR-551, AD-249, AD-230

### 73.5 — The ledger says what is true
The triage's own result, written down: the ≈18 verified-resolved entries closed with their evidence, the moot ones marked `skip` with reasons, the blocked ones carrying the blocker's name, the entries needing a device or a running app marked `needs-field-check` with the command that settles them, and the six proposed bundles plus the ≈21 human decisions recorded where the next planning session will read them.
**Acceptance:** every entry the triage touched carries one of `done` / `skip` / `blocked` / `needs-field-check` / `open`, with `resolution:` evidence (a `file:line` or a commit) on every `done`; no entry is left with two statuses; the bundle list and the decision list exist as a section of the ledger rather than as six agent reports nobody can find; the count of open entries at the end is stated and matches the arithmetic.
**binds:** FR-552

## What stays out

- **The ≈187 real entries the triage confirmed.** They are bundles now, with names and touchpoints; this epic fixes the four the field produced and does not pretend to clear the rest.
- **The ≈21 decisions.** They are recorded for a human, not resolved by an agent — that is what makes them decisions.
- **Renormalising the 746 JSON files already stored as LFS objects** in the owner's folder. History keeps them; keeper's own anomaly already says the cost is permanent and known. Only new writes change.
- **Anything that needs the shell crate to link on Linux** (five ledger entries, and 73.4's UI half): still gated by the macOS job, unchanged.
