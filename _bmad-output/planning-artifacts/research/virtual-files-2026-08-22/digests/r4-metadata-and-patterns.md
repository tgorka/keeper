# Metadata surfaces for non-local content, and pattern-file design for materialization policy
_agent: R4Metadata · accessed: 2026-08-22_

## Verdict (decision-grade)

- **The durable, portable, cheap carrier for "this is a stub for a 6 GB video, oid …, last materialized …" is a repository-internal sidecar index (a file under the tool's own control directory), NOT xattrs and NOT the placeholder's own bytes.** xattrs are silently dropped by the default settings of every common copy tool: `rsync` needs `-X` and even then only copies the `user.*` namespace as a non-root user; `cp` needs `-a`/`--preserve=xattr`; GNU `tar` needs explicit opt-in. A stub whose identity lives only in an xattr becomes an anonymous 0-byte file after one `rsync` or one unzip.
- **The in-file placeholder ("the stub IS the file") is the dominant prior art and the only carrier that survives arbitrary copying** — git-LFS pointers, git-annex pointer files, DVC `.dvc` sidecars, macOS `.icloud` plists all do this. Its cost is well documented and unavoidable: apps that open it get garbage, `du`/`ls -l` report the stub size not the real size, and (for LFS/annex) git sees the stub as the tracked content.
- **git-LFS already gives you three of the four metadata fields you want, for free and in-band**: `oid sha256:…` and `size` are *mandatory* pointer keys, and the spec *requires* parsers to preserve unknown keys — so a `keeper`-specific line is spec-legal. The `ext-{order}-{name}` extension mechanism shows the intended shape for such extra keys, but it is explicitly labelled **experimental**, and any pointer (extensions included) **must stay under 1024 bytes**. That budget is the binding constraint on in-pointer metadata.
- **Do not put mutable state (last-materialized timestamp, last-access) in the pointer.** The pointer is a git blob: mutating it dirties the working tree, produces spurious diffs, and changes the blob OID. Volatile eviction state belongs in the same place LFS already keeps volatile state — a local, untracked index under the git dir. git-annex makes exactly this split: immutable key facts in the key/pointer, mutable location facts in the `git-annex` branch (`whereis`), and it explicitly refuses to record last-verified timestamps because it would "bloat the git-annex branch".
- **For the pattern file: adopt `.gitignore` semantics verbatim, and implement them with the `ignore` crate (`Unlicense OR MIT`) or `gix-glob`/`gix-pathspec`/`gix-attributes` (all `MIT OR Apache-2.0`). Every candidate is permissive; none is GPL/AGPL, so the licence firewall does not decide between them.** Prefer `ignore` if you want a whole-tree walker with per-directory `.gitignore` stacking already solved; prefer `gix-*` if you need git-identical `.gitattributes` semantics (macros, `-attr`, unset-vs-unspecified) and are already conceptually in git's model.
- **Do not invent a boolean-expression language for size/type policy.** git-annex's `largerthan=100kb and not (include=*.c or include=*.h)` is the fully-general design, and its own documentation warns that squeezing it into `.gitattributes` requires whitespace-free parenthesised mangling and is "not recommended". A two-layer design — gitignore-style patterns for *which paths*, plus a small number of scalar thresholds (`min-size`) as separate keys — matches how LFS (`migrate --above=<size>`) and rclone (`--min-size`/`--max-size`, both `SizeSuffix`) actually ship this, and avoids a parser you must maintain forever.
- **Size rules and pattern rules interact badly and the failure is directional.** A size rule cannot be evaluated for content that is not local — this is not a corner case, it is the steady state of a virtual-files system. git-annex documents precisely this for `mimetype=`: it "only matches when the content of the file is present in the local repository". A policy of the form "dematerialize anything over 100 MB" is decidable from LFS pointer `size` (which is recorded), but "dematerialize anything whose MIME type is video/*" is not decidable once the file is already a stub. Design the expression set so every term is answerable from the *pointer*, never from the bytes.
- **System-level "online-only" presentation is a platform capability, not something a daemon can synthesise.** On Windows it is the Cloud Filter API (`cldflt.sys` minifilter, reparse-point-based, NTFS-only, placeholders cost ~1 KB, three states placeholder/full/pinned-full, hydration state icons are provided by the platform and explicitly "replace legacy icon overlay Shell extensions"). On macOS it is File Provider. Both require a registered sync root and a desktop-app host. **Neither exists on a headless Linux `keeper-syncd` server**, where the only honest presentation is a pointer file plus a `keeper`-side `ls`/`status` command — i.e. the `git lfs ls-files --size --debug` and `git annex whereis` model.

## Findings

### 1. Metadata surfaces for content that is not local

#### git-LFS: the pointer is a metadata record with a hard size budget

- Pointer files are UTF-8, `{key} {value}\n` lines, keys restricted to `[a-z] [0-9] . -`, `version` always first, remaining keys sorted alphabetically ascending, and "Pointer files must be less than 1024 bytes in size, including any pointer extension lines" — source: git-lfs/git-lfs, `docs/spec.md`, GitHub `main`, published unknown (living doc).
- The required keys are exactly `version`, `oid` (`{hash-method}:{hash}`, currently only `sha256`, lower-case hex) and `size` (bytes) — source: git-lfs/git-lfs, `docs/spec.md`.
- "Tools that parse and regenerate pointer files MUST preserve keys that they don't know or care about." This is the licence to add a `keeper`-namespaced key without breaking `git-lfs` interop — source: git-lfs/git-lfs, `docs/spec.md`.
- "Pointer files are unique: that is, there is exactly one valid encoding for a pointer file." Any extra key therefore changes the blob OID and is a *content* change, not an annotation — source: git-lfs/git-lfs, `docs/spec.md`.
- The extension mechanism writes lines of the form `ext-{order}-{name} {hash-method}:{hash-of-input-to-extension}`, registered in git config under `[lfs "extension.foo"]` with `clean`, `smudge`, `priority`. "This feature is considered experimental… It is possible for buggy extensions to leave your repository in a bad state, so don't rely on them with a production git repository without extensive testing." Extensions carry *hashes*, not free-form metadata, so `ext-` is the wrong vehicle for size/date/provenance — source: git-lfs/git-lfs, `docs/extensions.md`.
- A pass-through extension may omit its key entirely (LFS detects it because input and output oids match), and extensions "must have no side effects other than writing to their STDOUT" — source: git-lfs/git-lfs, `docs/extensions.md`.
- If a smudge extension is missing or fails, "LFS will ensure that the pointer file is written to both the index and working directory" — i.e. **LFS's own documented failure mode is to leave the pointer in the worktree**. That is precisely the virtual-file state, arrived at accidentally. Any keeper design must distinguish deliberate stubs from LFS smudge failures — source: git-lfs/git-lfs, `docs/extensions.md`.

#### git-LFS: the query surface

- `git lfs ls-files` marks materialization state *in-band*: "An asterisk (`*`) after the OID indicates a full object, a minus (`-`) indicates an LFS pointer." Options: `--long` (full 64-char OID), `--size` (size in parentheses), `--debug` ("Show as much information as possible… intended for manual inspection; the exact format may change at any time"), `--json` ("Intended for interoperation with external tools"), and `-I/--include` `-X/--exclude` path patterns — source: git-lfs/git-lfs, `docs/man/git-lfs-ls-files.adoc`.
- Design note: `--debug` is explicitly *unstable*; `--json` is the contract. A keeper equivalent should follow the same split — a pretty human view and a stable JSON view — rather than one format serving both.

#### git-annex: the reference split between immutable and mutable metadata

- Pointer file format: "A pointer file starts with `/annex/objects/`, which is followed by the key"; "The maximum size of a pointer file is 32 kb"; extra lines are permitted but "Every such subsequent line has to contain `/annex/` somewhere in it, and end in a newline." The stated rationale is corruption detection: "The possibility exists that a pointer file is in a working tree, representing an annex object that is not present, and something appends data onto it accidentally" — source: git-annex.branchable.com, `internals/pointer_file`, last edited 2022-02-23.
- That rationale is directly load-bearing for keeper: **a stub sitting in a worktree is a target for accidental appends**, and a format with a structural invariant on *every* line detects that, whereas the LFS pointer (whose invariant is only "< 1024 bytes, sorted keys") is weaker.
- `git annex whereis` reports location without network I/O: "this command does not contact remotes to verify if they still have the content of files. It only reports on the last information that was received from remotes." Supports `--json`, `--batch`, `--batch-keys`, and `--format` with variables `file, key, uuid, url, backend, bytesize, humansize, keyname, hashdirlower, hashdirmixed, mtime` — source: git-annex.branchable.com, `git-annex-whereis`.
- Joey Hess, on why last-verified timestamps are *not* recorded: "git-annex does not track the last time it verified content was on a remote and tracking that would bloat the git-annex branch. I don't think displaying a very old timestamp for data at rest would give the right impression though." — source: git-annex.branchable.com, `git-annex-whereis`, comment dated 2018-09-24. **This is the strongest available prior-art argument against putting `last_materialized` in versioned storage.**
- `git annex metadata` is a genuine key-value store: "any number of metadata fields… Each metadata field can in turn have any number of values", with `-s field=value`, `+=`, `?=`, `-=`, `-r`, tags via `-t`. Critically: "Each metadata field has its own `field-lastchanged` metadata, which contains the date the field was last changed. Unlike other metadata, this cannot be directly modified by this command. It is updated automatically." — source: git-annex.branchable.com, `git-annex-metadata`.
- And the scoping rule that keeper must copy or consciously reject: "the metadata is attached to git-annex key corresponding to the content of a file, not to a particular filename on a particular git branch. All files with the same key share the same metadata" — source: git-annex.branchable.com, `git-annex-metadata`. Content-addressed metadata means two identical 6 GB videos at different paths share one record; per-path eviction state therefore **cannot** be keyed by oid alone.
- `git annex info` is the aggregate surface: without arguments it shows "how much annexed data is present in the local repository, the total size of all annexed data in the working tree, the combined size of annexed data in all repositories"; `--fast` ("Only show the information that can be gathered quickly"), `--json`, `--bytes`, and `--show=name` to skip expensive computations. The documented example is exactly the materialization-planning question: `git annex info --fast . --not --in here` to see "how much disk space that will use" — source: git-annex.branchable.com, `git-annex-info`.

#### DVC: the sidecar-as-YAML model

- A `.dvc` file is YAML with root fields `outs` (required), `deps`, `wdir`, `md5`. Output entries carry `path` (required), `hash`, `md5`/`etag`/`checksum`, `version_id` ("Version ID native to the cloud provider"), `size`, `nfiles`, `isexec`, `cache`, `remote`, `persist`, `push` — source: dvc.org, `/doc/user-guide/project-structure/dvc-files`.
- Note what DVC records that LFS does not and keeper wants: `size` *and* `remote` ("Name of the remote to use for pushing/fetching") *and* `version_id`. That triple is the "where it really is" the owner asked for. It is stored in a *separate* file, not in the placeholder — the tracked data file's own path stays clean.
- DVC's `deps.repo` sub-schema (`url`, `rev`, `rev_lock`, `config`, `remote`) is the shape to copy if keeper ever needs provenance beyond one remote — source: dvc.org, `/doc/user-guide/project-structure/dvc-files`.

#### restic: content-addressed metadata with no per-file sidecar

- restic stores everything under storage IDs that are "the SHA-256 hash of the content stored in the repository"; a *Snapshot* is "the state of a file or directory… the content and metadata like the name and modification time". Trees are blobs; index JSON records `{id, type, offset, length, uncompressed_length}` per blob — source: restic/restic, `doc/design.rst`, GitHub `master`.
- Relevance: restic proves you can hold complete file metadata with **zero worktree footprint** — but only because restic never presents a browsable worktree. It is the counter-example, not a model, for a system whose whole point is that the user sees the file in `ls`.

#### OS-level carriers

**Linux extended attributes.** Namespaces are `security`, `system`, `trusted`, `user`. Only `user.*` is usable by an ordinary process: "User extended attributes may be assigned to files and directories for storing arbitrary additional information"; access is governed by the file's own permission bits. `trusted.*` attributes are "visible and accessible only to processes that have the `CAP_SYS_ADMIN` capability". VFS limits: 255-byte names, 64 kB values, 64 kB total name list. On ext2/3/4 "the total bytes used by the names and values of all of a file's extended attributes must fit in a single filesystem block (1024, 2048 or 4096 bytes)". Btrfs caps name+value+overhead at the nodesize (16 kB default). "user extended attributes are allowed only for regular files and directories." Some filesystems need the `user_xattr` mount option. And: "Extended attributes are not specified in POSIX.1" — source: man7.org, `xattr(7)`, Linux man-pages 6.18, dated 2026-02-08.

**xattr durability across copy tools — sourced, and the answer is "not durable by default":**

- `rsync`: xattrs are copied only with `--xattrs`/`-X`; the option summary reads "`--xattrs, -X` preserve extended attributes". Furthermore, as a non-super-user rsync "copies the `user.*` namespace" only, and "the `-X` option does not copy rsync's special xattr values (e.g. those used by `--fake-super`) unless you repeat the option (e.g. `-XX`)". `--fake-super` itself "store[s]/recover[s] privileged attrs using xattrs", which means rsync will *write into your xattr space* in some configurations — source: download.samba.org, `rsync(1)` manpage.
- `cp` (GNU coreutils): xattrs are preserved only via `--preserve=xattr` ("Preserve extended attributes of the file, or fail with full diagnostics") or `--preserve=all`. `-a`/`--archive` will "Try to preserve SELinux security context and extended attributes (xattr), but **ignore any failure to do that and print no corresponding diagnostic**" — i.e. `cp -a` can silently lose them. Bare `--preserve` with no list means only `mode,ownership,timestamps` — **no xattrs** — source: gnu.org, GNU Coreutils 9.11 manual, `cp invocation`.
- GNU `tar`: the attribute-handling chapter documents `--atime-preserve`, `--same-owner`, `--numeric-owner`, `-p/--same-permissions` — xattrs are **not** part of the default attribute set and require separate opt-in flags — source: gnu.org, GNU tar 1.35 manual, §8.2 "Handling File Attributes", generated 2023-08-23. `UNVERIFIED`: the precise behaviour of `tar --xattrs`/`--xattrs-include` was not retrieved (the manual's dedicated xattrs page 404s at the URL tried); treat "tar preserves xattrs only with explicit `--xattrs`" as high-confidence-but-unverified.
- `zip`/ZIP archives: `UNVERIFIED`. No primary source retrieved. Do not claim ZIP xattr behaviour without checking the APPNOTE/Info-ZIP docs.
- APFS/HFS+ → non-Apple filesystem: macOS converts xattrs into a companion **AppleDouble** file named `._<name>`: "macOS keeps a copy of file metadata in a separate area, known as Extended Attributes (xattr) on HFS+ or APFS. However, when writing to external media which is not formatted as HFS+ or APFS (thus not having the capability to store extended attributes), it will [write a `._` file]" — source: swiftforensics.com (Yogesh Khatri), "The ._ (dot-underscore) file format", 2018-11. Corroborated by Apple DTS: "If the file is called `foo`, the corresponding AppleDouble file [is] `._foo`" — source: developer.apple.com forums thread 657862. Both are secondary/forum sources: treat the *mechanism* as solid, exact field layout as `UNVERIFIED`.

**macOS xattrs specifically.** `xattr(1)`: "Extended attributes are arbitrary metadata stored with a file… The metadata is often a null-terminated UTF-8 string, but can also be arbitrary binary data." Attribute names are listable via `ls -l@`. Some attributes are fixed-length and enforced: "The `com.apple.FinderInfo` attribute must be 32 bytes in length" — source: `xattr(1)` man page, Mac OS X, dated 2010-11-29 (mirrored at keith.github.io/xcode-man-pages).

**Spotlight `kMDItem*`.** Apple documents a set of "Metadata attribute keys that are common to many file types" under Core Services → File Metadata → MDItem → Common Metadata Attribute Keys — source: developer.apple.com, `/documentation/coreservices/file_metadata/mditem/common_metadata_attribute_keys`. `UNVERIFIED`: the individual key list (including `kMDItemUserTags` and the `com.apple.metadata:_kMDItemUserTags` xattr that backs Finder tags) did not render in the retrieved page; the *existence of the key namespace* is verified, the specific Finder-tag xattr name is not. Do not design against it without re-verification.

**Windows alternate data streams.** "All files on an NTFS volume consist of at least one stream — the main stream"; the full name form is `<filename>:<stream name>:<stream type>`, the default data stream is `sample.txt::$DATA`, a named stream is `sample.txt:bar:$DATA`, and "Any legal characters for a file name are legal for the stream name (including spaces)." "These alternate data streams are not normally visible, but can be observed from a command line using the `/R` option of the `DIR` command" — source: Microsoft Learn, `[MS-FSCC]: NTFS Streams`, updated 2025-11-21. ADS is NTFS-only and is lost on any copy to a non-NTFS target; it is the Windows analogue of xattrs and inherits the same durability problem.

**`.DS_Store`.** `UNVERIFIED` — no primary Apple documentation retrieved. Note only that third-party tooling treats it as noise: DVC's own docs cite "`.DS_Store` on macOS" as the canonical example of a file you want a `.dvcignore` for — source: dvc.org, `/doc/user-guide/project-structure/dvcignore-files`. It is a per-directory Finder-state blob, not a per-file metadata carrier, and is unsuitable for keeper's purpose.

#### Carrier scorecard

| Carrier | Durable across copy? | Portable Linux+macOS+Win? | Cheap? | Holds oid/size/date? | Verdict |
|---|---|---|---|---|---|
| In-file pointer (LFS/annex/DVC style) | **Yes** — it is the bytes | **Yes** | Yes (<1 KB) | Yes, but mutable fields dirty git | **Use for immutable identity** |
| Sidecar index under `<git-dir>/` | Yes within the clone; not copied with the file | Yes | Yes, one file | Yes, freely mutable | **Use for eviction/access state** |
| `user.*` xattr | **No** — needs `-X`, `--preserve=xattr`; `cp -a` fails silently | Linux+macOS only; Windows needs ADS | Yes, but ext4 block-limited | Yes | Cache/hint only, never authority |
| NTFS ADS | No (non-NTFS targets) | Windows only | Yes | Yes | Not portable |
| AppleDouble `._name` | Accidental, and pollutes listings | macOS-originated only | Yes | Yes | Side-effect, not a design |
| Platform placeholder (CfAPI / File Provider) | N/A (OS-managed) | **No — absent on Linux server** | ~1 KB | Yes | Desktop-only enhancement |

### 2. Sidecar vs xattr vs in-file placeholder — the trade when the stub *is* the file

- **LFS**: the smudge filter's own algorithm is "Read 100 bytes. If the content is ASCII and matches the pointer file format… Otherwise, simply pass the STDIN out through STDOUT." A stub is therefore detectable cheaply and unambiguously from a 100-byte prefix — source: git-lfs/git-lfs, `docs/spec.md`. This is the single most useful property of the in-file design: **stub detection is O(100 bytes), not a database lookup.**
- **git-annex** offers *two* in-file forms — pointer file, or "a symbolic link pointing to a file in the `.git/annex/objects/` directory" — source: git-annex.branchable.com, `internals/pointer_file`. The symlink form makes `ls -l` honest about non-presence (dangling link) at the cost of breaking every app that follows links.
- **DVC** takes the opposite branch: the placeholder is a *separate* `.dvc` file and the data path may simply be absent — source: dvc.org, `/doc/user-guide/project-structure/dvc-files`. Consequence documented by DVC itself: ignoring a path makes it "non-existent for DVC", and "`dvc exp run` and `dvc repro` might remove ignored files. If they are not produced by a pipeline stage, they can be lost permanently" — source: dvc.org, `/doc/user-guide/project-structure/dvcignore-files`. **A pattern file that governs data lifecycle is a data-loss surface.** Given keeper's "above all simple and safe (no data loss)" constraint, this is the sharpest warning in the whole corpus.
- **macOS `.icloud` placeholders**: when Optimize Mac Storage evicts a file, the contents are removed and "replaced with an `.iCloud` placeholder", formatted as a property list "that holds key details about the file, such as its storage location and sync status", containing `bplist00`, `NSURLFileSizeKey`, `NSURLNameKey`, `NSURLFileResourceTypeKey`, averaging ~170 bytes (range 160–190) — sources: macfilos.com, "iCloud Drive: The danger with Optimised Storage file placeholders", 2017-06/2019-02; filext.com, "ICLOUD File Extension". **`UNVERIFIED` on the `.<name>.icloud` leading-dot naming convention** — the retrieved sources confirm the `.icloud` extension and plist payload but I could not confirm the leading-dot-prefixed form from a primary Apple source. The named risk in the primary write-up is exactly keeper's risk: a *second* sync tool (Dropbox, in that account) saw the 170-byte placeholders and replicated *those* as if they were the user's files.
- Apple's supported programmatic surface for the same state is `NSMetadataUbiquitousItemDownloadingStatusKey`: "The value is a string constant that indicates the download status of the item" (macOS 10.9+) — source: developer.apple.com, `/documentation/foundation/nsmetadataubiquitousitemdownloadingstatuskey`.

**Trade-offs when the stub IS the file, each with a sourced consequence:**

1. *Apps get garbage.* Mitigated on Windows/macOS by kernel-level hydration (CfAPI: "Whether you use file system APIs, the Command Prompt, or a desktop or a UWP app to access a placeholder file, the file will hydrate without additional code changes" — Microsoft Learn, `build-a-cloud-file-sync-engine`, ms.date 2025-05-12). **On a Linux server with no such layer, there is no mitigation** — the app reads the pointer text.
2. *`du` lies.* LFS's answer is to make the true size queryable out-of-band: `git lfs ls-files --size` — source: `git-lfs-ls-files.adoc`. git-annex's answer is `info`'s "total size of all annexed data in the working tree" vs "how much annexed data is present in the local repository" as *two separate numbers* — source: `git-annex-info`. **Keeper should report both numbers too; a single "size" is always a lie in one direction.**
3. *Git sees the stub as content.* This is by construction for LFS — the pointer *is* the committed blob. The corollary is that a keeper-added metadata key changes the blob OID ("there is exactly one valid encoding") and would show as a diff on every machine. **Therefore: no mutable metadata in the pointer.**
4. *Second sync tools replicate stubs.* Documented failure in the iCloud case above.
5. *Accidental append corrupts silently.* git-annex explicitly engineered against this (`/annex/` on every line, 32 kB cap); LFS's 1024-byte cap gives partial protection. **Prefer validating a stub's whole structure, not just its prefix, before treating it as authoritative.**

### 3. Pattern-file design

#### `.gitignore` semantics (the thing to copy)

Source for all of the following: git-scm.com, `gitignore(5)`, "last updated in 2.55.0", version dated 2026-06-29.

- **Precedence, highest → lowest**: command-line patterns; `.gitignore` in the same directory as the path or any parent up to the worktree top ("patterns in the higher level files being overridden by those in lower level files"); `$GIT_COMMON_DIR/info/exclude`; `core.excludesFile`. And the rule that catches everyone: **"within one level of precedence, the last matching pattern decides the outcome"** — order-dependence is per-file, not global.
- Blank line matches nothing; `#` starts a comment (escape with `\#`); "Trailing spaces are ignored unless they are quoted with backslash".
- Negation `!` re-includes, **with a hard limit**: "It is not possible to re-include a file if a parent directory of that file is excluded. Git doesn't list excluded directories for performance reasons, so any patterns on contained files have no effect, no matter where they are defined." This is the #1 source of "my rule doesn't work" reports and keeper must either replicate it or diverge *loudly*.
- Anchoring: "If there is a separator at the beginning or middle (or both) of the pattern, then the pattern is relative to the directory level of the particular `.gitignore` file itself. Otherwise the pattern may also match at any level below". Patterns from outside the worktree (`info/exclude`, `core.excludesFile`) "are treated as if they are specified at the root of the working tree".
- Trailing `/` restricts to directories. `*` and `?` do not match `/` (fnmatch `FNM_PATHNAME`). `**` has exactly three special forms: leading `**/` = any directory; trailing `/**` = everything inside; `/**/` = zero or more directories. "Other consecutive asterisks are considered regular asterisks."
- "a backslash at the end of a pattern is an invalid pattern that never matches."
- The canonical exclude-all-but-one idiom requires four lines and the `/foo/*` step: `/*`, `!/foo`, `/foo/*`, `!/foo/bar`. **If keeper's policy file is "deny by default, allow specific trees", users will hit this immediately.**

#### `.gitattributes` semantics (the alternative model)

Source for all of the following: git-scm.com, `gitattributes(5)`, "last updated in 2.55.0".

- Line form: `pattern attr1 attr2 ...`. Four states per path: **Set** (bare name), **Unset** (`-name`), **Set to a value** (`name=value`), **Unspecified** (no pattern matched). The Unset-vs-Unspecified distinction is real and is the reason attributes can express "explicitly not this" — something `.gitignore` can only approximate with `!`.
- "When more than one pattern matches the path, a later line overrides an earlier line. **This overriding is done per attribute.**"
- Same matching rules as `.gitignore` **with two exceptions**: "negative patterns are forbidden" and "patterns that match a directory do not recursively match paths inside that directory (so using the trailing-slash `path/` syntax is pointless in an attributes file; use `path/**` instead)".
- Precedence is **inverted** relative to gitignore: `$GIT_DIR/info/attributes` has the *highest* precedence, then `.gitattributes` nearest the path, outward to the worktree top, then global/system files lowest.
- Index fallback: "When the `.gitattributes` file is missing from the work tree, the path in the index is used as a fall-back. During checkout process, `.gitattributes` in the index is used and then the file in the working tree is used as a fall-back." **This matters for keeper**: a policy file expressed as attributes still works during checkout, when the worktree does not yet exist.
- **Macro attributes**: "you can define an attribute that, when set, also sets or unsets a number of other attributes at the same time." The built-in `binary` macro is literally `[attr]binary -diff -merge -text`. Constraint: "Custom macro attributes can be defined **only in top-level gitattributes files** (`$GIT_DIR/info/attributes`, the `.gitattributes` file at the top level of the working tree, or the global or system-wide gitattributes files), not in `.gitattributes` files in working tree subdirectories." And "macro attributes can only be 'Set'".
- **Recommendation for keeper**: gitignore semantics for the *policy file* (simple, familiar, order-dependent-in-a-way-users-expect), and reuse of `.gitattributes` only where keeper must interoperate with `filter=lfs` lines it already owns. Do not build a third precedence model.

#### Tools that reuse these semantics

- **`.dvcignore`**: "similar to `.gitignore` in Git"; "Populate it with `.gitignore` patterns" (linking git-scm.com/docs/gitignore); "Each line should contain only one pattern"; can be placed "in the root of the project, or in any subdirectory"; and DVC ships `dvc check-ignore` as the debugging tool. Notably DVC *forbids* nesting inside a tracked directory: "If DVC finds a `.dvcignore` file inside a dependency or output directory, it raises an error" — source: dvc.org, `/doc/user-guide/project-structure/dvcignore-files`. **The `check-ignore`-equivalent command is not optional; ship `keeper check-policy <path>` from day one.**
- **`.dockerignore`**: "You can use `.dockerignore` file to exclude files and directories from the build context" — source: docs.docker.com, Dockerfile reference, §`.dockerignore file`, cross-referencing docs.docker.com `/build/concepts/context/`. Docker's variant is *not* byte-identical to gitignore (it is Go `filepath.Match`-derived); `UNVERIFIED` on the exact divergences — I did not retrieve the section enumerating them.
- **`.rgignore`**: `UNVERIFIED` — the ripgrep guide was not retrieved. What *is* verified is the implementing crate; see below.
- **`annex.largefiles`**: a real boolean expression language. "`largerthan=100kb and not (include=*.c or include=*.h)`". Terms: `include=glob`/`exclude=glob` ("this matches on the whole filename, relative to the top of the git directory. So, `include=foo` will include a file `foo` in the top, but not `subdir/foo`. To include both, use `include=foo or include=*/foo`"), `smallerthan=`/`largerthan=` ("The size can be specified with any commonly used units, for example, '0.5 gb' or '100 KiloBytes'"), `mimetype=glob`, `mimeencoding=glob`, `anything`, `nothing`, `not`, `and`, `or`, `( )` — source: git-annex.branchable.com, `git-annex-matching-expression`, last edited 2024-12-19.
- Configuration precedence for `annex.largefiles`, three layers: `git config` (local clone) > `.gitattributes` > `git annex config` (all clones). Stated as: "Any `.gitattributes` setting overrides the `git annex config` setting, but will be overridden by the `git config` setting" — source: git-annex.branchable.com, `tips/largefiles`. Confirmed in a maintainer comment: "if `annex.largefiles` is set in git config (including global git config), it overrides the `.gitattributes` setting" (joey, 2017-03-20).
- And the anti-pattern warning, from the same page: because "git attribute values cannot contain whitespace", the expression must be mangled to `* annex.largefiles=(largerthan=100kb)and(not((include=*.c)or(include=*.h)))`, and "It's generally a better idea to use `git annex config` instead" / "using .gitattributes for this is not recommended" — source: git-annex.branchable.com, `tips/largefiles`.
- **rclone filter files**: glob-style, not gitignore-style — `*` (non-separator), `**` (including separators), `?`, `[…]` classes, `{a,b}` alternates, `{{regexp}}` for re2. Anchoring: "If the filter pattern starts with a `/` then it only matches at the top level of the directory tree, relative to the root of the remote… If it does not start with `/` then it is matched starting at the end of the path/file name but it only matches a complete path element." Ordering: "**At first match to a rule the path/file name is included or excluded and no further filter rules are processed for that path/file**" — the exact opposite of gitignore's last-match-wins. "If rclone does not find a match, after testing against all rules… the path/file name is included." `--include` implies a trailing `- **`. "Within `--include-from`, `--exclude-from` and `--filter-from` flags rules are processed from top to bottom of the referenced file." And the usability warning: "**Important** Avoid mixing any two of `--include...`, `--exclude...` or `--filter...` flags in an rclone command. The results might not be what you expect" — source: rclone.org, `/filtering/`, added in v1.22, author Nick Craig-Wood.
- **First-match-wins vs last-match-wins is the single most consequential choice in this file format.** rclone's own documentation has to warn users about rule interaction; gitignore's is the model users already have in their fingers from git. For a git-native tool, **last-match-wins (gitignore) is the correct choice**, and mixing the two conventions in one product would be indefensible.

### 4. Size and content-type policy expressions

- **git-annex**: `largerthan=size` / `smallerthan=size`, units "any commonly used units, for example, '0.5 gb' or '100 KiloBytes'" — source: `git-annex-matching-expression`.
- **git-LFS**: `git lfs migrate import --above=<size>`, "Only migrate files whose individual filesize is above the given size. `size` may be specified as a number of bytes, or a number followed by a storage unit, e.g., '1b', '20 MB', '3 TiB'". Same flag on `migrate info`. **Crucially: "This option cannot be used with the `--include`, `--exclude`, and `--fixup` options."** — source: git-lfs/git-lfs, `docs/man/git-lfs-migrate.adoc`.
- That mutual exclusion is a deliberate design decision by the LFS maintainers, and it is the strongest available evidence for the pitfall keeper must plan around: **LFS refuses to define the interaction between a size threshold and a path pattern.** It picks one or the other per invocation.
- **rclone**: `--min-size` / `--max-size`, both `SizeSuffix`-typed. `SizeSuffix` semantics: "specified as an integer value, which will then be assumed to represent a KiB value (multiples of 1024 bytes) by default. The interpretation can be changed by appending a suffix: `B` for Byte, `K` for KiB, `M` for MiB, `G` for GiB, `T` for TiB and `P` for PiB." Note the trap: a bare integer means **KiB**, not bytes. rclone also lists `--min-size`/`--max-size` among the flags that `--files-from` overrides — source: rclone.org, `/docs/` and `/filtering/`.
- **Pitfalls, each sourced:**
  1. *Bare-number units are a footgun.* rclone: bare integer = KiB. LFS: `--above=1b` is explicitly one byte. git-annex accepts "0.5 gb". Three tools, three conventions. **Keeper must require an explicit unit suffix and reject bare integers** — the alternative is a rule that evicts 1024× more or less than intended.
  2. *Content-type predicates are undecidable on non-local content.* git-annex on `mimetype=`/`mimeencoding=`: "This only matches when the content of the file is present in the local repository. Usually that is the case, but eg, when importing from a special remote with `--no-content`, the content is usually not present." It is also build-gated: "only available to use when git-annex was built with the MagicMime build flag" — source: `git-annex-matching-expression`. For keeper, "content not present" is the *normal* state, so any mimetype term must fall back to extension-matching or be rejected at parse time.
  3. *Size and pattern rules compose non-obviously.* git-annex composes them with explicit boolean operators and parentheses precisely because implicit composition is ambiguous. LFS sidesteps by forbidding the combination. **A design that says "patterns select candidates, thresholds filter candidates" (AND, in that fixed order) is unambiguous and does not need a parser.**
  4. *`include=` glob anchoring is a documented trap.* git-annex: `include=foo` matches top-level `foo` but not `subdir/foo`; you must write `include=foo or include=*/foo`. gitignore's rule is the opposite (an unanchored pattern "may also match at any level below"). Users coming from `.gitignore` will get this wrong in an annex-style language — another reason to use gitignore semantics rather than invent.
  5. *Directory-level short-circuiting silently voids file-level rules.* gitignore: "Git doesn't list excluded directories for performance reasons, so any patterns on contained files have no effect." rclone documents its own directory-filter optimization being disabled by regexp rules ("using any regular expression filter will prevent rclone from using directory filter rules"). A fast implementation *will* prune directories; keeper must document that pruning as semantics, not as an optimization.

### 5. UX conventions for "online-only" in file managers

- **Windows / Cloud Filter API (the fully-worked reference design).** Introduced Windows 10 v1709. "Sync engines can create placeholder files that consume only 1 KB of storage for the filesystem header, and that automatically hydrate into full files under normal use conditions." Three states: **Placeholder file** ("An empty representation of the file and only available if the sync service is available"), **Full file** ("hydrated implicitly and could be dehydrated by the system if space is needed"), **Pinned full file** ("hydrated explicitly by the user through File Explorer and is guaranteed to be available offline"). Shell integration: "The cloud files API provides standardized, automatic hydration state icons shown in File Explorer and on the Windows desktop" and "**Replaces legacy icon overlay Shell extensions**" — the old overlay-handler mechanism is explicitly superseded. Placeholders can carry "rich service-provided thumbnails and extended file metadata". Hydration policy is `max(app hydration policy, provider hydration policy)`, resolved at open time and immutable thereafter; policies ordered "Always full > Full > Progressive > Partial", default progressive. Implementation: minifilter `cldflt.sys`, placeholders built on **reparse points**, NTFS-only; and because "many existing applications hit errors when encountering any reparse point", "the cloud files API always hides its reparse points from all applications except for sync engines and processes whose main image resides under `%systemroot%`" — source: Microsoft Learn, `Build a Cloud Sync Engine that Supports Placeholder Files`, ms.date 2025-05-12.
- **OneDrive's user-visible vocabulary** (the thing users already know): **blue cloud outline** = "the file is only available online. Online-only files don't take up space on your computer. You can't open online-only files when your device isn't connected to the Internet." **Green circle with a tick** = "When you open an online-only file, it downloads to your device and becomes a locally available file… If you need more space, you can change the file back to online only. Just right-click the file and select 'Free up space.'" Plus per-state icons for syncing (circular arrows), error (red circle/white cross), paused, blocked-file (gray circle with flat bar) — source: Microsoft Support, "What do the OneDrive icons mean?", ms.date 2026-06-16.
- **"Free up space" is the exact user-facing name for keeper's *release* operation, and "online-only" for the stub state.** Reusing this vocabulary costs nothing and removes an entire class of explanation.
- **macOS / File Provider.** Item presentation is driven by `NSFileProviderFileSystemFlags` — "Flags that define an item's on-disk properties and its appearance in the user interface. The flags define the on-disk properties of the item. The system modifies the item's appearance based on these flags" (`userReadable`, `userWritable`, `userExecutable`, `hidden`, `pathExtensionHidden`; macOS 11.0+) — source: developer.apple.com, `/documentation/fileprovider/nsfileproviderfilesystemflags`. Download state for ubiquitous items is surfaced via `NSMetadataUbiquitousItemDownloadingStatusKey` (macOS 10.9+) — source: developer.apple.com. **`UNVERIFIED`**: the specific API that drives the Finder *cloud/download glyph* (materialized-set / `NSFileProviderItemCapabilities` / dataless-file `SF_DATALESS` flag) was not retrieved; do not scope Tauri work against a named symbol here without re-verification.
- **Nextcloud**: `UNVERIFIED` — every candidate documentation URL tried returned 404 (`docs.nextcloud.com/desktop/latest/navigating.html`, `/desktop/3.13/`, `/desktop/3.15/`, `/desktop/latest/`). No claim about Nextcloud's virtual-files implementation is made here. It should be re-researched before being cited in a design doc.
- **Linux**: there is no equivalent platform layer, and none of the retrieved sources describes one. The `cldflt.sys`/File Provider pattern has no counterpart a daemon can register with; a FUSE mount is the only architecture that reproduces the semantics, and it was out of scope for this digest.

## Applicability to a git-LFS-backed virtual-file design

1. **Two-store metadata split, mirroring git-annex.** Immutable identity (`oid`, `size`) is already in the LFS pointer and is free. Mutable state (`materialized_at`, `last_accessed_at`, `pinned`, `remote`) goes in an untracked local index under the git dir, alongside where LFS already keeps `lfs/objects`. Rationale: pointers have exactly one valid encoding, so mutating one is a git-visible content change; and git-annex's maintainer rejected timestamp-in-branch for bloat.
2. **The stub should be the LFS pointer itself, unmodified.** It is already the on-disk artifact for a non-smudged LFS file; it is detectable from 100 bytes; it survives copies. Adding `keeper-*` keys is spec-legal ("MUST preserve keys that they don't know or care about") but costs pointer-byte budget (<1024 total), changes blob OIDs, and buys nothing that the local index cannot hold. **Recommend: no custom pointer keys.**
3. **Distinguish deliberate stub from failed smudge.** LFS's own documented error path leaves a pointer in the worktree. The local index is what separates "keeper evicted this on purpose" from "the smudge filter broke" — a distinction that a pure in-file design cannot make, and that is directly load-bearing for the no-data-loss requirement.
4. **xattrs, if used at all, are a cache.** A `user.keeper.state` xattr can make `ls`-time queries cheap on Linux, but must be treated as reconstructible-from-index, because `cp -a` drops it silently, `rsync` needs `-X`, and non-`user.*` namespaces need `CAP_SYS_ADMIN`.
5. **Report two sizes, always.** `git annex info` and `git lfs ls-files --size` both exist because the on-disk size of a stubbed tree is meaningless. Keeper needs "logical size" and "materialized size" as distinct numbers in every status surface.
6. **Policy file: gitignore semantics, `ignore` or `gix-glob` crate, plus a `check-policy` command.** Last-match-wins, per-directory stacking, `!` negation with the documented parent-directory limitation, `**` with git's three special forms. DVC shipped `dvc check-ignore` and git ships `git check-ignore` because these semantics are not predictable by inspection.
7. **Thresholds as separate scalar keys, ANDed after pattern selection, units mandatory.** Not a boolean expression language. LFS refuses to combine `--above` with `--include`; annex needs full parenthesised boolean syntax to do so safely; rclone's bare-integer-means-KiB is a live footgun. A fixed composition order is simpler, safer, and expressible in a config schema.
8. **Reject or extension-approximate any content-type predicate.** It is undecidable on the stubbed steady state, by git-annex's own documentation.
9. **Desktop presentation is a separate, later, platform-specific story.** CfAPI (Windows) and File Provider (macOS) both require registered sync roots and desktop hosts. The server surface is `keeper ls --json` in the shape of `git lfs ls-files --json` / `git annex whereis --json`. Borrow OneDrive's words — "online-only", "free up space", "always keep on this device" — for whatever UI does appear.

## Risks / failure modes

- **Second sync tool replicates stubs as real files.** Documented in the wild for iCloud + Dropbox: 170-byte `.icloud` placeholders were backed up as if they were the user's documents. Any keeper stub in a directory also watched by another sync engine has this failure mode. Mitigation: make stubs recognisable (LFS pointers already are) and document the interaction.
- **Pattern file becomes a data-loss surface.** DVC's own docs: ignored files "can be lost permanently" under `repro`/`exp run`, and "when you add `.dvcignore` patterns that affect an existing output, its status will change and DVC will behave as if the affected files were deleted." A keeper policy file that governs eviction has the same shape. Mitigation: never let a policy edit trigger destructive action without an explicit, separate command; treat "policy changed" as "re-plan", never "re-apply".
- **Silent xattr loss.** `cp -a` "ignore[s] any failure to [preserve xattrs] and print[s] no corresponding diagnostic". If any keeper state is xattr-only, a routine `cp -a` produces an unlabelled stub.
- **Accidental append to a stub.** git-annex engineered a whole-file structural invariant against exactly this. An LFS pointer with junk appended exceeds 1024 bytes and becomes invalid — detectable, but the failure is late.
- **Negation-under-excluded-directory.** Users will write `!important/big.mov` under an excluded parent and it will silently do nothing, per gitignore(5). This will be reported as a keeper bug.
- **Unit ambiguity.** `min_size: 100` means 100 KiB in rclone, would mean 100 bytes to a naive reader. A 1024× eviction error is a plausible first-week incident.
- **Pointer-size budget.** 1024 bytes total including extension lines. A design that starts adding keys has a hard ceiling and no graceful degradation.
- **Content-addressed vs path-addressed metadata.** git-annex shares metadata across all files with the same key. Two identical large files at different paths must be able to have independent materialization state; keying the local index on oid alone is wrong.
- **CfAPI is NTFS-only and reparse-point-based**, and reparse points are hidden from most applications for compatibility reasons. Any Windows ambition inherits both constraints.
