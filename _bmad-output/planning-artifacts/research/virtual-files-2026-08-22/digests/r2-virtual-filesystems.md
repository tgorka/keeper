# OS-level virtual / placeholder file technologies: a source-verified survey
_agent: R2VirtualFs · accessed: 2026-08-22_

## Verdict (decision-grade)

- **There is no cross-platform way to make a not-yet-downloaded file appear inside an *ordinary directory* (e.g. a git worktree) and materialize on access.** Every OS mechanism that produces true placeholder semantics either (a) confines the files to a system-chosen location (macOS File Provider → `~/Library/CloudStorage/…`), (b) requires a mount (FUSE/NFS/autofs/ProjFS/cfapi sync-root), or (c) requires kernel-version-gated privileged daemons (Linux `fanotify` pre-content). Only Linux `fanotify` HSM can decorate arbitrary in-place paths — and it needs `CAP_SYS_ADMIN`-class privilege, kernel ≥ 6.14, and still has unresolved deadlock/`mmap` caveats.
- **macOS is the hard constraint, and it is decisive.** `NSFileProviderReplicatedExtension` gives exactly the desired model — dataless items, `fetchContents` on access, `evictItem` to release — but the domain's storage is exposed under `~/Library/CloudStorage/<Provider>-<Domain>`; it is *not* a way to virtualize an arbitrary path such as a user's git checkout. `SF_DATALESS` is an internal APFS flag that user space **may not set** (`chflags(2)`: "internal flags and may not be set or unset from user space"). So a third party cannot mark its own files dataless outside the File Provider machinery.
- **macFUSE is licence-disqualifying for a shipped product**, and this is explicit, not inferred: LICENSE.txt clause 4 forbids redistribution of binaries "bundled with commercial software … including the automated download or installation" without written permission; and the kext itself is closed-source. `fuse-t` is "Free for personal use" with a paid commercial licence. Neither is compatible with a permissive-only OSS licence firewall. On Apple silicon macFUSE additionally requires the user to enable third-party kexts (Reduced Security + reboot), and Apple states kexts "are no longer recommended".
- **The pragmatic architecture for a small OSS Rust project is a two-tier one:** (1) a *portable, privilege-free* pointer/stub representation that lives directly in the worktree and is understood by the tool itself (git-LFS pointer text is already exactly this: ≤1024 bytes, `version`/`oid`/`size`), plus a metadata sidecar (xattrs) — this works identically on Linux server, macOS and Windows and never risks data loss; and (2) an *optional*, opt-in **FUSE mount on Linux** (`fuser`, MIT) for the "looks real in `ls`" experience on the primary server environment. Treat true system-level placeholders on macOS as a separate, later, Apple-Developer-Program-gated deliverable.
- **The `git status` question kills most "present but empty" tricks.** A sparse/truncated stub is a *different file content* than the checked-out blob, so git reports the path as modified unless the tool owns the filter/index. git-LFS already solves this by owning `filter.lfs.process`: the pointer *is* the committed content, so a worktree containing pointers is clean by construction. Any virtual-file design that keeps the LFS pointer in place is safe with `git status`; any design that writes a fake-sized zero file is not.
- **Eviction is the easy half; safe eviction is the hard half.** Apple's own API is the reference semantics to copy: refuse to evict when there are unsynced local edits (`NSFileProviderError.unsyncedEdits`), refuse when file descriptors are open (`EBUSY`), refuse pinned items, and recurse deterministically. A nightly 24h-idle release job should implement the same four refusals.
- **Every candidate degrades badly when the backing store is unreachable, and the degradations differ.** Placeholder systems block the calling syscall (macOS pauses the syscall; Windows cfapi shows hydration progress/toast); mount-based systems return `EIO`/hang; a pointer-file design simply leaves a readable pointer and fails loudly at an explicit `materialize` command. For "above all simple and safe", the pointer design has by far the best failure mode.

## Findings

### macOS — `NSFileProviderReplicatedExtension` is the only sanctioned placeholder API

- The replicated File Provider extension is available macOS 11.0+; the system owns the local replica and the extension only syncs — "the system takes responsibility for monitoring and managing the local copies of your documents" — source: Apple Developer, https://developer.apple.com/documentation/fileprovider/nsfileproviderreplicatedextension, published unknown (accessed 2026-08-22).
- On-access materialization is a real syscall-blocking hook: "When the kernel detects a read access to a dataless file, that syscall is paused while your extension is called to fetch the contents of the file… Reads trigger downloads, and files lose their dataless property before the reads are allowed to resume." — source: Apple, WWDC21 session 10182 "Sync files to the cloud with FileProvider on macOS", https://developer.apple.com/videos/play/wwdc2021/10182/, published 2021.
- The download callback is `fetchContents(for:version:request:completionHandler:)` — "Tells the file provider to download the requested item from remote storage." — source: Apple Developer, https://developer.apple.com/documentation/fileprovider/nsfileproviderreplicatedextension/fetchcontents(for:version:request:completionhandler:), published unknown.
- Eviction API, verbatim signature: `func evictItem(identifier itemIdentifier: NSFileProviderItemIdentifier, completionHandler: @escaping @Sendable ((any Error)?) -> Void)`, availability macOS 11.0+/iOS 16.0+. "Calling this method turns a materialized item into a dataless item to free up disk space." Failure modes are enumerated: `unsyncedEdits` if the item had nonuploaded changes; `nonEvictable` if the user marked it nonevictable; `EBUSY` if the item has open file descriptors; `EMLINK` for too many hardlinks; `nonEvictableChildren` aborts a recursive directory eviction. Directory eviction recurses and finally makes the directory itself dataless, re-enumerating on next access. — source: Apple Developer, https://developer.apple.com/documentation/fileprovider/nsfileprovidermanager/evictitem(identifier:completionhandler:), published unknown.
- Declarative eviction exists from macOS 13 via `NSFileProviderItem.contentPolicy`: `.downloadLazilyAndEvictOnRemoteUpdate` evicts when you bump `contentVersion`; `.downloadEagerlyAndKeepDownloaded` makes the item non-evictable. Apple's own engineer notes "There is no guarantee, it could fail for various reasons, but that is what the system will try to do", and pre-13 you call `evictItemWithIdentifier:` imperatively. — source: Apple Developer Forums thread 712371 ("FileProvider needs to invalidate materialised items"), https://forums.developer.apple.com/forums/thread/712371, published unknown; and thread 739295 ("FileProvider's eviction is failing with resource busy error"), https://developer.apple.com/forums/thread/739295.
- **Where the files appear — the decisive constraint.** "All cloud-storage services must now store their files in `~/Library/CloudStorage`." — source: TidBITS, "Apple's File Provider Forces Mac Cloud Storage Changes", https://tidbits.com/2023/03/10/apples-file-provider-forces-mac-cloud-storage-changes/, published 2023-03-13. Corroborated by an implementer: "Your new File Provider domain should also be accessible under `~/Library/CloudStorage/`… via a path like `~/Library/CloudStorage/YourApp-YourDomainDisplayName`. Accessing these locations will trigger macOS to launch your File Provider Extension process" — source: Claudio Cambra, "Build your own cloud sync on iOS and macOS using Apple FileProvider APIs", https://claudiocambra.com/posts/build-file-provider-sync/, published 2025-05-01.
  - The API does expose `NSFileProviderDomain.init(displayName:userInfo:volumeURL:)` and a `volumeUUID` property, and `pathRelativeToDocumentStorage` is documented as "The path of the domain's subdirectory relative to the file provider's shared container" — i.e. relative to an app-group container, still not an arbitrary user path. — source: Apple Developer, https://developer.apple.com/documentation/fileprovider/nsfileproviderdomain, published unknown.
  - **Conclusion:** a File Provider domain cannot present virtual files inside an ordinary git worktree at a path the user chose. `[INFERENCE]` from the two sources above plus the absence of any documented arbitrary-path API.

### macOS — dataless files, `SF_DATALESS`, and why you cannot roll your own

- Definition and materialization policy, primary: "A file that contains only metadata is known as a *dataless* file… when a person taps the same file, or an app accesses it, the system redownloads the file's content — a process known as materialization." — source: Apple Developer, TN3150 "Getting ready for dataless files", https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files, first published 2023-05-09.
- Detection is via `stat`: `if ((fileStat.st_flags & SF_DATALESS) > 0)`. Apple warns "`stat` and `getattrlist` both trigger the materialization of any intermediate folders in the file's path, if they themselves are dataless." A process/thread can opt out: `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_THREAD, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)`, after which accesses return `EDEADLK`. — source: TN3150, ibid.
- **You cannot set the flag yourself:** "SF_DATALESS — The file is a dataless placeholder… The 'SF_DATALESS' and 'UF_COMPRESSED' flags are internal flags and may not be set or unset from user space. Attempting to modify them using `chflags()` will result in undefined behaviour." — source: Apple `chflags(2)` man page (macOS 26 rendering), https://keith.github.io/xcode-man-pages/chflags.2.html, accessed 2026-08-22. Flag value `#define SF_DATALESS 0x40000000 /* file is dataless object */` — source: apple/darwin-xnu, `bsd/sys/stat.h`, https://github.com/apple/darwin-xnu/blob/main/bsd/sys/stat.h.
- The materialization is implemented in APFS itself: Apple's own Instruments trace shows `apfs_materialize_dataless_file_ext` under `getattrlistbulk`. Directory enumeration and `fileExists(atPath:)` are called out as materialization triggers, with watchdog terminations as a documented symptom. — source: TN3150, ibid.
- Real-world hazard for developer tooling: FileProvider-backed paths deadlock or fail for tools that do not use `NSFileCoordinator` — "This on-demand materialization appears to deadlock or fail within the bridge's process context." — source: anthropics/claude-code issue #40783, https://github.com/anthropics/claude-code/issues/40783, published 2026-03-30. Directly relevant: a virtual-file scheme that a build tool or `git` walks will hit this class of bug.
- Tooling: `fileproviderctl evict "path/to/myFile.txt" --namespace` is used by developers to inspect/force eviction and to read back the item's `contentPolicy`. — source: Apple Developer Forums thread 741529, https://developer.apple.com/forums/thread/741529, published unknown. `[UNVERIFIED]` — no Apple primary man page for `fileproviderctl` or `brctl` was located; both appear undocumented/unsupported.

### macOS — entitlements, signing and distribution

- `com.apple.developer.fileprovider.testing-mode` (macOS 11.3+) is required only to set `NSFileProviderDomain.testingModes`, and Apple states: "You can only use this entitlement during testing and development. If you add it to your app or extension, you must remove it before you submit your app to TestFlight or the Mac App Store." — source: Apple Developer, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.fileprovider.testing-mode, published unknown.
- `[UNVERIFIED]` Whether shipping a File Provider extension requires paid Apple Developer Program membership: no primary Apple source located stating this explicitly. What *is* verified is that File Provider extensions ship as app extensions inside a signed host app, and Apple's guidance for system extensions generally is to distribute signed/notarized. Treat "needs a $99/yr team + Developer ID signing + notarization" as the working assumption, but do not cite it as sourced.
- Kernel extensions are a dead end by Apple policy: "Important: Kexts are no longer recommended for macOS. Kexts risk the integrity and reliability of the operating system." and on macOS 11+ third-party kexts "can't be loaded into the kernel on demand. They require the user's approval and restarting" plus Reduced Security on Apple silicon. — source: Apple Support, "System extensions in macOS", https://support.apple.com/guide/deployment/system-extensions-in-macos-depa5fb8376f/web, published 2021-10-27.

### macOS — FSKit (macOS 15.4+)

- "With FSKit, you can extend macOS by enabling access to new types of file systems. You do this by developing an FSKit module (`FSModule`), which you deliver as an app extension that runs in user space, and is compatible with Mac App Store distribution." Availability is stated as **macOS 15.4+** (not 15.0). — source: Apple Developer, https://developer.apple.com/documentation/fskit, published unknown.
- "Note: The current version of FSKit supports only `FSUnaryFileSystem`." Two design flows exist (`FSFileSystem`, `FSUnaryFileSystem`); resources include `FSBlockDeviceResource`, `FSPathURLResource` ("a path in the system file space"), `FSGenericURLResource`. There is an official sample "Building a passthrough file system — Expose an existing path as its own file system". — source: Apple Developer FSKit, ibid.
- Entitlement verified: `com.apple.developer.fskit.fsmodule` — "An entitlement that indicates an extension provides an FSKit filesystem", availability macOS 15.4+. A second entitlement `com.apple.developer.fskit.mount` exists. — source: Apple Developer, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.fskit.fsmodule, published unknown.
- Third parties *can* ship it (App Store-compatible, per Apple's own text). But FSKit gives you a **mounted volume**, not in-place placeholders — same topological problem as FUSE, with the added constraints of Swift/Obj-C app-extension packaging. Notably, fuse-t now lists "native FSKit on macOS 26 and later" as a backend. — source: fuse-t.org, https://www.fuse-t.org/, accessed 2026-08-22.

### macOS — escape hatches: macFUSE, fuse-t, NFS/SMB loopback

- **macFUSE licence — decisive.** Clause 4 of the macFUSE licence: "Redistributions in binary form, bundled with commercial software, are not allowed without specific prior written permission. This includes the automated download or installation or both of the binary form in the context of commercial software." — source: macfuse/macfuse `LICENSE.txt`, https://raw.githubusercontent.com/macfuse/macfuse/master/LICENSE.txt, Copyright (c) 2011-2026 Benjamin Fleischer, accessed 2026-08-22. It is therefore **not** a plain BSD-3 dependency, and a cargo-deny permissive-only firewall should reject it.
- macFUSE is also only partly open: "This repository contains the source code of libfuse.dylib and macFUSE.framework. The other components, e.g. the macFUSE kernel extension, are closed-source." Last fully open release was 3.8.3 (macOS 10.5–10.14.4). Current macFUSE supports macOS 12–27. — source: macfuse/macfuse README, https://github.com/macfuse/macfuse, accessed 2026-08-22.
- macFUSE on Apple silicon requires the user to "enable support for third party kernel extensions" — source: cberner/fuser README linking macFUSE's own wiki, https://github.com/cberner/fuser, accessed 2026-08-22.
- **fuse-t licence:** "Free for personal use. Commercial license available for embedding and shipping Fuse-T in a product." It is kext-less, with "Three supported backends: NFS, SMB, and native FSKit on macOS 26 and later", and "Can be embedded within an existing app bundle to be published in the App Store". Latest release 1.2.0. — source: fuse-t.org, https://www.fuse-t.org/, accessed 2026-08-22.
- **NFS loopback is the licence-free path, and it is proven twice over.** rclone: "Mounting on macOS can be done either via built-in NFS server, macFUSE (also known as osxfuse) or FUSE-T… This method spins up an NFS server using `serve nfs` and mounts it to the specified mountpoint" (with `--nfs-cache-handle-limit`, default 1000000). — source: rclone, https://rclone.org/commands/rclone_mount/, accessed 2026-08-22. And EdenFS: "On macOS, EdenFS uses NFSv3." — source: facebook/sapling, `eden/fs/docs/Overview.md`, https://github.com/facebook/sapling/blob/main/eden/fs/docs/Overview.md, accessed 2026-08-22.

### Linux — FUSE

- `fuser` is the Rust option: MIT-licensed, "a rewrite of the original FUSE C library", and on Linux the libfuse dependency is optional — "on Linux these calls to libfuse are optional. They can be removed by building without the 'libfuse' feature flag." Note the maintainer's policy change: "Pull requests are no longer being accepted" and "Version 0.18.0 is the last version that was primarily developed without coding agents." — source: cberner/fuser README + repo metadata (License: MIT), https://github.com/cberner/fuser, accessed 2026-08-22. This is a real supply-chain governance consideration for a small OSS project.
- **FUSE passthrough** landed in **Linux 6.9** (`CONFIG_FUSE_PASSTHROUGH`, found in 6.9 onward): the daemon registers a backing fd via the `FUSE_DEV_IOC_BACKING_OPEN` ioctl, gets a `backing_id`, replies to OPEN/CREATE with `FOPEN_PASSTHROUGH` + `backing_id`, and later `FUSE_DEV_IOC_BACKING_CLOSE`. Supported for `read(2)`/`write(2)` via read_iter/write_iter, `splice(2)` and `mmap(2)`. **"Setting up passthrough functionality currently requires the FUSE daemon to possess the `CAP_SYS_ADMIN` capability"** — kernel docs — with kernelnewbies noting "For now this is only allowed to privileged servers, but this limitation will go away in the future." — sources: The Linux Kernel documentation, https://docs.kernel.org/filesystems/fuse/fuse-passthrough.html; kernelnewbies Linux_6.9, https://kernelnewbies.org/Linux_6.9; Phoronix, "FUSE Passthrough Mode Merged For Linux 6.9", https://www.phoronix.com/news/Linux-6.9-FUSE-Passthrough, published 2024-03-15; LKDDB CONFIG_FUSE_PASSTHROUGH, https://cateee.net/lkddb/web-lkddb/FUSE_PASSTHROUGH.html.
  - Design consequence: passthrough is exactly the right primitive for "once materialized, get out of the way" — hand the kernel the fd of the real object in the content-addressed store and stop paying per-read round trips.
- Behaviour of ordinary tools on a FUSE mount: `ls -l` shows whatever `getattr` reports (so you can report the true `size` from the pointer while holding no bytes); `cat`/`mmap` trigger your read path; `du` reports what you report for blocks; `rsync` will read every file it copies and thus materialize everything — this is the single biggest operational hazard of a mount-based design. `[INFERENCE]` from FUSE semantics; the `rsync`/`du` behaviours are not separately cited.

### Linux — `fanotify` pre-content events / HSM (the only in-place option)

- fanotify's stated purpose includes HSM: "Use cases include virus scanning and hierarchical storage management… the ability to make access permission decisions, and the possibility to read or modify files before access by other applications." — source: `fanotify(7)`, Linux man-pages 6.18, https://man7.org/linux/man-pages/man7/fanotify.7.html, accessed 2026-08-22.
- Range information is delivered so you can populate only what is read: `struct fanotify_event_info_range { struct fanotify_event_info_header hdr; __u32 pad; __u64 offset; __u64 count; };` — "In case of `FAN_PRE_ACCESS` events, an additional information record describing the access range is returned." — source: `fanotify(7)`, ibid.
- **Kernel version — verify carefully, the sources disagree in nuance.** Phoronix reported the pre-content series "Expected For Linux 6.14" (queued in linux-fs for_next) — https://www.phoronix.com/news/Linux-6.14-precontent-fanotify. LWN's 2026 LSFMM+BPF report says of `FAN_PRE_ACCESS`: "This event was merged in early 2025" — consistent with 6.14 (released early 2025). Treat **6.14** as the floor. — source: LWN.net, Jake Edge, "An update on fanotify", https://lwn.net/Articles/1075829/, published 2026-06-08.
- **The `mmap` story is a live regression, and it matters.** "Josef Bacik contributed a hook for page faults, which would allow files that are mapped using `mmap()` to be lazily populated when they are accessed. Unfortunately, 'this backfired after it got merged'; some regressions were found so the page-fault hook has been backed out. Instead, the file needs to be populated at `mmap()` time." The deadlock: "a file is mapped using `mmap()` and part of that mapped memory is used as a buffer to write to another file. That causes a page fault for the mapped range, which deadlocks when the HSM daemon tries to populate it." — source: LWN, ibid. **So under fanotify HSM, an `mmap` materializes the whole file at map time, not lazily.**
- Other current limitations from the same primary report: pre-content events for directories "also suffer from deadlock problems and it is difficult to find ways to avoid them"; filesystem freeze (LVM snapshots, XFS scrub, suspend) can deadlock, with a proposal to disable freezing for such mounts; and "the pre-content events are emitted every time there is a read, even if the region has already been populated" — the planned BPF-based suppression "has not yet been implemented". — source: LWN, ibid.
- Constraint from patch review: "Pre-content permission events are not allowed for `FAN_CLASS_CONTENT`" (they need `FAN_CLASS_PRE_CONTENT`) and are only supported on regular files and directories. — source: fanotify pre-content patch series v2 04/16, https://www.mail-archive.com/linux-bcachefs@vger.kernel.org/msg02279.html.
- Measured overhead is modest: a kernel-tree build took ~17 s longer with HSM (9m49s → 10m6s real). — source: Phoronix, https://www.phoronix.com/news/Linux-6.14-precontent-fanotify.
- Production pedigree: "already the code is used in production in Meta for fanotify-based Hierarchical Storage Management" — same Phoronix source.
- Restartability (not yet merged as of the 2026 summit): a two-fd design (control fd in a systemd fd-store + queue fd) so a crashed/restarted daemon does not let unpopulated files be read. Until this merges, **a crashed HSM daemon is a correctness hazard**. — source: LWN, ibid.

### Linux — the cheap tricks and what `ls`/`du`/`cat` actually do

- **Sparse files.** `lseek(2)` `SEEK_HOLE`/`SEEK_DATA` exist since Linux 3.1 and are supported on Btrfs (3.1), XFS (3.5), ext4 (3.8), tmpfs (3.8), NFS (3.18), FUSE (4.5), GFS2 (4.15). "a hole is a sequence of zeros that (normally) has not been allocated in the underlying file storage. However, a filesystem is not obliged to report holes." — source: `lseek(2)`, Linux man-pages 6.18, https://man7.org/linux/man-pages/man2/lseek.2.html, accessed 2026-08-22.
  - Practical semantics: `ls -l` prints `st_size` (so a sparse stub can *look* full size); `du` prints `st_blocks` (so it correctly reports ~0); `cat` returns **zeros, silently** — no hook, no error. **That silent-zeros property makes bare sparse files unsafe as placeholders**: a build or a checksum sees plausible garbage instead of failing. `[INFERENCE]` from the man page semantics.
- **`overlayfs`** is a stacking filesystem, not an on-demand fetch mechanism; it has no hook that lets user space supply bytes on first read. It is useful only as a composition layer over a materialized store. — source: The Linux Kernel documentation, Overlay Filesystem, https://docs.kernel.org/filesystems/overlayfs.html (index retrieved 2026-08-22). `[UNVERIFIED]` at the level of specific quoted text — only the document index was retrieved; the "no on-demand fetch hook" characterization is inference, not quotation.
- **`autofs`** mounts on demand at *directory* granularity, driven by maps: "key [-options] location", with executable maps ("A map can be marked as executable. A program map will be called with the key as an argument") and wildcard keys (`*  server:/export/home/&`). — source: `autofs(5)`, https://man7.org/linux/man-pages/man5/autofs.5.html, accessed 2026-08-22. It can lazily *mount*, but it cannot make an individual file inside an existing directory materialize.
- **`cachefiles`/`fscache`** is a kernel-side cache for network filesystems (NFS/AFS/CIFS), not a user-space content provider — you do not get to define where bytes come from. `[UNVERIFIED]` — no primary source retrieved in this pass; flagged rather than asserted.
- **Extended attributes as metadata carriers** are viable and free: they survive on ext4/XFS/btrfs/APFS, are ignored by git, and can hold oid/size/origin/last-materialized timestamps without changing file content. `[INFERENCE]` — no single citation; the git-neutrality follows from git tracking content and mode only (see git-LFS spec below).
- **Lustre/GPFS-style HSM stubs** are the enterprise precedent for the whole model; the Linux-generic re-implementation of that idea is precisely the fanotify pre-content work above. `[UNVERIFIED]` — no Lustre/GPFS primary doc retrieved.

### Windows (brief, for completeness)

- **Cloud Files API (`cfapi`)**, since Windows 10 1709, is the closest thing to an ideal implementation of the requirement: "Sync engines can create placeholder files that consume only 1 KB of storage for the filesystem header, and that automatically hydrate into full files under normal use conditions… Whether you use file system APIs, the Command Prompt, or a desktop or a UWP app to access a placeholder file, the file will hydrate without additional code changes." Three states: placeholder / full / pinned-full. Hydration policy is `max(app policy, provider policy)` over `Always full > Full > Progressive > Partial`, fixed at open time. — source: Microsoft Learn, "Build a Cloud Sync Engine that Supports Placeholder Files", https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine, ms.date 2025-05-12, updated 2025-11-18.
- Implementation detail with direct app-compat consequences: "The cloud files API implements the placeholder system using reparse points… the cloud files API always hides its reparse points from all applications except for sync engines and processes whose main image resides under `%systemroot%`." Driver is the `cldflt.sys` minifilter, **NTFS-only**. Sync engines "are designed to use the Desktop Bridge as an implementation requirement" and cannot be UWP. — source: ibid.
- **ProjFS** is the sibling API and Microsoft explicitly steers slow/remote backing stores away from it: "ProjFS is designed for use with high-speed backing data stores… As such, ProjFS doesn't provide: mechanisms for reporting progress of data recall; indication of the online versus offline state of a file… For such scenarios, consider instead using the Cloud Files API." — source: Microsoft Learn, "Windows Projected File System", https://learn.microsoft.com/en-us/windows/win32/projfs/projected-file-system, ms.date 2018-09-14, updated 2025-04-15.

### Real implementations to learn from

- **OneDrive Files On-Demand** is the reference UX and the reference vocabulary: online-only (blue cloud, "don't take up space… doesn't download to your device until you open it"), locally available (green check, reclaimable via "Free up space"), always-available (pinned). Crucially it also defines the *automatic* release policy the requirement asks for: "With Storage Sense turned on, these files will become online-only files after the time period you've selected." And the honest limitation: "Desktop search can search for online-only files by name, but it cannot search the contents within online-only files." Requires Windows 10 1709+; enabled by default since OneDrive build 23.066. — source: Microsoft Support, https://support.microsoft.com/en-us/onedrive/save-disk-space-with-onedrive-files-on-demand-for-windows, ms.date 2025-12-17.
- **Nextcloud desktop** is the closest analogue to the proposed project and shows the per-platform split cleanly: Windows via `WindowsCfApiVFS` on cfapi with a registered virtual-file suffix (`APPLICATION_VIRTUALFILE_SUFFIX = "nextcloud_virtual"`) plus shell extensions; macOS via a `FileProviderExt` implementing `NSFileProviderReplicatedExtension`, shipped as a **separate client build** ("Unlike on Windows, virtual files support on macOS is provided by a separate client version"); **Linux: none** ("Neither the AppImage nor the nextcloud-desktop support virtual files", with only an experimental-options workaround). — sources: nextcloud/desktop wiki "Virtual files client for macOS", https://github.com/nextcloud/desktop/wiki/Virtual-files-client-for-macOS; DeepWiki nextcloud/desktop Windows Integration, https://deepwiki.com/nextcloud/desktop/4.2-windows-integration (published 2025-07-11); Nextcloud community forum, https://help.nextcloud.com/t/linux-desktop-client-doesnt-support-virtual-files/244807 (published 2026-05-26). **The Windows suffix trick is the key transferable idea: a placeholder that is a distinct, recognizable file, not a lie about a real one.**
- **rclone `mount`** is the best-documented cache/eviction design in OSS. Four modes `off|minimal|writes|full`; `--vfs-cache-max-age` default **1h** with exactly the requested semantics: "will evict files from the cache after the set time since last access has passed… When a cached file is accessed the 1 hour timer is reset to 0." Eviction is LRU ("rclone will attempt to evict the least accessed files from the cache first"), polled every `--vfs-cache-poll-interval` (1m), and honestly documents that "the cache may exceed these quotas… because open files cannot be evicted from the cache." In `full` mode "the files in the cache will be sparse files and rclone will keep track of which bits of the files it has downloaded" — with the warning that FAT/exFAT lack sparse support and "Rclone will perform very badly". Also: "You should not run two copies of rclone using the same VFS cache… This can potentially cause data corruption." — source: rclone docs, https://rclone.org/commands/rclone_mount/, accessed 2026-08-22. **Directly reusable: the 24h-idle release job is rclone's `--vfs-cache-max-age` with a different constant, plus the open-fd exemption, plus a single-writer lock.**
- **EdenFS (Meta / Sapling)** is the strongest evidence for what a source-control virtual filesystem costs. It exists precisely for "lazily fetching file data, so that it only needs to fetch file information for portions of the repository that are actually used", and targets `hg status`/`git status` and checkout speed. Three separate OS backends: FUSE on Linux, **NFSv3 on macOS**, ProjFS on Windows — "This behaves fairly differently from FUSE and NFS, but EdenFS still shares most of the same internal logic." — source: facebook/sapling `eden/fs/docs/Overview.md`, https://github.com/facebook/sapling/blob/main/eden/fs/docs/Overview.md, accessed 2026-08-22. The design docs list Inodes, InodeLifetime, InodeLocks, InodeStorage, Caching, Globbing, Redirections, Rename, Threading — **that is the true surface area of "build a virtual filesystem for a repo", and it is enormous for a small project.** `[UNVERIFIED]` on usability outside Meta: no primary source located confirming supported standalone use.
- **VFS for Git is deprecated by its own maintainers, and the reason is instructive:** "for new deployments, we strongly recommend you consider Scalar instead of VFS for Git. By combining the lessons from operating VFS for Git at scale with new developments in Git, Scalar offers a clearer path forward for all large monorepos." It requires the `PrjFlt` filter driver, a GVFS-protocol server, a `microsoft/git` fork, no clean/smudge filters in the repo, and `* -text` in `.gitattributes`. MIT-licensed, Windows-only. — source: microsoft/VFSForGit README, https://github.com/microsoft/VFSForGit, accessed 2026-08-22.
- **Scalar completed that retreat:** "we have successfully transitioned Scalar from a modified version of VFS for Git into a thin shell around core Git features" — the mount process was deleted entirely ("drop the `Scalar.Mount` process"), replaced by partial clone + sparse-checkout + background prefetch + fsmonitor + commit-graph + multi-pack-index. MIT. — source: microsoft/scalar README, https://github.com/microsoft/scalar, accessed 2026-08-22. **This is the single most important strategic datapoint in this digest: the industry's flagship git-virtualization project concluded that native git mechanisms beat a virtual filesystem.**
- **git-LFS itself already ships the portable placeholder.** The pointer is "text files which MUST contain only UTF-8 characters", "must be less than 1024 bytes", carry `version`, `oid` (`sha256:…`) and `size` in bytes, are "unique: that is, there is exactly one valid encoding", and "MUST be stored in Git with their executable bit matching that of the replaced file". The smudge filter's documented behaviour is *literally the materialization contract*: "Read 100 bytes. If the content is ASCII and matches the pointer file format: Look for the file in `.git/lfs/objects/{OID-PATH}`. If it's not there, download it from the server. Write its contents to STDOUT." — source: git-lfs/git-lfs `docs/spec.md`, https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md, accessed 2026-08-22. **Size and oid — two of the three metadata fields the requirement asks for — are already in the pointer, and a worktree full of pointers is `git status`-clean by construction.**
- **JuiceFS** — Apache-2.0, Go, FUSE + Windows + S3 gateway, POSIX-complete (passes 8813 pjdfstest cases), supports mmap, flock/fcntl, xattr, fallocate punch-hole. Splits files into 64 MiB chunks → slices → 4 MiB blocks in object storage with metadata in Redis/MySQL/SQLite/TiKV. — source: juicedata/juicefs README + repo metadata (License: Apache-2.0), https://github.com/juicedata/juicefs, accessed 2026-08-22. Licence-clean, but it is a whole distributed filesystem, not a per-file placeholder layer.
- `[UNVERIFIED]` — Dropbox Smart Sync / online-only, iCloud Drive "Optimize Mac Storage", Google Drive for desktop, `restic mount`, `s3fs`, `goofys`, Seafile: no primary sources retrieved in this pass. Do not cite claims about these. Note only the structural fact that on current macOS *all* of the commercial ones are forced through File Provider into `~/Library/CloudStorage` (per the TidBITS source above), which is itself the useful conclusion.

## Applicability to a git-LFS-backed virtual-file design

1. **Keep the LFS pointer as the placeholder.** It is already a 1024-byte UTF-8 record carrying `oid` and `size`, it is the committed blob (so `git status` is clean), it is cross-platform, and it cannot lose data. Everything the requirement calls "pointer/placeholder with metadata" exists today; what is missing is a *selection policy* (a gitignore-like pattern file deciding which paths stay as pointers) and a *materialize/release* command pair.
2. **Metadata beyond oid/size goes in xattrs, not in the file.** Origin URL, last-materialized timestamp, last-access timestamp, remote-holds-it flag. Invisible to git, cheap, and it makes the nightly release job a pure local scan.
3. **Model the release job on Apple's `evictItem` refusal set and rclone's LRU.** Refuse if: local content differs from `oid` (unsynced edit), any process holds an open fd, the path is pinned, or the remote is not confirmed to hold the object. `--vfs-cache-max-age`-style last-access timer, reset on every materialization, default 24h. This is verified-by-precedent, not invented.
4. **`ls`-visibility is a separate, optional, platform-specific tier.** Linux server: an opt-in `fuser`-based mount (MIT) that reports the pointer's `size` from `getattr` and serves reads from the content-addressed store, using FUSE passthrough (≥6.9, `CAP_SYS_ADMIN`) once materialized so steady-state reads cost nothing. macOS desktop: a File Provider domain under `~/Library/CloudStorage` — *a second view of the data, not the worktree itself*. Do not promise in-worktree placeholders on macOS.
5. **Do not attempt `SF_DATALESS` or a macFUSE dependency.** The first is prohibited by `chflags(2)`; the second is prohibited by macFUSE's own licence clause 4 and requires a kext Apple discourages.
6. **Take Scalar's lesson seriously.** Before building any filesystem layer, check whether git's own partial-clone/sparse-checkout plus an explicit `materialize`/`release` CLI delivers 90% of the value at 5% of the risk. For "above all simple and safe", it very likely does.

## Risks / failure modes

- **Silent zeros.** A sparse-file placeholder returns zeros from `cat` with no error and no hook. Any design that fakes `st_size` without an interception layer can corrupt downstream artifacts. (`lseek(2)` semantics.)
- **Accidental mass materialization.** `rsync`, `du -a` on a mount, a backup agent, an antivirus scan, an IDE indexer, or `find -exec` will each read every file. On macOS, even `contentsOfDirectory`/`fileExists` materializes (TN3150). A single unguarded tool can pull the entire LFS store down.
- **`mmap` under fanotify HSM materializes the whole file at `mmap()` time**, not lazily, because the page-fault hook was reverted after deadlocks (LWN 2026). Any "only fetch the bytes you read" promise is false for mmap'd files on Linux HSM today.
- **Deadlock classes are real and current.** fanotify: pre-content on directories still deadlocks; filesystem freeze (LVM snapshot, XFS scrub, suspend) can deadlock a pre-content mount. macOS: FileProvider-backed reads deadlock in processes that bypass `NSFileCoordinator` (claude-code #40783). A watchdog-terminated app is a user-visible data-loss-adjacent failure.
- **Crashed daemon = unpopulated reads.** fanotify restartable permission events are posted but unmerged as of LSFMM+BPF 2026; a crashed HSM daemon can let a process read an unpopulated file.
- **Two writers, one cache.** rclone documents outright data corruption when two processes share a VFS cache dir. A `keeper-syncd` plus a desktop app both managing the same store needs a single-owner lock.
- **Licence contamination.** macFUSE (clause 4) and fuse-t (commercial licence for shipping) are both incompatible with a permissive-only firewall. This is verified from the licence texts themselves and must gate any macOS mount design.
- **Redundant event storms.** fanotify emits pre-content events "every time there is a read, even if the region has already been populated"; the BPF suppression is unimplemented. Expect to need your own populated-range bookkeeping.
- **Eviction is best-effort everywhere.** Apple's own guidance: "There is no guarantee, it could fail for various reasons." A release policy must be idempotent and must tolerate persistent failures without retry storms.

## Open questions

1. Does shipping a macOS File Provider extension require paid Apple Developer Program membership and notarization? `[UNVERIFIED]` — not established from an Apple primary source here; must be confirmed before scoping any macOS tier.
2. Can an FSKit `FSUnaryFileSystem` be mounted *over* an existing populated directory (union/passthrough style) so a worktree path is preserved? Apple ships a "Building a passthrough file system" sample; its mount topology was not examined.
3. What is the minimum kernel the target server fleet runs? fanotify pre-content needs ≥6.14; FUSE passthrough needs ≥6.9. Below 6.9 the FUSE tier pays per-read round trips forever.
4. Is `CAP_SYS_ADMIN` acceptable for `keeper-syncd`? Both the fanotify HSM path and FUSE passthrough currently require privileged daemons.
5. Does `git status` remain clean when a FUSE mount overlays a worktree — specifically, do the synthesized `st_mtime`/`st_ino`/`st_size` values invalidate git's index stat-cache on every command? Untested; this is the make-or-break question for the mount tier.
6. Behaviour of the LFS smudge/clean filter *inside* a FUSE mount: `filter.lfs.process` writing through a virtual filesystem that is itself backed by the LFS store is a recursion hazard.
7. `cachefiles`/`fscache` and Lustre/GPFS HSM stubs were not sourced; if in-kernel caching is being considered seriously they need a dedicated pass.
