# Git-native and git-adjacent mechanisms for "don't download this content, but keep knowing about it"
_agent: R1GitNative · accessed: 2026-08-22_

## Verdict

- **Every shipped git-native design uses a *placeholder-in-the-worktree* model, not a filesystem-virtualization model.** git-lfs leaves a <1024-byte UTF-8 pointer file at the real path; git-annex leaves either a dangling symlink (locked) or a `/annex/objects/<key>` pointer file (unlocked). Both are ordinary files that `ls` sees with the *placeholder's* size, not the content's size. The only production systems that made `ls` show the true size were filesystem virtualizations (VFS for Git / ProjFS, hf-mount FUSE/NFS) — and the git one was abandoned when Apple deprecated the required macOS kernel APIs.
- **The selective-fetch primitives already exist in git-lfs and are the cheapest possible starting point**: `lfs.fetchinclude`/`lfs.fetchexclude` (gitignore-style, comma-separated) are honoured by *fetch*, *smudge* **and** *prune* — i.e. one config expresses "don't download" AND "safe to evict" — and `.lfsconfig` is on the security allow-list for exactly those two keys, so the pattern file can be committed to the repo.
- **`.lfsconfig` is the only committed, repo-scoped, gitignore-syntax pattern file git-lfs offers, and local git config overrides it.** That precedence (worktree file → index → HEAD; git config wins) is the model a keeper-style "virtual-files" pattern file should copy rather than invent.
- **git-annex's preferred-content / required-content split is the closest prior art to the whole product intent**: `wanted` = "which files this repo wants present" (advisory, drives `--auto` drop/get), `required` = "never drop these" (enforced). Plus `numcopies`/`mincopies` give the never-lose-data guarantee: `drop` refuses unless it can *verify* N copies elsewhere. git-lfs has no equivalent verification by default — `prune` infers "pushed" from ref comparison and only optionally calls the remote (`--verify-remote`).
- **The eviction step is where every one of these tools has shipped data-loss bugs.** git-lfs `prune` has been fixed for deleting objects referenced by stashes (#4209) and for deleting staged files in the index (#5637), still doesn't understand partial clones (#4335), and explicitly ignores the reflog ("LFS objects that are only referenced by orphaned commits are always deleted"). Design implication: a release/evict job must be *conservative-by-construction* (drop only what a remote positively confirms), not "conservative by enumerating what to keep".
- **Partial clone is the wrong layer for LFS-tracked content and the two do not compose today.** `--filter=blob:none` hides *git* blobs behind a promisor remote, transparently backfilled on access — including by `git log -p`, causing fetch storms — but LFS objects are not git blobs, so partial clone gives no help, and `git lfs prune` is broken under it.
- **Metadata offline is basically free in both designs, and is a design win**: the LFS pointer itself carries `oid sha256:…` and exact `size`; the git-annex key carries backend, size (`-sNNNN`) and optionally mtime (`-mNNNN`) *in its name*, so `git annex examinekey` reports `${bytesize}` with zero network. "Where it really is" is a separate, replicated ledger only in git-annex (`whereis`, backed by the `git-annex` branch); LFS has nothing equivalent offline.
- **CoW is the right materialization primitive.** `git lfs dedup` already re-creates worktree files as copy-on-write clones of the object store, and exits unsuccessfully if the filesystem can't do it — so materialize can be O(1) and release can be a plain unlink of the worktree file, leaving the store copy intact.

## Findings

### 1. git-lfs: what the worktree actually contains when smudge is skipped

- A pointer file is a UTF-8 text file, `{key} {value}\n` lines, keys sorted (except `version` first), **< 1024 bytes**, with required keys `version`, `oid` (`sha256:<lowerhex>`), `size` (bytes); encoding is *unique* (exactly one valid encoding) — source: git-lfs/git-lfs, `docs/spec.md` @20be8f8eaf88e6b6c571eba1d84adbfbd769dc25 (2026-08-19), published unknown.
- An empty file is its own pointer — no LFS object is involved — source: same, `docs/spec.md`.
- With smudge skipped, git writes that pointer text to the worktree path verbatim: "Why do I end up with small text files in my working tree instead of my files? … these pointer files usually start with the line `version https://git-lfs.github.com/spec/v1` … you've explicitly chosen to skip that behaviour by using the `--skip-smudge` option" — source: git-lfs, `docs/man/git-lfs-faq.adoc` @20be8f8.
- `GIT_LFS_SKIP_SMUDGE`: "Sets whether or not Git LFS will skip attempting to convert pointers of files tracked into their corresponding objects when checked out into a working copy. If 'true', '1', 'on', or similar, Git LFS will skip the smudge process in **both `git lfs smudge` and `git lfs filter-process`**" — source: git-lfs, `docs/man/git-lfs-config.adoc` @20be8f8.
- `git lfs install --skip-smudge`: "Skips automatic downloading of objects on clone or pull. This requires a manual `git lfs pull` every time a new commit is checked out on your repository." `--skip-repo` installs filters without touching hooks — source: git-lfs, `docs/man/git-lfs-install.adoc` @20be8f8.
- **Path-selective skipping without a global switch**: `git lfs smudge` itself honours `lfs.fetchinclude`/`lfs.fetchexclude`; "Git LFS pointer files that are **not** replaced with the contents of their corresponding object files are simply copied to standard output without change." Paths matched "using wildcard matching as per gitignore(5)" — source: git-lfs, `docs/man/git-lfs-smudge.adoc` @20be8f8. **This is the load-bearing mechanism**: a gitignore-style pattern list already yields per-path pointer-vs-content behaviour at checkout time, with no filter driver replacement.
- Fetch-side: `lfs.fetchinclude`/`lfs.fetchexclude` are comma-separated path lists; `--include`/`--exclude` set them per-invocation; `--all` "Ignores any globally configured include and exclude paths to ensure that all objects are downloaded" — source: git-lfs, `docs/man/git-lfs-fetch.adoc` @20be8f8.
- `git lfs fetch --recent` additionally downloads objects for recent refs/commits, governed by `lfs.fetchrecentrefsdays` (default 7), `lfs.fetchrecentremoterefs`, `lfs.fetchrecentcommitsdays` (default 0), `lfs.fetchrecentalways` — source: same.
- Materialization is a separate, *offline* step: `git lfs checkout` "Try to ensure that the working copy contains file content for Git LFS objects for the current ref, **if the object data is available. Does not download any content**… where a file is either missing in the working copy, or contains placeholder pointer content with the same SHA, the real file content is written… **Modified files are never overwritten.**" — source: git-lfs, `docs/man/git-lfs-checkout.adoc` @20be8f8. `git lfs pull` ≡ `fetch` + `checkout` — source: `docs/man/git-lfs-pull.adoc`.
- **Trap**: since Git 2.42.0, `checkout`/`pull` only act on files matching an LFS filter attribute present in the index or worktree `.gitattributes`; "In a repository with a partial clone or sparse checkout, it is therefore advisable to check out all `.gitattributes` files from HEAD before using this command", or set `GIT_ATTR_SOURCE=HEAD` — source: git-lfs, `docs/man/git-lfs-checkout.adoc`, `git-lfs-pull.adoc` @20be8f8.

### 2. git-lfs: how tools report pointer vs materialized

- `git lfs ls-files`: "An asterisk (`*`) after the OID indicates a full object, a **minus (`-`) indicates an LFS pointer**." Options `-l/--long` (full 64-char OID), `-s/--size`, `-d/--debug`, `-a/--all` (full history), `--deleted`, `-I/-X` include/exclude, `-n/--name-only`, `-j/--json` — source: git-lfs, `docs/man/git-lfs-ls-files.adoc` @20be8f8. **This is the canonical "is it materialized?" query and it is already JSON-emitting.**
- `git lfs status` reports unpushed objects, index-vs-HEAD differences, and worktree-vs-index differences; `-p/--porcelain`, `-j/--json`. It "must be run in a non-bare repository" — source: git-lfs, `docs/man/git-lfs-status.adoc` @20be8f8. Note it does **not** report pointer-vs-materialized; that is `ls-files`.
- `git lfs pointer --check [--strict]` validates that a byte stream is a valid (and, with `--strict`, *canonical*) pointer; exits 0 valid, 1 invalid, 2 non-canonical — source: git-lfs, `docs/man/git-lfs-pointer.adoc` @20be8f8. Useful as the safety predicate before overwriting a placeholder.
- `git lfs dedup` "Deduplicates storage by re-creating working tree files as clones of the files in the Git LFS storage directory using the operating system's copy-on-write file creation functionality. If the operating system or file system don't support copy-on-write file creation, this command exits unsuccessfully." It refuses to run when LFS extensions are configured — source: git-lfs, `docs/man/git-lfs-dedup.adoc` @20be8f8. `-t/--test` probes CoW support without acting.
- `git lfs locks --local` (own locks, no remote call), `--cached` (last known locks, "intended to display the last known locks in case you are offline"), `--verify` (server-side owner verification, detects broken/force-released locks) — source: git-lfs, `docs/man/git-lfs-locks.adoc` @20be8f8. `git lfs track --lockable` marks paths so they are "made read-only in the working copy when not locked" — source: `docs/man/git-lfs-track.adoc`. **Read-only-until-claimed is directly reusable as a materialization UX.**
- `git lfs migrate import|export|info` rewrites history and "will only make changes to your local repository and working copy, never any remotes… generally 'destructive' in the sense that they rewrite your Git history" (exception: the `no-rewrite` import sub-mode) — source: git-lfs, `docs/man/git-lfs-migrate.adoc` @20be8f8. Not a virtual-file mechanism; relevant only as the on-ramp for retro-tracking existing content.

### 3. git-lfs `prune`: the eviction command and its unsafe-drop bug class

- Retention set: prune deletes any local object not referenced by **the current checkout, all existing stashes, a 'recent branch', a 'recent commit', a commit which has not been pushed, or any other worktree checkouts** — source: git-lfs, `docs/man/git-lfs-prune.adoc` @20be8f8.
- Explicit unsafety: "**The reflog is not considered, only commits. Therefore LFS objects that are only referenced by orphaned commits are always deleted.**" — source: same.
- Explicit unsafety: "you should **not** run `git lfs prune` if you have different repositories sharing the same custom storage directory" (`lfs.storage`) — source: same. Directly relevant to any server-side shared object store.
- `lfs.fetchexclude` doubles as an eviction rule: "any Git LFS files whose paths match one in that list will be pruned **unless they are referenced by a stash or an unpushed commit**" — source: same. This is exactly the "don't keep this materialized" semantics, already implemented.
- "Pushed" is *inferred*, not verified, by default: "we check the difference between local refs and remote refs; where the local ref is ahead, any LFS files referenced in those commits is unpushed". `--verify-remote` / `lfs.pruneverifyremotealways` makes prune call the remote API to confirm presence before deleting; `--when-unverified=halt|continue` chooses the failure policy — source: same.
- Timing safety margin: `lfs.pruneoffsetdays` (default 3) is added to the fetch-recent windows "to ensure that we always keep files you download for a few days"; "If a day value is zero, that condition is not used at all to retain objects and they will be pruned" — source: same. **This is the shipped precedent for a lazy, N-hours-after-last-use release policy — and note it is calendar/ref-based, not access-time-based; no git-native tool tracks last *use*.**
- Historical unsafe drops (the bug class): "prune: fix deleting objects referred to by stashes #4209", "Fix git lfs prune is deleting staged files in the index #5637", "Add test to check `prune` command retains tagged unpushed objects #4962", plus repeated hangs (#4557, #3460) — source: git-lfs, `CHANGELOG.md` @20be8f8.
- Open, unfixed: "git lfs prune does not work with partial clone" — source: git-lfs/git-lfs issue #4335, https://github.com/git-lfs/git-lfs/issues/4335, opened 2020-12-04, still open as of 2026-08-22.
- Materialization-integrity bug class (not prune, but the same blast radius): "Zero-filled working tree files on Windows ReFS/Dev Drive: checkout block-clones objects before they are flushed to disk" — source: git-lfs/git-lfs issue #6312, https://github.com/git-lfs/git-lfs/issues/6312, opened 2026-07-30, open. **CoW materialization must fsync the store object before cloning it.**

### 4. git partial clone / promisor remotes

- Design intent: "Partial clone allows us to avoid downloading such unneeded objects *in advance* during clone and fetch operations… Missing objects can later be 'demand fetched' if/when needed. A remote that can later provide the missing objects is called a **promisor remote**" — source: git/git, `Documentation/technical/partial-clone.adoc` @1a3e64c6c4a623626ff0687008732a8e007e2a1c (2026-08-20).
- "Use of partial clone **requires that the user be online** and the origin remote or other promisor remotes be available for on-demand fetching of missing objects." — source: same. **No offline-degraded mode; this is the sharpest contrast with a pointer-file design, which degrades to "you can see the metadata".**
- Mechanics: a `filter` capability in fetch-pack/upload-pack negotiation; filtered packs are marked by a sibling `<name>.promisor` file ("arbitrary contents, like the `<name>.keep` files"); the local repo records `extensions.partialClone` "to prevent older versions of git from failing mid-operation because of missing objects that they cannot handle" — source: same.
- Filters: `blob:none`, `blob:limit=<n>` (with `k`/`m`/`g` suffixes, `blob:limit=1k` ≡ 1024), `object:type=…`, `sparse:oid=<blob-ish>`, `tree:<depth>`; multiple `--filter=` flags intersect; `combine:<f1>+<f2>` with %-encoding; `--filter=sparse:path=<path>` "has been dropped for security reasons" — source: git/git, `Documentation/rev-list-options.adoc` @1a3e64c.
- Config: `remote.<name>.promisor` ("When set to true, this remote will be used to fetch promisor objects") and `remote.<name>.partialclonefilter` ("The filter that will be applied when fetching from this promisor remote") — source: git/git, `Documentation/config/remote.adoc` @1a3e64c.
- Inspecting what's absent: `git rev-list --missing=error|allow-any|allow-promisor|print|print-info`. `allow-promisor` "will only allow object traversal to continue for EXPECTED promisor missing objects. Unexpected missing objects will raise an error" — the built-in corruption-vs-intentionally-absent discriminator. `print` prefixes missing OIDs with `?`; `print-info` adds `path=<path>` and `type=<type>` inferred from the containing object, emitted as `<OID> NUL missing=yes NUL [<token>=<value> NUL]…` — source: git/git, `Documentation/rev-list-options.adoc` @1a3e64c. **This NUL-delimited `missing=yes path=… type=…` record is the closest git-native equivalent of a virtual-file listing, and it is the format to imitate.**
- Failure mode acknowledged upstream: "if the user can stay within the pre-selected subset of the source tree, they may not encounter any missing objects. Alternatively, the user could try to pre-fetch various objects if they know that they are going offline" — source: `Documentation/technical/partial-clone.adoc` @1a3e64c. Any history-walking command (`git log -p`, `git blame`, `git diff` across old commits) leaves the pre-selected subset and triggers a serialized backfill; upstream's only remedy is pre-fetching.
- **Partial clone ≠ sparse-checkout.** Sparse-checkout removes paths from the *worktree* (SKIP_WORKTREE), leaving objects present locally; partial clone removes *objects*, leaving paths in the worktree. Cone mode is the default and restricts patterns to directory prefixes; "Non-cone mode uses gitignore-style patterns to select what to [include]" and upstream says "we do not recommend using it" because of the listed "Non-cone Problems" — source: git/git, `Documentation/git-sparse-checkout.adoc` @1a3e64c.
- Sparse index (`--sparse-index`, `index.sparse`) is a *performance* variant: the on-disk index stores a directory entry instead of every file below an excluded cone. "**WARNING:** Using a sparse index requires modifying the index in a way [that older/other tools may not understand]" and "Some commands might be slower with a sparse index" — source: same. It changes nothing about content availability.
- **Neither mechanism helps for LFS-tracked content**: LFS objects live outside the git object graph, so no `--filter` describes them, and `git lfs prune` is documented-broken under partial clone (#4335 above).

### 5. git-annex: the closest prior art

**Content vs key.** Files are checked into git as a reference to a *key*, not content. Key format: `BACKEND[-sNNNN][-mNNNN][-SNNNN-CNNNN]--NAME`, e.g. `SHA256E-s31390--f50d7ac4…cc0.mp3`; "The `-s` field is optional, and is the size of the content in bytes"; `-m` is mtime (WORM only); `-S`/`-C` are chunk size and chunk number — source: git-annex, `doc/internals/key_format.mdwn` @6bc1790845270f4465003adb6c8772ea859c68ee (2026-08-21). **The size is in the name, so full metadata is available with no object and no network.**

**What `ls -l` shows — be precise:**
- *Locked (default)*: "a symlink is made that points to the content. These symlinks are checked into git" — source: git-annex, `doc/git-annex.mdwn` @6bc1790 (line ~25). `ls -l` shows `lrwxrwxrwx … name -> ../.git/annex/objects/<hashdirs>/<key>/<key>`; when content is absent the symlink is **dangling** — `ls` shows it, `cat` fails with ENOENT, `stat -L` fails. The key (hence the exact byte size) is legible directly from the link target.
- *Unlocked (pointer file)*: `ls -l` shows a **regular file** whose content is the text `/annex/objects/<key>` (plus optional newline). "A pointer file starts with `/annex/objects/`, which is followed by the key… Pointer files usually have a newline after the key… The maximum size of a pointer file is 32 kb." Every subsequent line must contain `/annex/` and end in a newline, "Otherwise it [is] not considered to be a valid pointer file" — source: git-annex, `doc/internals/pointer_file.mdwn` @6bc1790. The stated rationale is a safety invariant worth stealing: "The possibility exists that a pointer file is in a working tree, representing an annex object that is not present, and something appends data onto it accidentally. The limitation that each line of a valid pointer file contains `/annex/` and that it cannot be larger than 32kb let such a situation be detected."
- *Unlocked with content present*: a real file (a copy, or — with `annex.thin` — a hard link to the object).
- *`git annex adjust --hide-missing`*: absent files are **removed from the tree entirely** — "Only include annexed files in the adjusted branch when their content is present." `ls` does not show them at all. The branch is not live: "The adjusted branch is not immediately changed when content availability changes, so if you `git annex drop` files, they will become broken links in the usual way"; refresh by re-running, or set `annex.adjustedbranchrefresh` — source: git-annex, `doc/git-annex-adjust.mdwn` @6bc1790.
- *`git annex adjust --unlock-present`*: "Unlock files whose content is present, and lock files whose content is missing" — i.e. present files are ordinary files, absent files are dangling symlinks — source: same. **This is arguably the single best UX in the entire survey for the stated product intent: materialized = normal file, released = visible placeholder, automatically.**

**Fetch / release / query:**
- `git annex get` fetches content; `git annex drop` releases it. "git-annex will refuse to drop content if it cannot verify it is safe to do so. Usually this involves verifying that the content is stored in some other repository." The failure output is explicit: `drop photo2.jpg (unsafe) / Could only verify the existence of 0 out of 1 necessary copies / Rather than dropping this file, try using: git annex move / (Use --force to override this check, or adjust numcopies.)` — source: git-annex, `doc/git-annex-drop.mdwn` @6bc1790.
- `git annex drop --auto` drops "only those [files] that are not preferred content of the repository" — source: same. **This is the nightly-release job, already built.**
- Listing what is absent: `git annex find --not --in=here` — "To list annexed files whose content is not present, specify `--not --in=here`" — source: git-annex, `doc/git-annex-find.mdwn` @6bc1790. Matching options support boolean composition, e.g. `--include='*.mp3' --and -( --in=usbdrive --or --in=archive -)`, and time travel (`--in=here@{yesterday}`) — source: `doc/git-annex-matching-options.mdwn` @6bc1790.
- Offline "where it really is": `git annex whereis` prints per-file repo UUIDs and descriptions with a copy count, and "**does not contact remotes** to verify if they still have the content of files. It only reports on the last information that was received from remotes" — source: git-annex, `doc/git-annex-whereis.mdwn` @6bc1790. The ledger is replicated in the `git-annex` branch.
- `git annex examinekey` is "given a key, and prints information that can be determined **purely by looking at the key**", with format vars `${bytesize}`, `${humansize}`, `${backend}`, `${keyname}`, `${mtime}`, `${objectpath}`, `${objectpointer}`, plus `--json` — source: git-annex, `doc/git-annex-examinekey.mdwn` @6bc1790. **`${objectpointer}` is literally "render me the placeholder for this key".**
- `git annex unused` "Checks the annex for data that does not correspond to any files present in any tag or branch, or in the git index, and prints a numbered list"; the results feed `--unused` in other commands, e.g. `git annex unused; git annex move --unused --to origin` — source: git-annex, `doc/git-annex-unused.mdwn` @6bc1790. Note the recommended verb is **move** (relocate, then drop), not delete — a safer eviction shape than `lfs prune`.

**Safety numbers:**
- `numcopies` (default 1) is stored *in the git-annex branch* so "it will be seen by all clones"; overridable per-file via the `annex.numcopies` attribute in `.gitattributes`, or `--numcopies`. "When git-annex is asked to drop a file, it first verifies that the number of copies can be satisfied among all the other repositories that have a copy." Known limit: "In unusual situations, involving special remotes that do not support locking, and concurrent drops of the same content from multiple repositories, git-annex may violate the numcopies setting. **It still guarantees at least 1 copy is preserved.**" — source: git-annex, `doc/git-annex-numcopies.mdwn` @6bc1790.
- `mincopies` (default 1) is the hard floor honoured even in those racy cases; upstream advice: "Set numcopies as well, to a larger number, and keep mincopies at the bare minimum you're comfortable with" — source: git-annex, `doc/git-annex-mincopies.mdwn` @6bc1790.
- `required` content is enforced against drop; `wanted`/preferred content is advisory — see below.

**Unlocked-mode space/safety tradeoff:**
- `git annex unlock` "changes how it is stored in the git repository (from a symlink to a pointer file), so this command will make a change that you can commit" — source: git-annex, `doc/git-annex-unlock.mdwn` @6bc1790.
- `annex.thin`: "make unlocked files be a hard link to their content in the annex, rather than a second copy. This can save considerable disk space, but **when a modification is made to a file, you will lose the local (and possibly only) copy of the old version.** Any other, locked files in the repository that pointed to that content will get broken as well (`git-annex fsck` will detect and clean up after that). So, enable this with care." Also: "this has no effect when the filesystem does not support hard links. And when multiple files in the work tree have the same content, only one of them gets hard linked" — source: git-annex, `doc/git-annex.mdwn` @6bc1790. **Hard-linking is the unsafe CoW; reflink/`FICLONE` (what `git lfs dedup` uses) is the safe one.**

**Smudge/clean behaviour — the performance lesson:**
- Filter config is `smudge = git-annex smudge %f`, `clean = git-annex smudge --clean %f`, with `* filter=annex` normally placed in `.git/info/attributes` by `git annex init` — source: git-annex, `doc/git-annex-smudge.mdwn` @6bc1790.
- "**The smudge filter does not provide git with the content of annexed files, because that would be slow and triggers memory leaks in git.** Instead, it records which worktree files need to be updated, and `git annex smudge --update` later updates the work tree to contain the content. That is run by several git hooks, including post-checkout and post-merge. However, a few git commands, notably `git stash` and `git cherry-pick`, do not run any hooks, so after using those commands you can manually run `git annex smudge --update`" — source: same. Corroborated independently by git-lfs: "all currently available versions of Git (v2.51.2 and earlier) read the output of a long-running filter process like Git LFS into in-memory buffers, one for each file processed by the filter. As a result… Git's memory usage scales with the size of the largest Git LFS file" — source: git-lfs, `docs/man/git-lfs-faq.adoc` @20be8f8. **Two independent implementations converged on: do not stream content through the smudge filter; write placeholders and materialize out-of-band via hooks.**

### 6. DVC, XetHub/xet-core, and LFS alternatives

- **DVC** replaces each tracked path with a small `.dvc` YAML file in git; content lives in a cache. Materialization link strategy is `cache.type`, validated against exactly `{"reflink", "hardlink", "symlink", "copy"}` — source: iterative/dvc, `dvc/config_schema.py:46` @56e59829512ff134aa269099a2099587b810b4dd (2026-08-06). Default ordering is `reflink,copy` in practice; `symlink`/`hardlink` make the worktree file read-only-by-convention and risk cache corruption on edit — the same tradeoff as `annex.thin`.
- **DVC's availability model is a first-class status command.** `dvc data status` classifies into `not_in_remote` ("use `dvc push <file>…` to upload files"), `not_in_cache` ("use `dvc fetch <file>…` to download files"), `committed`, `uncommitted`, `untracked`, `unchanged` — source: iterative/dvc, `dvc/commands/data.py` (`CmdDataStatus.LABELS`/`HINTS`) @56e5982. **`not_in_cache` is exactly the "virtual / dematerialized" state, and it is presented as a normal status class with a remediation hint rather than an error.**
- `dvc fetch` = cache-only download; `dvc pull` = fetch + checkout (link into worktree); `dvc gc` is the eviction command — source: iterative/dvc, `dvc/repo/gc.py` @56e5982 (function `gc`). `.dvcignore` (`DvcIgnore.DVCIGNORE_FILE = ".dvcignore"`, gitignore-syntax patterns compiled per-directory into a trie) excludes paths from DVC's *traversal*, not from fetching — source: iterative/dvc, `dvc/ignore.py:32-33, 41, 263-322` @56e5982. **DVC has no per-path "never fetch this" file; granularity is whole-`.dvc`-target.**
- **XetHub / xet-core** (now HuggingFace's storage backend) replaces whole-file LFS objects with content-defined chunking: ~64 KiB Gearhash-boundaried chunks, deduplicated against the current session, a local metadata cache, and a global dedup query; explicitly "backwards compatible with Git LFS" — sources: huggingface/xet-core README, https://github.com/huggingface/xet-core (accessed 2026-08-22); HuggingFace docs "Deduplication", https://huggingface.co/docs/hub/xet/deduplication; "Xet Protocol Specification", https://huggingface.co/docs/xet/index. Relevance: chunk-level dedup makes *partial* materialization (byte ranges) coherent, which whole-object LFS cannot express.
- **hf-mount** is the system-level presentation done properly and recently: it "presents a standard filesystem interface (FUSE or NFS) and translates file operations into Hub API calls and storage fetches", with a disk cache layer that is either chunk-range (xorb ranges) or whole-file keyed by xet hash — source: huggingface/hf-mount README, https://github.com/huggingface/hf-mount (repo published ~2026-07-09, accessed 2026-08-22); HF changelog "Introducing hf-mount", https://huggingface.co/changelog/hf-mount.
- **VFS for Git / ProjFS** is the cautionary tale for system-level presentation: it "virtualizes the file system beneath your Git repository so that Git and all tools see what appears to be a regular working directory, but VFS for Git only downloads objects as they are needed" — source: microsoft/VFSForGit README, https://github.com/microsoft/VFSForGit (accessed 2026-08-22). It is now maintenance-only, superseded by Scalar, which uses **partial clone + sparse-checkout instead of virtualization** — sources: microsoft/VFSForGit `docs/faq.md`, https://github.com/microsoft/VFSForGit/blob/master/docs/faq.md; GitHub Blog, "The Story of Scalar", https://github.blog/open-source/git/the-story-of-scalar/, published 2022-10-13. The stated reason for abandoning the macOS port: "they needed cross-platform support, specifically for macOS development. After getting pretty far in a macOS port, **Apple deprecated the kernel features that provided the filesystem virtualization** that was required for that flow" — same GitHub Blog source. **[INFERENCE] On macOS today the surviving supported route to online-only file semantics is FileProvider (an extension, sandboxed, per-provider domain), not a kernel filesystem; that is a materially larger commitment than a pointer-file design.**
- **Transport alternatives.** `lfs.standalonetransferagent` "Specifies a custom transfer agent to be used if the API server URL matches… git-lfs will not contact the API server" (stage-2 transfer actions become null); `lfs.customtransfer.<name>.{path,args,concurrent,direction}` define the agent — source: git-lfs, `docs/man/git-lfs-config.adoc` @20be8f8 and `docs/custom-transfers.md`, https://github.com/git-lfs/git-lfs/blob/main/docs/custom-transfers.md. `git lfs standalone-file` is the built-in adapter for `file:///` URLs: "By default, Git LFS requires the support of an HTTP server… however, this tool allows the use of URLs starting with `file:///`… Configuration is not necessary; Git LFS handles this internally" — source: git-lfs, `docs/man/git-lfs-standalone-file.adoc` @20be8f8.
- **Pure-SSH LFS**: released in git-lfs v3.0.0 (2021-09); the client attempts `git-lfs-transfer` over SSH and falls back to `git-lfs-authenticate` + HTTP if the server does not respond positively — sources: git-lfs/git-lfs PR #4446 "Pure SSH-based protocol", https://github.com/git-lfs/git-lfs/pull/4446; charmbracelet/git-lfs-transfer README, https://github.com/charmbracelet/git-lfs-transfer (Go port of bk2204/scutiger, the Rust reference implementation); Gitea docs, https://docs.gitea.com/administration/git-lfs-setup/ (`LFS_ALLOW_PURE_SSH`). **UNVERIFIED**: I did not retrieve a primary source for `git-media` (the pre-LFS ancestor) or for Perforce Helix Core / Unity plugin behaviour; treat any claim about those as unsupported. What is verified for Helix-style workflows is only the *lock* concept, which git-lfs mirrors via `--lockable` (above).

## Applicability to a git-LFS-backed virtual-file design

1. **Do not build a filesystem.** The one git project that virtualized the FS (VFS for Git) is in maintenance mode and its macOS port died on deprecated kernel APIs; its successor deliberately retreated to partial clone + sparse-checkout. A pointer-file design is what both surviving tools ship, is inspectable with `cat`, survives `rsync`/backup/`tar`, and needs no privileged component on a headless server. Reserve any FUSE/FileProvider layer as a strictly optional *presentation* over an authoritative pointer-file state.
2. **The "don't fetch this" pattern file already exists and is honoured by three code paths.** `lfs.fetchexclude` in a committed `.lfsconfig` is simultaneously (a) a fetch filter, (b) a smudge filter — pointers pass through unchanged — and (c) a prune eligibility rule. Any bespoke pattern file should be *compiled into* the same semantics, and should use gitignore syntax, because that is what all four surveyed tools use.
3. **Metadata offline is free — take it.** The pointer already carries `oid sha256:…` and exact `size`. The missing pieces relative to the product intent are (i) mtime/type and (ii) "where it really is". git-annex proves (ii) needs a *replicated ledger* (the `git-annex` branch + `whereis`), not a live query, and that stale-but-offline is the right answer: `whereis` explicitly "does not contact remotes". Type is derivable from extension; mtime is the one datum LFS genuinely lacks (git-annex bolted it into the key as `-mNNNN`, WORM-only).
4. **Report availability as a status class, not an error.** DVC's `not_in_cache` + "use `dvc fetch <file>…`" and git-lfs `ls-files`' `*` vs `-` are both cheap, scriptable, JSON-capable. Emit both a machine format (imitate `rev-list --missing=print-info`'s `path=`/`type=` records) and a human one.
5. **Materialize via reflink, and fsync first.** `git lfs dedup` establishes CoW-from-the-object-store as the sanctioned mechanism and establishes hard failure when unsupported. Issue #6312 establishes that block-cloning an object not yet flushed to disk produces **zero-filled worktree files** — the fsync-before-clone ordering is mandatory, not an optimization. Never use hard links (`annex.thin`'s documented data-loss mode).
6. **Release must be verify-then-drop, and must never touch modified files.** Compose git-annex's rule (refuse unless N copies verified elsewhere; `mincopies` floor of 1) with git-lfs `checkout`'s rule ("Modified files are never overwritten"). Concretely: release a materialization only if (a) the worktree file's hash still equals the pointer's `oid`, (b) the object exists in the local store *or* the remote positively confirms it (`--verify-remote` semantics, `when-unverified=halt`), (c) the path is not locked, (d) the path is not `required`. Then rewrite the placeholder. Prefer git-annex's `move --unused --to origin` shape (relocate then drop) over unlink-and-hope.
7. **Track last *use*, because nothing upstream does.** `lfs.pruneoffsetdays` is the only shipped "grace period" and it is measured against ref recency, not access. A 24h-after-last-use policy therefore has no prior art to copy and must be built: record materialization time and last-open time explicitly (atime is unreliable under `relatime`/`noatime`). This is the single largest genuinely-new component.
8. **Two safety invariants worth copying verbatim.** (a) git-annex's pointer-file validity rule — bounded size (32 KiB) *and* every line contains a fixed marker — exists precisely so that "something appended data onto the placeholder" is detectable rather than silently committed. (b) git-lfs's canonical-encoding rule (`pointer --check --strict`) makes "is this a placeholder or real content?" a total, cheap predicate. Both are prerequisites for a safe release step.
9. **Server-side (`keeper-syncd`) caveat from upstream:** git-lfs explicitly warns against running `prune` when repositories share a storage directory. A shared server-side object store must therefore do refcounting across all clones itself; per-clone eviction logic is unsafe there by construction.
10. **Do not expect partial clone to help.** LFS objects are not git blobs; `--filter` cannot describe them, and `git lfs prune` is documented-broken under partial clone (#4335, open since 2020). Sparse-checkout is likewise orthogonal — but note the *interaction trap*: since Git 2.42, `git lfs checkout/pull` skip files whose `.gitattributes` are not checked out, so a virtual-file design must set `GIT_ATTR_SOURCE=HEAD` or guarantee `.gitattributes` presence.

## Risks / failure modes

- **Eviction is the data-loss surface, empirically.** git-lfs has shipped fixes for pruning stash-referenced objects (#4209) and index-staged files (#5637), and *still* deletes objects reachable only from orphaned commits by design (reflog ignored). A retention-set-enumeration design will keep growing these bugs; a positive-confirmation design ("the remote told me it has this OID") will not.
- **Zero-filled materialization.** Block-cloning an object before it is flushed yields all-zero worktree files (#6312, open). Silent, passes any check that only compares file *size*.
- **Placeholder/content confusion in both directions.** A pointer accidentally appended-to becomes a corrupt file that looks committable (git-annex's stated motivation for its 32 KiB + `/annex/` invariant); conversely, real content whose first bytes happen to parse as a pointer is why git-lfs added `pointer --check --strict`.
- **Smudge-filter memory blowup.** Streaming content through the filter makes git's peak RSS scale with the largest file (git-lfs FAQ) and "triggers memory leaks in git" (git-annex). On a server syncing many large files this is a hard failure, not a slowdown. Placeholder-then-hook is the only proven shape.
- **Hooks are not universal.** git-annex names `git stash` and `git cherry-pick` as commands that run no hooks, leaving the worktree stale until `smudge --update`/`fix`. Any hook-driven materialization needs an idempotent reconciliation command and something that calls it.
- **Adjusted-branch staleness.** `--hide-missing` does not update on content change; the tree lies until re-run or `annex.adjustedbranchrefresh` fires. Any "hide released files" presentation inherits this.
- **Lazy-fetch storms.** Partial clone's documented failure is that any history-walking command leaves the pre-selected subset and serially backfills; upstream's only mitigation is pre-fetching. An on-demand materializer must rate-limit, batch, and be able to *refuse* (fail loudly) rather than fetch a thousand objects because someone ran a recursive grep.
- **Offline hard-dependency.** Partial clone "requires that the user be online". A pointer-file design must not inherit this: metadata queries must be answerable with zero network.
- **Shared object store + per-clone prune = deletion of another clone's only copy** (explicit git-lfs warning re `lfs.storage`).
- **`.gitattributes` availability trap** (Git ≥2.42) silently reduces `lfs checkout`/`pull` to a no-op under sparse checkout.
- **Hard-link "thin" mode loses the old version on first write** and breaks every other worktree file sharing that object (`annex.thin`).
