## The defect: a drive is chosen, and nothing tells the engine

The owner's hypothesis for item 5 was that keeper never creates the configuration folder. It does not — but not because the code that creates it is broken. The folder is created by `TaskLedger::write_run` (`ledger.rs:546-549`, `create_dir_all` on the year directory), and that code is never reached, because the run never receives a `TaskLedger` at all. The chain, each link in the shipped build:

1. **Settings writes a choice, and only a choice.** The Tasks section's picker calls `syncTasksLedgerSet(profileId)` (`tasks-section.tsx:49-65`). The command, `sync_tasks_ledger_set` (`sync_ipc.rs:2482-2497`), writes exactly two things: the machine-local registry key `tasks.ledger_vault` (`:2492`, `registry.rs:1332-1334`, the `KeySpec` at `keys.rs:519-528`) and, through `Engine::set_ledger_profile` (`engine.rs:2539-2541`), the `sync.db` meta row `tasks.ledger_profile` (`db.rs:4551-4563`). It writes nothing into the drive.
2. **The engine requires a flag the choice never sets.** `perform_copy_task` asks for its ledger at `engine.rs:4332` (`self.task_ledger(task, profiles, &fingerprint)`), which delegates to `task_ledger_for` (`engine.rs:4243-4280`). Its `eligible` closure (`:4249-4255`) admits a profile only when `profile.tasks.is_some()` (`:4250`) — that is, only when `SyncProfile.tasks` carries a `TasksConfig`, which is the `[folder.tasks]` table of the drive's own `.keeper/keeper.toml` or a value on the stored profile row. The chosen profile is filtered out before it is even compared with the choice (`:4256-4259`), the fallback finds no other flagged profile (`:4260`), and the `?` returns `None`.
3. **No surface writes that flag.** `SyncProfile.tasks` has two writers in the whole product: the folder-file overlay, where `tasks` is an `Allowed` key (`folder.rs:162`) that somebody types into `.keeper/keeper.toml` by hand, and `upsert_profile`, which no task surface calls with `tasks` set. The folder form cannot express it — `tasks` sits in `PRESERVED` (`sync_ipc.rs:5383-5386`), and the shell's own guard test says so out loud: *"The task ledger's flag, which no form expresses yet (Story 74.3)"* (`sync_ipc.rs:5505`). The notes drive has `notes_vault_flag` (`notes_ipc.rs:1238-1263`); tasks has no counterpart.
4. **A ledger-less run leaves nothing to read.** With `ledger == None`, `latest_mark` is never asked (`engine.rs:4333-4335`, so every pass is a full pass), `write_run` is never called, and the close carries `ledger_entry: None`, so `task_runs.ledger_entry` stays `NULL`.
5. **The panel renders the refusal.** Opening the run calls `sync_task_run_log` → `Engine::task_run_log` (`engine.rs:12393-12413`), which meets the `NULL` at `:12403-12407` and answers *"This run has no ledger log. Its detail is the available record."* — the owner's sentence.

**Measured on hesperia, not only read in the code:** `meta.tasks_ledger_profile = 01KYKB3P5YT754K6SG43ACQA61`; every row of `task_runs` has `ledger_entry` `NULL`; none of the three drives' `keeper.toml` carries a `tasks` key. The owner did what the section invited him to do — it lists **every** profile (`tasks-section.tsx:93-97`), not only flagged ones — and the engine, correctly by its own rule, ignored him.

Why the tests were green: `tasks-section.test.tsx:14-20` mocks `syncTasksLedger` to answer a resolved `/archive/tasks`; the ledger-selection test in the engine (`engine.rs:18817-18876`) flags every fixture profile at `:18823` before choosing one; every copy-task fixture in `db.rs` seeds `TasksConfig { subfolder: "tasks" }` (`:7204-7206`); and the one test that runs a copy with no ledger (`engine.rs:19340-19369`) makes no choice at all. The exact state the owner is in — a choice, and zero flags anywhere — runs in no test on either side of the IPC.

## What last week decided, and what this epic reverses

AD-285 (epic 78) made the *selector* machine-local and the *flag* a folder-file fact, and wrote the rule that *"an unknown or unflagged choice costs nothing, never a run"* — meaning a choice that names an unflagged profile silently falls back to the first flagged one. Story 78.5 specified the picker as *"a `Select` over the profiles the listing reports as carrying `[folder.tasks]`"* and deferred the form control that would let anyone set that flag (*"DW-258's picker half stays open"*). The shipped section offers every profile instead, which is the better behaviour and the one this epic keeps — but combined with AD-285's silent fallback and no flag control anywhere, it shipped a choice the engine could not honour and a run log the owner could not get.

This epic reverses two sentences of AD-285, on the owner's word and the field measurement, and says so here rather than pretending they were never written:

- *"an unknown or unflagged choice costs nothing, never a run"* becomes: an **unknown** choice (a profile id that is gone) still costs nothing and falls back; an **unflagged** choice of a profile that exists is honoured, with the default subfolder, because choosing the drive is the act (AD-297).
- *"the selector second"* over flagged profiles becomes: the selector offers every drive, and choosing one is what flags it (AD-297, AD-298).

Everything else in AD-285 stands: the key is machine-local (`keys.rs:519-528`), the engine is told through `meta` rather than left to read the registry (`db.rs:4540-4563`), the daemon honours the same row (`commands.rs:4273-4312`), and Settings shows what actually resolved. The `folder.rs:154-161` argument — a ledger exists so the *other* machine can read it — is not overturned; it is why AD-297 writes the folder file instead of only the stored row.

## The one sentence

**A drive that was chosen and never flagged, a flag no form can set, a copy row that says "the whole machine" over two concrete paths, a name that is hidden under an id nobody chose, a manual task with a schedule box under it, and two paths with no way to Finder: choosing the drive becomes the whole act, tasks joins the drive-role family with its own icon, a copy says what it acts on, the description becomes the name, the form shows only what its mode uses, and every path is one click from Finder.**

## Decisions this epic takes

- **AD-297 — Choosing the drive is the whole act.** **Binds:** FR-646, FR-647, FR-648, FR-649, FR-650, NFR-85, NFR-87; Story 80.1; D-23. **Prevents:** a choice the engine cannot honour; a run that is ledger-less because a file could not be written; a folder that exists on this machine's word only; a second write to a synced file for a value it already holds; a hand-written `keeper.toml` rewritten by keeper; Settings that says *configured* over a folder that does not exist. **Rule:** Two halves, both required. *(a)* `task_ledger_for` (`engine.rs:4243-4280`) admits the **explicitly chosen** profile when it exists and matches the task's scope, whether or not it carries `tasks`, and resolves its subfolder as `candidate.tasks.as_ref().map_or(DEFAULT_TASKS_SUBFOLDER, |c| &c.subfolder)` (`profile/mod.rs:236`); a profile that is *not* the choice is admitted only when flagged, exactly as today, so *keeper decides* (no choice) still requires a flag and `a_copy_without_a_ledger_folder_still_runs_and_writes_nothing_extra` (`engine.rs:19340`) stays green. `Engine::tasks_ledger` (`:2543-2556`) mirrors the same rule so the Settings read side and `keeper-syncd tasks ledger` (`commands.rs:4273-4312`) say what will actually run; `task_ledger_path_for` (`:2570-2577`) follows. *(b)* `sync_tasks_ledger_set(profile_id, subfolder)` writes the registry key and the `meta` row **first** (so the choice is honoured through (a) whatever happens next), then writes `[folder.tasks]\nsubfolder = "<subfolder>"` into `<drive>/.keeper/keeper.toml` through one writer, `profile::folder::write_tasks_key(local_path, subfolder) -> Result<FolderWrite>`, creating `.keeper/` and the file when absent; the writer's outcome (`Written | Unchanged | Refused(sentence)`) is returned to the section rather than turned into an error, because the choice already took. The subfolder defaults to `tasks`, is editable in the same section, and passes `TasksConfig::validate` against the profile's notes, recordings and sessions blocks (`profile/mod.rs:768-831`) before any write. Clearing the choice (*Keeper decides*) writes no file and removes nothing: the flag is a repository fact and a machine-local un-choice must not unflag a folder other machines read. The ledger directory itself is still created by the first run (`ledger.rs:546-549`); Settings shows the resolved path, whether it exists on disk yet, where the flag came from — the folder file, this machine's profile row, or the default applied to a chosen drive — and the writer's sentence when the file could not be written.

- **AD-298 — A tasks drive is marked like a notes drive.** **Binds:** FR-651, FR-652; Story 80.2; closes DW-258. **Prevents:** a flag reachable only by hand-editing a file; a role vocabulary that lags the flag family (`sessions` already does — DW-282); a Files tree that marks a folder by its name. **Rule:** `tasks` joins `notes`, `recordings` and `sessions` in the folder form on the sessions row's exact shape (`add-folder-form.tsx:1897-1939`): `SyncProfileVm { tasks: bool, tasks_subfolder: String }` resolved in Rust to the stored value or `DEFAULT_TASKS_SUBFOLDER` (the `sessions_subfolder` rule, `sync_ipc.rs:280-284`), `SyncProfileReq { tasks: Option<bool>, tasks_subfolder: Option<String> }` with the recordings/sessions verbatim-subfolder rule (`:1203-1215`), a fourth block in `parse_req` (`:1165-1184` is the model), and `tasks` moved from `PRESERVED` to `EXPRESSED` (`:5309`, `:5369`) the way `recordings` moved in Story 41.7. A key the folder file owns disables the switch with `syncFolderOwnedNote("tasks")` (`add-folder-form.tsx:436-438`), which is what makes the two tiers coexist: the form writes this machine's row, Settings (AD-297) writes the file, and when the file speaks the form says so and steps back. The Files tree gains `FilesFolderRoleVm::Tasks` — `FilesFolderRoles.tasks_subfolder` (`vm.rs:4166-4173`), a third arm in `role_of` (`:4197-4211`, notes wins a tie as today, then recordings, then tasks), passed from `profile.tasks` at `sync_ipc.rs:3474-3480` — rendered with the Tasks surface's own glyph (`CalendarClock`, the sidebar's `TASKS_VIEW` icon at `sidebar-pane.tsx:131`) and the title *Where task ledgers are written* in `FOLDER_ROLE_ICON`/`FOLDER_ROLE_TITLE` (`files-pane.tsx:621-631`). Any drive may hold task ledgers; the machine-local key picks which one this machine writes to.

- **AD-299 — A task says what it acts on, not where it is hosted.** **Binds:** FR-653, FR-654, FR-660, NFR-86; Story 80.3; UX-DR110. **Prevents:** a copy row that claims *the whole machine* over two paths it names; a React row re-implementing `same_folder_path`'s case and separator rules (`vm.rs:4214-4218`); a path that cannot be read because the row is 320 px wide. **Rule:** `TaskVm` gains `copy_source_facts: Option<TaskPathFacts>` and `copy_destination_facts: Option<TaskPathFacts>` with `TaskPathFacts { drive: Option<String>, drive_id: Option<String>, exists: bool }`, composed in Rust beside `mark_ms` and `ledger_path` (`sync_ipc.rs:1902-1968` reads a row and decides nothing about the filesystem; the caller that already holds the engine and the profile list does): `drive` is the name of the profile whose `local_path` contains the path — the same `same_folder_path` normalisation the Files tree uses, applied to the profile root as prefix — or `None` for *outside any drive*; `exists` is one `symlink_metadata` per path and no walk (NFR-86). The row's second line renders `source → destination` for a copy task, truncated, with a `HoverHint` carrying the full pair and each path's drive beneath; the detail's line (`tasks-pane.tsx:1679-1681`) becomes two full-width path facts, each naming its drive or *outside any drive*; the run panel's Source/Destination lines (`panel-strip.tsx:643-651`) say the same. The host **block** (`:1755-1769`) is untouched: its sentence is Rust's and is about where the task runs, which is a different question. The shared `HoverHint` primitive change (UX-DR110: 600-weight label, muted detail, 4 px gap, no three-line clamp, 320 px maximum, `tooltip.tsx:69-70`) lands in this story because this rung sits below epic 79's and two rungs editing one file for one reason is how a rung stops compiling alone; epic 79's call sites arrive on top.

- **AD-300 — A task gets a name; its id stays its id.** **Binds:** FR-655, FR-656; Story 80.4. **Prevents:** a rename that orphans `task_runs`, a ledger folder and a `task.toml` at once; a row titled by a ULID nobody chose; a hover hint that invents an id or a name. **Rule:** `TaskVm.id` is immutable — quoted from `tasks.rs:343-347`: *"`Self::id` is minted by Rust when the form leaves it blank, and it can never be changed afterwards because `task_runs.task_id` joins on it — so an id is either a ULID nobody chose or a word chosen once, and this is where a second thought about the wording has to go."* `description` **is** that place, and the surface finally says so: the form labels the box *Name* and keeps the id box with its edit-time sentence (`task-form.tsx:975`); the row (`tasks-pane.tsx:1521`), the detail heading (`:1668`), the history disclosure's accessible name, the run panel's heading once its read has landed (`panel-strip.tsx:783-797`, the `useNoteTitle` pattern) and the unknown-row title (`:3243-3245`) render the name; the id is the `HoverHint` detail and the detail's small print. A task with no name (`null` or blank — `taskDescriptionText`'s rule) is titled by its id exactly as today, so no fixture that leaves `description: null` changes shape. The real rename — `UPDATE task_runs`, `fs::rename` of the ledger directory, a `task.toml` rewrite, a new command — is refused in *What stays out* with that reason.

- **AD-301 — A form shows only the fields its mode uses.** **Binds:** FR-657, FR-658; Story 80.5; UX-DR109. **Prevents:** a schedule box under a task that will never obey it; a stored schedule cleared by a mode switch; two idioms for one three-way choice. **Rule:** With mode `manual` — and `off`, which uses none of them either; the AD's title is the rule and manual is the instance the owner hit — the schedule box, its preview, the offers menu, the missed-window policy and the delay box are not rendered (`task-form.tsx:1132-1258`). The form state keeps `schedule`, `onMissed` and `missedDelayMinutes` untouched across the switch, and a save in `manual` sends the stored schedule unchanged, so `tasks::decide`'s *remembers a schedule without obeying it* (`:177-178`) remains true and switching back to `scheduled` shows what was typed. The mode (`:1036-1048`) and the missed-window policy (`:1225-1237`) become the house `RadioGroup` (the `export-dialog.tsx:39` / `settings-dialog.tsx:39` precedent) — three exclusive options each, UX-DR109's rule; the kind menu (six options, `:1011-1028`) and the folder menu (an open list with an empty-string sentinel, `:1079-1099`) stay native, and the comment at `:1069-1074` is rewritten to state that rule instead of *"all three menus here are native"*. Settings' ledger-folder `<select>` stays native too (the ScoutBar2 inventory keeps it: an open list of drives).

- **AD-302 — Every path a task names is one click from Finder.** **Binds:** FR-659; Story 80.6. **Prevents:** a second reveal command; an enabled button over a path that is not there; an error state for the normal condition of a copy task that has never run. **Rule:** The copy task's source and destination each get *Reveal in Finder* (the house label, `files-pane.tsx:267`) in the detail beside the path fact and in the row's context menu (`tasks-pane.tsx:1540-1569`), over the existing `revealPath` → `reveal_path` (`ipc.rs:2832-2840`), gated by the same desktop capability the run row's reveal already relies on. When `TaskPathFacts.exists` is `false` the control is disabled and a sentence beside it says the folder is not there yet — for a destination, *created by the first run* is the normal state, not a fault. Nothing here stats a path in React: the fact arrives on the VM (AD-299).

## The failure shape this epic must not repeat

Two, both from this epic's own history.

**An offer the engine cannot honour, proved by a test that mocked the engine.** The Settings section listed every drive; the engine accepted only flagged ones; the section's test answered the resolution from a mock and never asked the engine anything. 80.1's regression runs the real chain — a choice, a run, a file, a log — and its mutation clause names the one line whose restoration must turn it red. A Settings test over a mock may prove the section renders what it is told; it may not be the only test of whether the owner gets his log.

**A guarantee stated in a comment and enforced nowhere.** `folder.rs:154-161` says the ledger exists so the other machine can read it; nothing wrote the fact the other machine would read. AD-297's writer is bounded by NFR-85 to the byte, and its outcome is a sentence on screen, because a write into a synced file that fails silently is the same class of lie as a choice that fails silently — this time on the other machine.

**The risk lives in the shell crate, which cannot compile on this host.** `sync_tasks_ledger_set`, the `SyncProfileReq` block, `task_vm`'s new facts and the roles composition are all `crates/keeper/**`; every one is *by inspection, awaits CI macOS*, and every core signature changed under it (`tasks_ledger`'s return type, `FilesFolderRoles`'s field, `task_vm`'s arity) is grepped for callers in the same change. The engine default, the folder writer, the path attribution and the form's gating are provable on Linux with real files and jsdom, and that is where the proof goes.

## D-23 — keeper writes one key into a folder file, and a chosen drive is a ledger drive

The folder tier (epic 46, AD-98…AD-101) was built read-only: a synced folder's own
`.keeper/keeper.toml` is overlaid onto the stored profile at read time, the table never
learns what the file said, and the file wins. Nothing in keeper wrote such a file. Epic 74
put the task ledger's flag into that tier on purpose — a run recorded on one machine has
to be readable on the other, so the folder has to be a fact both machines read — and
epic 78 made the *choice* of drive machine-local. Between them, nothing set the flag, and
the owner's chosen drive never held a log.

- **What changes:** choosing a drive in Settings → Tasks writes `[folder.tasks]
  subfolder = "…"` into that drive's `.keeper/keeper.toml` (creating it), and the engine
  resolves an explicitly chosen drive with the default subfolder even when the key is
  missing, so an unwritable file costs a sentence and never a ledger-less run. Tasks
  joins notes, recordings and sessions in the folder form and the Files tree. (AD-297,
  AD-298; FR-646…FR-652; NFR-85, NFR-87)
- **The bounds on the write:** one block, keeper's own spelling, appended or replaced in
  place; every other byte identical; the same value is not rewritten (the file syncs,
  and a no-op rewrite is a commit); a file that does not parse, or spells the key
  another way, is refused with a sentence and left alone; the result is re-parsed before
  the rename. The reader is unchanged, so 0.8.31 reads what this build writes.
- **What it is not:** a general settings writer for folder files, a rewrite of
  hand-written keys, or a change to AD-98's rule that the file wins. The machine-local
  choice stays machine-local; clearing it removes nothing from the file.
- **What it amends:** AD-285's *"an unknown or unflagged choice costs nothing, never a
  run"* now applies to an unknown choice only; an unflagged choice of a drive that exists
  is honoured. Story 78.5's flagged-only picker is superseded by an every-drive picker
  whose choice is what flags.
- **Revisit triggers:** the daemon needing to read folder files (DW-279); a field-level
  TOML edit being required in the field (DW-280); a second key wanting to travel the
  same way (epic 79's spaces-folder setting names this writer; a table with more than
  one field needs field-level editing first).
- **Status / owner:** decided. Owner is the architect; Epic 80 implements it; NFR-85 is
  the bar.
