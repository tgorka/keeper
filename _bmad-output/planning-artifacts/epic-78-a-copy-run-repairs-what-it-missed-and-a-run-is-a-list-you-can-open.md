## The headline defect is not the one the owner suspected

The owner's hypothesis for item 30 was that keeper compares files by something too weak to notice a content change. It does not. When a file is examined, the decision is size first and then SHA-256 of both sides — `copy.rs:464` (`existing.len() != source_meta.len()`) and `copy.rs:490` (`digest == destination_digest`); modification time plays no part in the equality decision, and a changed file that reaches that predicate is always noticed.

The modified file never reached it. Before a file is examined it passes the watermark gate in `classify`, `copy.rs:1068-1069`: `if modified <= bound { return Ok(PlanItem::Behind) }` — not examined, not a line, not a count. The bound is the mark the last successful run left in its ledger file's **name** (AD-252, `engine.rs:4223-4225`, `ledger.rs:369-376`). And the mark is written at `engine.rs:4309-4314`:

```rust
mark_ms: report.mark_ms.unwrap_or_else(|| self.platform.now_ms()),
```

`report.mark_ms` is `None` whenever a run covered nothing markable — every file already behind the previous mark, or every file failed, or an empty source. In that case the run file is stamped with **the wall clock at the end of the run**. A wall-clock stamp is greater than every file modification time that exists, so from that run on, any file written before that instant — one written while the run was walking, one edited a minute before, one that *failed* that pass and would have been retried — satisfies `modified <= bound` on every later run and is Behind, forever. The run list shows the pass as `ok`; the file simply stops existing to the copy. That is item 30, and it is also the mechanism behind "copied half-written and never repaired": `stream_source`'s torn-read guard (`copy.rs:730-770`) correctly reports a file that changed mid-read as `Failed` — and the very next idle run hides it.

The engine's own comment three lines above claims the opposite: *"marked with the instant it finished, which advances nothing a file could hide behind"* (`engine.rs:4305-4308`). The ledger module's rule 1 says the opposite of the code too: *"The mark is the newest source modification time the run actually covered — never the wall clock"* (`ledger.rs:19-24`), and so does `CopyReport::mark_ms`'s own doc (`copy.rs:187-191`). No test exercises the fallback — the story-74.4 fixture (`engine.rs:18510-18639`) only walks the happy mark path (3000 → 5000). It shipped untested, and the ledger folder on hesperia is its fingerprint: a `run-<stamp>-…-ok-….md` whose stamp is a run's finish time rather than any source file's mtime.

Two more facts the owner must not read the wrong way:

- **Item 31 depends on whether a ledger folder is configured**, and nothing says so. A destination file that has gone missing takes `Publish::Fresh` (`copy.rs:445-447`) and is re-copied — but only if its source is examined. With no ledger there is no mark, every pass is full, and the hole is refilled (what he saw). With a ledger and a mark, a source behind the mark is Behind and its missing destination is *not* refilled. Two silent behaviours for one folder; AD-282 names both and gives each a default.
- **Item 33 is already true.** The server build is `keeper-syncd`, whose only first-party dependency is `keeper-sync` (AD-52, `keeper-syncd/Cargo.toml`), the crate the copy engine lives in; its CLI carries copy tasks end to end — `--copy-source`, `--copy-destination`, `--replace-existing` (`commands.rs:717-725`), `TaskKindArg::Copy` (`:911-924`), the `keeper-syncd-tasks@.timer` unit — and `check:syncd-lean` (`package.json:27`) keeps it that way. What is missing on the server is parity for the options this epic adds, and a sentence in the app: the seven host sentences (`keeper-core/src/tasks.rs:50-110`) never tell the owner that copy runs on the daemon too.

## The one sentence

**A copy that hashes every file it looks at but stamps the clock into its own memory when it looks at nothing, a deletion the module was built to refuse, a log that lists what did not change, a right pane that repeats the left one, and a server that already does all of it without saying so: the run keeps its memory honest, learns two named options, lists only what it changed, becomes something you can open, says where it lives, and offers the daemon every knob the app has.**

## Decisions this epic takes

- **AD-281 — A copy run's mark never advances to wall-clock time, and the watermark is read with a lookback.** **Binds:** FR-600, FR-601, FR-602, FR-603; Story 78.1. **Prevents:** a file written around an idle run being hidden forever; a failed file being hidden by the next idle run; a same-second edit on a coarse-mtime filesystem (HFS+ 1 s, FAT 2 s) falling behind the line; an invented instant in a file name that the ledger's own rules forbid; an idle run overwriting the previous run's file, or being invisible in the run list. **Rule:** The `unwrap_or_else(|| self.platform.now_ms())` at `engine.rs:4311` is deleted. The verdict vocabulary gains a fourth word, `RunVerdict::Idle`, spelled `idle`, meaning *ran, did everything it set out to do, and covered nothing* — the engine chooses it when `failed == 0 && report.mark_ms.is_none()`. `advances_mark()` is `false` for it, exactly as for `partial` and `failed` (`ledger.rs:167-171`), which is what makes "an idle run keeps the previous mark (or none)" a property of the ledger's own rule 2 rather than of a call site that could forget it. An advancing name (`ok`) always carries `report.mark_ms`; a non-advancing name (`partial`, `failed`, `idle`) carries the run's finish instant — the convention `RunFileName::mark_ms`'s doc already gives verify and gc (`ledger.rs:182-185`) — so every run still leaves exactly one file (78.4 depends on that) and no two runs share a name. An older keeper parses `idle` as *not a mark* (`RunVerdict::parse` returns `None`) and degrades in the safe direction: a full pass. An idle run is **legible, not invisible**: its `task_runs` row is `ok`, and its detail says why nothing happened and how much lies behind the line — `nothing newer than the mark (2026-09-19T14:02:11Z) — 1 204 files behind it` — from a new `CopyReport.behind: u64` that counts files the gate turned away and never lists them. The bound is read with a lookback: `bound = latest_mark − copy_lookback_ms` (new `tasks` column, `INTEGER NOT NULL DEFAULT 300000`, five minutes; `0 ..= MAX_SCHEDULE_INTERVAL_MS`, refused outside by `validate_copy_lookback_ms` beside `validate_missed_delay_ms`, `tasks.rs:1249`), and the gate becomes `modified < bound` → Behind: a file whose mtime equals the bound is examined. The cost of that inclusivity is one hash of the newest already-covered file per pass, which finds it `Identical` and moves nothing; the cost of the old exclusivity was a file lost on every filesystem whose clock is coarser than a millisecond. The lookback is applied where the mark is *read* (`engine.rs:4223`), never baked into a name: the ledger grammar is unchanged.

- **AD-282 — Deletion and restoration are two named options; the default is still a job, not a relationship.** **Binds:** FR-604, FR-605, FR-606, NFR-77, NFR-78; Story 78.2; D-22. **Prevents:** a mirror mode nobody asked for; a "sync" that eats a destination somebody is using as an archive; a destination deletion that comes back or does not come back depending on whether a ledger folder happens to be configured; a second full walk of the source to learn what it holds; keeper's own logs pruned from the destination. **Rule:** `CopyOptions` gains `prune_destination: bool` (default `false`) and `refresh_missing: bool` (default `true`). With `prune_destination`, **after** the copy pass, one walk of the destination removes every regular file with no counterpart in the source — the counterpart set is collected during the plan walk the copy already does (`plan_copy`, `copy.rs:930`), including paths the gate turned away and paths it refused, so nothing is walked twice — each reported as `CopyOutcome::Deleted`; directories the source no longer has are removed only once empty, deepest first, never through `remove_dir_all`; symlinks are never followed; `keeper-copy-*.log` at the destination root is keeper's own evidence and is never pruned. With `refresh_missing`, a source behind the bound whose destination file is missing is examined anyway (one `symlink_metadata` on the destination per behind file, no read, no hash — `classify` learns the destination root), so a hole is refilled whether or not a ledger is configured; with it off, the pass is *only what changed at the source since the last run* — the owner's other reading of item 31. AD-C1's sentence at `copy.rs:3-5` is **amended in place**: *"A copy here is a job, never a relationship: it walks a source once, moves the bytes, reports what happened to each file, and — unless the job was told to prune — changes nothing about either folder afterwards. Pruning is still a job: it removes what this walk proved absent and remembers nothing."* The default stays a job because the failure mode AD-C1 was written against — the classic tool that deletes the newer file on the wrong side — is the one a person hits without having chosen it; a person who chose `prune_destination` on a form that says what it deletes has chosen it.

- **AD-283 — The run log lists what changed; the summary keeps the counts, and the ledger body opens with a line a machine can read.** **Binds:** FR-607; Story 78.3 (the writer), Story 78.4 (the reader). **Prevents:** an 83-line log for one changed file; a collision — keeper refusing to change a file — hidden in a count, which would rebuild the silent-hole class this epic exists to close, one place over; a frontend that has to parse prose to learn whether anything changed. **Rule:** `render_copy_log` (`copy.rs:1288-1350`) writes a line for `copied`, `overwritten`, `deleted`, `left-alone` and `FAILED` (with its `reason:` line) and **no line for `identical`** — the header's counts line carries every outcome, in the order `copied, overwritten, identical, deleted, left alone, failed`. `identical` alone becomes counts-only because it is the one outcome that refused nothing: a collision is exactly "keeper would not touch this file", and the owner must be able to find that file by name a year later with no keeper installed (the module's own reason for plain text, `copy.rs:1279-1283`). `CopyOutcome` gains `Overwritten` — the replacing publish at `copy.rs:659-674` returns it instead of `Copied`, so "nadpisane" is a word in the log and a count in the summary rather than a copy that pretends it found nothing there. A run that changed nothing produces a header, a counts line and no file lines; the one-shot copy surface's `COPY_OUTCOME_ORDER` already renders a kind it does not know as itself (`copy-job.ts:53-59`), so the two new kinds reach it without a second vocabulary. The **ledger body's first line** is machine-readable — `keeper-run: copied=1 overwritten=0 deleted=3 identical=82 collision=0 failed=0 behind=1204` — written by `perform_copy_task` above `render_run_header`'s five human lines (`ledger.rs:530`), and `keeper-sync` owns both ends of that grammar: the writer in `engine.rs`, the reader beside `RunFileName::parse` in `ledger.rs`. It is what lets the run panel say *No files changed.* honestly at any pagination position — the fact is read from the file's head, never counted from whatever chunk happens to be mounted — and a ledger written before the line existed has no such fact, so the reader answers `None` and the pane renders no caption rather than a guess.

- **AD-284 — A run is a panel target with a bounded log reader, and the strip stops repeating the task.** **Binds:** FR-608, FR-609, FR-610, FR-611, NFR-76; Story 78.4; UX-DR104, UX-DR105. **Prevents:** a second `TaskDetail` beside the first; a run row that cannot be opened; a log reader that loads a 50 MB file to show its last screen; a chunk cut mid-line or mid-UTF-8; a DOM that grows without bound as older chunks arrive; a third context-menu idiom; a frontend that infers counts by parsing log lines. **Rule:** `task_runs` gains `ledger_entry TEXT` (nullable; the `<year>/run-….md` path inside the task's ledger, written by `perform_copy_task` when the entry is published; `NULL` for sync, bot, verify and gc runs, for a copy with no ledger, and for every row written before the column). `TaskRunVm.ledger_entry` carries it. A new read-only command `sync_task_run_log(run_id: i64, cursor: Option<u64>, max_bytes: u32) -> TaskRunLogVm { text, next_cursor, total_bytes, path, changed_files }` — `run_id` is the numeric `task_runs.id` that `TaskRunVm.id` already carries, and the client wrapper takes a `number` — resolves the row's `ledger_entry` through the engine's own `task_ledger` (`engine.rs:4166`) and reads **from the tail**: at most `MAX_RUN_LOG_CHUNK_BYTES` (64 KiB, keeper-core) per call, the chunk snapped forward to the first `\n` after its start so every chunk is whole lines and therefore whole UTF-8, `next_cursor` naming where the older chunk ends and `None` at the head; `max_bytes` above the cap is clamped, never refused; `total_bytes` is the file's length at the time of the read, so a caller that sees it change between pages knows the file moved under it; `changed_files: Option<u32>` is `copied + overwritten + deleted` from the body's `keeper-run:` head line (AD-283), read on every call from the file's head regardless of which chunk is being served, `None` when the line is absent. A run with no entry answers `Err` with a finished, Rust-composed sentence naming why (*this run left no log file — no ledger folder was configured; choose one in Settings → Tasks* / *this run's log file is no longer in the ledger* / *a sync run's record is its line above*), and the pane renders the sentence — never an empty box, never a diagnosis invented from a missing body. `PanelTargetVm` gains `run: { kind: "run", taskId, runId }` and **loses `task`**: a task row's plain click only selects (the pane's own detail column is unchanged); a run row's plain click previews the run into the strip and a double-click opens it beside, with the `Panel.replaced` semantics every sibling has (`panels.ts:270-287`); a `task` target in a saved cookie is dropped by `isTarget` under the existing trust-boundary rule (`:302-325`). Story 59.12's intent — the owner can open a task's record beside the list — survives as the task's runs; its mechanism, `TaskDetail` in the strip, is retired, and `panel-strip.test.tsx:1015-1028` moves with it rather than being re-pinned. The run panel is UX-DR105's: a heading naming task and run, the run's facts each on its own full-width line, then the log in a bounded scroll region — file order (older above newer; tail-first means *which bytes arrive first*, never reversed lines), the viewport positioned at the end when the tail lands, a toolbar outside the text holding *Load older* while `next_cursor` is present, at most 1 MiB of decoded text mounted with *Return to latest* once older pages would exceed it — and every count on it comes from Rust: the report sentence is rendered whole, the *No files changed.* caption is rendered only when `changed_files` is `Some(0)`, and nothing is derived from splitting the sentence or counting log lines. The runs disclosure gives the report its own full-width block (item 27; UX-DR105's row geometry). Task rows and run rows mount `ContextMenu` on epic 77's shared idiom (AD-280 / UX-DR104, `src/components/ui/menu-target.ts`: the menu's open state rings the clicked row, `aria-expanded`, selection untouched, cleared on dismiss) — a cross-epic dependency that the stack order satisfies (`epic77/surface` is rung 3, `epic78/surface` rung 5); if epic 77's surface rung is ever dropped from beneath this one, `menu-target.ts` is lifted into this rung unchanged, never duplicated.

- **AD-285 — Where the ledger lives is a machine-local setting with a visible resolved path, and the engine is told rather than left to read it.** **Binds:** FR-612; Story 78.5. **Prevents:** a selector `keeper-sync` would have to read from a crate it may not depend on (AD-40); a daemon that writes one half of a history to a different folder than the app (`folder.rs:154-161`'s own warning); a Settings section that shows what somebody chose instead of what actually ran. **Rule:** `tasks.ledger_vault` becomes a `KeySpec` beside `notes.active_vault` (`keys.rs:509-518`): `Scope::MachineLocal`, `Settable::MachineFileOnly(PROFILE_ID_WHY)`, `Shape::Text`, default `""` = *keeper decides*; `docs/settings-keys.md` is regenerated through the ignored generator (`keys.rs:1729-1732`) so the pin at `:1711-1723` passes. The shell mirrors the key into the engine through `Engine::set_ledger_profile(Option<String>)` — stored in `sync.db`'s `meta` table under `tasks.ledger_profile`, the `set_device_label` precedent (`engine.rs:2516`) — at startup and on every write, so `keeper-syncd` sharing the same `sync.db` honours the choice with no `keeper-core` in its tree (AD-52), and gains `tasks ledger [<SEL> | --none]` for a daemon-only host. `task_ledger` (`engine.rs:4166-4198`) prefers the chosen profile when it exists, carries `[folder.tasks]` and matches the task's scope, and otherwise falls back to today's first-flagged-folder rule — an unknown or unflagged choice costs nothing, never a run. Settings grows a **Tasks** section, read-only truth first: which folder holds the ledger *as the engine resolved it* (when the mirror and the engine disagree — a stale registry value, a profile gone since — the engine's resolved path wins the display, because it is what actually ran, and the section says the choice could not be honoured), the subfolder, each copy task's `<root>/<task_id>/` (`TaskVm.ledger_path`) and each copy task's destination log location (`<copy_destination>/keeper-copy-<stamp>.log`); the selector second.

- **AD-286 — Every copy option the desktop offers, `keeper-syncd` offers as a flag, and the app says so.** **Binds:** FR-613, FR-614, FR-615, NFR-79; Story 78.6. **Prevents:** a server copy task that cannot express what the form can; drift between `CopyOptions` and the CLI discovered by a user; a Tasks pane that lets the owner believe copy is desktop-only. **Rule:** `tasks set` gains `--prune-destination <bool>`, `--no-refresh-missing`, `--copy-lookback <duration>` (`5m`, `1h`, or plain milliseconds; the schedule's own duration reading), writing the same three `tasks` columns, defaults as the form's; `docs/sync.md` §14 documents the three flags, the mark fix, the `idle` verdict and the log's new shape in one edit. A test beside the existing copy CLI tests enumerates `CopyOptions`' fields against the flags `tasks set` can write and fails when the struct gains a field the CLI cannot set. `check:syncd-lean` stays green by construction — nothing here adds a dependency. The daemon sentences in `keeper-core/src/tasks.rs:72-89` stop being the only place copy-on-the-daemon is true: `HOST_SENTENCE_DAEMON` and `HOST_SENTENCE_DAEMON_UNTIL_LOGOUT` are rendered for copy tasks exactly as for sync tasks (they already are, by `task_host`), and the pane's copy-task form says, under the destination, *runs wherever this task is hosted — the daemon included*.

## What stays out

- **Making copy a two-way relationship.** AD-C1 keeps its default: a copy walks one way, remembers only its mark, and never changes the source. `prune_destination` is a job's option, not a mirror mode: it removes what *this* walk proved absent and forgets it. Bidirectional copy is sync, and keeper already has one.
- **Sharing sync's `StabilityGate` settle window with copy.** The gate (`stability.rs:494-508`) decides whether a *watched* file has stopped changing by observing it over time inside a long-lived engine; a copy task is a one-shot walk with no observation window, and the failure it needs to close is not "a file still being written" (the fstat pair at `copy.rs:730-770` already refuses those) but "a file written after the last covered mtime and before the clock". A five-minute lookback answers that for one subtraction per run; importing the gate would make the copy wait on files it is not watching and share state AD-C1 says it has none of.
- **A rich log viewer** — search, filter by outcome, per-file drill-down. The log is plain text for a person with no keeper installed (`copy.rs:1279-1283`); the panel shows it whole and tail-first, and `Reveal log file` hands it to whatever the owner reads logs with.
- **Scheduling changes.** No new schedule grammar, cadence or host; the daemon's timer unit and the app's tick are as epic 57 left them.
- **The folder-edit form's `tasks` subfolder control** (DW-258's other half) and **moving where runs are written**.
- **The one-shot copy surface's vocabulary.** *Copy files once* gains the two outcome words only through the wire; its grouping renders them as themselves.

## The failure shape this epic must not repeat

Two, and both are already in this epic's own history.

**A guarantee stated three times and enforced nowhere.** The ledger module's rule 1 (`ledger.rs:19-24`), `CopyReport::mark_ms`'s doc (`copy.rs:187-191`) and `docs/sync.md:2170-2172` all say the mark is never the clock; `engine.rs:4311` made it the clock, and its own comment said it did not. No test exercised the branch. Every acceptance line in 78.1 that says *mutation-proved* exists for this: the fixture must go red when the fallback is put back, when `Idle` is made to advance, and when the comparison is made exclusive again. A story here does not close on a doc that agrees with itself.

**A behaviour that depends on a configuration nobody can see.** Whether a deleted destination file came back depended on whether a ledger folder was configured — a `.keeper/keeper.toml` key with no form, no setting and no sentence. 78.2 names the behaviour (`refresh_missing`) and 78.5 shows the configuration; neither may ship a default that changes what the owner's folders do today without the row saying so in the run's detail. The same rule reaches 78.4: an idle run, a run with no log and a run whose ledger entry is gone are three different facts and each gets its own sentence, never an empty box.

**The risk lives in the shell crate, which cannot compile on this host.** `sync_task_run_log`, `sync_tasks_ledger*`, the `task_vm`/`task_run_vm` fields and the startup seed are all `crates/keeper/**`; every one is *by inspection, awaits CI macOS* and every core signature changed under it is grepped for callers in the same change. The engine, the ledger grammar, the copy decisions, the log renderer and the daemon's flags are all provable on Linux with real files, and that is where the proof goes.

```markdown
## D-22 — A copy stays a job; two named options let it delete and refill, and the default is unchanged

keeper's verified copy (epic 33, AD-C1) was written as a job, never a relationship: it walks
a source once, moves the bytes, reports each file, and changes nothing about either folder
afterwards. Epic 78 amends that sentence in place rather than quietly contradicting it. The
owner asked for a copy that removes what the source no longer has, and for a say over whether
a destination file he deleted comes back; the triage found that the second already depended,
invisibly, on whether a ledger folder was configured.

- **What changes:** `CopyOptions` gains `prune_destination` (default off) and `refresh_missing`
  (default on). Pruning runs after the copy pass over the set of paths the plan walk already
  saw, deletes only what that walk proved absent, and reports each file as `deleted`;
  refilling examines a behind-the-mark source only when its destination file is missing.
  Both are per-task columns, form controls, `task.toml` lines and daemon flags. (AD-282,
  AD-286; FR-604…FR-606)
- **Why the default stays a job:** AD-C1 was written against the tool that deletes the newer
  file on the wrong side — the failure a person meets without having chosen it. A person who
  turned on `prune_destination` on a form that says what it deletes has chosen it, and the
  copy still remembers nothing but its mark: a prune is a job's last step, not a state.
- **What it is not:** a mirror, a two-way sync, or a watch. The source is never written; no
  journal is kept; the sync engine's stability gate is not shared (a five-minute lookback on
  the mark answers the in-flight-write question for one subtraction). (AD-281; What stays out)
- **The fact this makes visible:** with a ledger, a source behind the mark is not examined;
  without one, every pass is full. `refresh_missing` names that so the answer no longer
  depends on a `.keeper/keeper.toml` key nobody could see, and Settings now shows where the
  ledger is. (AD-285)
- **Revisit triggers:** the owner asking for the source side to change (that is sync, and
  this entry says no); a measured pass where the per-file destination stat of
  `refresh_missing` costs more than the hashing (DW-274).
- **Status / owner:** decided. Owner is the architect; Epic 78 implements it; NFR-77 and
  NFR-78 are the bars.
```
