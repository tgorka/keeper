## How it works
keeper-sync leans on four library stacks. (1) **gitoxide, forked**: `gix = { git = "tgorka/gitoxide", branch = "keeper/gix-filter-0.33-reap" }` (`Cargo.toml:227`), with `gix-quote`/`gix-pack` pinned to the same branch (`:306`, `:315`) so all three resolve from one checkout. The branch is the `gix-filter-v0.33.0` release tag (commit `842bc447e`, which also published `gix 0.86.0`) plus exactly two commits: `6a49f8ede` (`process::Client::id()` + lifecycle tests) and `0ae30235f` (`shutdown_mut` + `impl Drop for State`). Everything else in the tree is identical to crates.io 0.86.0. (2) **notify 8.2 / debouncer-full 0.7**: FSEvents on macOS, inotify on Linux, PollWatcher on demand; keeper deliberately uses `NoCache` instead of `RecommendedCache` (`watch.rs:455-500`) and maps `Flag::Rescan` to a full-tree rescan (`watch.rs:331-334`). (3) **rusqlite 0.37 bundled** (SQLite 3.50.2): WAL + NORMAL sync, default open flags, one `Mutex<Connection>` (`engine.rs:919, 1553-1556`). (4) **reqwest 0.13.4 + rustls**: two long-lived shared clients built once in `Engine::open` (`engine.rs:1378-1382`) with connect/read/pool-idle timeouts (`http.rs:129-141`); LFS upload bodies stream through a hand-written `http_body::Body` (`lfs/basic.rs:1069-1133`); git fetch/push ride gix-transport's own blocking reqwest client.

## Findings

### F-Deps-1 The fork's one fix is upstreamed and merged upstream, but not yet released — the pin can be retired the moment it ships — P2, effort S
Evidence: upstream PR **GitoxideLabs/gitoxide#2946** ("fix(gix-filter): reap long-running filter processes", Codex-authored by Byron) was **merged 2026-08-27T08:57Z**; commit `5c82383020` verified on upstream `main`. keeper's own PR #2948 was closed unmerged (superseded). But crates.io `gix-filter` max stable is **0.34.0, published 2026-08-22** — *before* the merge — and upstream's `gix-filter/CHANGELOG.md` Unreleased section does not yet carry the reap entry. Upstream's shape differs from the fork: explicit `shutdown(WaitForProcesses)` in every workspace caller plus best-effort wait on drop, "keeping Drop off the public State type".
Why: the fork pin is now pure migration debt with a moving expiry date; `Cargo.toml:195-232` already documents the retire procedure ("restore `version = "0.86"`, drop the git/branch keys… re-run the reaping proof"). The correct retire gate is **the first gix-filter release containing `5c82383020`** (≥ 0.34.1), not a calendar date.
Fix: watch gix-filter ≥ 0.34.1 (or check the release notes for `5c82383020`); on retire, bump `gix`/`gix-quote`/`gix-pack` off the git source in one commit and re-run the zombie-count proof from `docs/upstream/gitoxide-filter-process-leak.md`.

### F-Deps-2 gix fetch/push transport: 20 s connect timeout only — a stall after connect hangs the blocking thread forever — P2, effort M
Evidence: `gix-transport/src/client/blocking_io/http/reqwest/remote.rs:63-64`:
```rust
let client = reqwest::blocking::ClientBuilder::new()
    .connect_timeout(std::time::Duration::from_secs(20))
```
No `read_timeout`, no total timeout anywhere in the transport; `git/fetch.rs:3-7` documents the path is blocking and must run in `spawn_blocking`, and `engine.rs:6132-6135` does exactly that with no watchdog. The hesperia line `error=git object store failure: fetch from electra… tcp connect error: deadline has elapsed` (53 occurrences in 3 days) is precisely this 20 s connect timeout (tokio `Elapsed` inside reqwest's connect error) — correct behaviour for an unreachable remote, and it classifies `Transient` (`fetch.rs:251-254`).
Why: the LFS HTTP paths got this right (`http.rs:26-36` — read-timeout-not-total-timeout reasoning) and `push_http.rs:123` uses the shared guarded client; the **git** fetch/push leg is the one network path with an unbounded silence window. A half-open tailscale connection mid-negotiation parks a blocking thread and the profile's one-operation reservation indefinitely (`[INFERENCE]` on frequency; the mechanism is certain from source).
Fix: wrap `fetch`/`push` blocking threads with a coarse app-level deadline (tokio timeout around `spawn_blocking` + gix's `should_interrupt`), or thread a custom transport. Long-term, ask upstream for a client-injection point on the reqwest transport — today there is none (`grep` of `gix-transport/src` finds no `with_client`/custom-client API), so each fetch also builds a fresh client + tokio runtime thread and pays a fresh TLS handshake per pass.

### F-Deps-3 gix's decoded-index snapshot cache is thrown away every walk (fresh `Repository` per pass) — P2, effort M
Evidence: keeper opens a **new** `gix::Repository` per status pass — `engine.rs:12461` (`let repo = git::repo::open(&repo_path, removable)?;` inside the `spawn_blocking` closure), same pattern at `engine.rs:6133, 6371`. gix caches the decoded index on the handle and reuses it across clones until the file's mtime changes — `gix/src/repository/index.rs:103-121`: `index_or_empty()` → `try_index()` → `self.index.recent_snapshot(…mtime check…, open_index)`.
Why: on tgdrive that is a ~26 MB decode per pass on a USB volume, contributing to the p50 1.1 s / p90 5.3 s walks (1371 walks in the current session). Two honest caveats: (a) the tracked walk writes refreshed stats back (`repo.rs:1932` `outcome.write_changes()`), which rewrites `.git/index` and would invalidate the snapshot on the *next* pass even with a long-lived handle — so the win applies to read-only passes (`open_read_only`, verify, listings) and to making the stats write rarer; (b) the parse is threaded (`index.threads` read at `gix/src/repository/index.rs:29-34`, unset on hesperia).
Fix: keep one `gix::ThreadSafeRepository` per profile in the engine (clones share the snapshot cache) and measure walk p50 before committing; pair it with `index.skipHash=true` (F-Deps-4) to also drop the trailing SHA-1 on every stats write.

### F-Deps-4 `core.fsmonitor` / `core.untrackedCache` are dead letters for keeper's walk; gix's only status accelerator is Windows-only; index stays v2 — P3, effort S
Evidence: gix 0.86 **reads** the FSMonitor and UNTR index extensions but never consults them — `gix-index/src/access/mod.rs:653-656` (`pub fn fs_monitor(&self) -> Option<&extension::FsMonitor>`) with no consumer in `gix-status`; grep finds no `fsmonitor` config key in `gix/src/config/tree/` (only the sample hook asset gix installs at init). The accelerator added in the locked line is `index_as_worktree::Options::fscache`, **Windows-only** ("a Windows-only status accelerator equivalent in spirit to Git's `core.fscache`", gix-status 0.33.0 changelog, 2026-07-23). gix writes index v2 only (no v4 writer in `gix-index/src/file/write.rs`; hesperia confirms `DIRC 2`, 26.4 MB); `index.skipHash` **is** honoured on read and write (`gix/src/repository/index.rs:31-33`, `gix-index/src/file/write.rs:27-28`).
Why: setting `core.fsmonitor`/`core.untrackedCache` on hesperia would speed only foreign `git status` runs, not keeper; that matters for the owner's mental model and `docs/performance.md` should say so. `index.skipHash=true` is the one index-level knob gix will actually honour today.
Fix: document both keys as inert for the gix walk; consider `index.skipHash=true` on large profiles; ask upstream for an fsmonitor-backed status.

### F-Deps-5 keeper's reqwest clients omit `tcp_keepalive` (and inherit HTTP/2 by feature unification, not by choice) — P3, effort S
Evidence: `http.rs:129-141` sets exactly four options: `user_agent`, `connect_timeout`, `read_timeout`, `pool_idle_timeout`. No `tcp_keepalive`, no `http2_keep_alive_*`, no `pool_max_idle_per_host`. Workspace features: keeper declares `reqwest = { default-features = false, features = ["json","rustls"] }` (`Cargo.toml:84`) — which alone would mean HTTP/1.1-only and no system-proxy — but gix-transport's reqwest dependency enables `http2` (`gix-transport/Cargo.toml:128`), and cargo unifies features, so the compiled reqwest has HTTP/2+ALPN for all clients.
Why: over tailscale, a half-open pooled connection is detected only when the next request's read times out; `POOL_IDLE_TIMEOUT = 20 s` (`http.rs:107`) is an explicitly-labelled hypothesis for the throughput-decay symptom. A TCP keepalive would let the OS reap dead mappings sooner and is one line.
Fix: add `.tcp_keepalive(Duration::from_secs(30))` (or `Os`) to `client_with` and keep the 20 s pool-idle experiment; make the `http2` feature explicit so retiring gix's transport later cannot silently change HTTP behaviour.

### F-Deps-6 rusqlite default open flags include `SQLITE_OPEN_NO_MUTEX` — correct here, but load-bearing and undocumented — P3, effort S
Evidence: `rusqlite-0.37.0/src/lib.rs:1226-1232` — default flags are `READ_WRITE | CREATE | URI | NO_MUTEX`; keeper opens with `Connection::open(db_path(...))` (`db.rs:41`) and serialises all access through `db: Mutex<Connection>` / `with_db` (`engine.rs:919, 1553-1556`).
Why: with NO_MUTEX SQLite skips its internal serialisation; that is only safe because keeper's own `std::Mutex` guarantees single-threaded access to the handle. It is safe today (verified: every use goes through `with_db` or an owned connection), but nothing in `db.rs:35-60` records the invariant — a future `&Connection` shared across tasks would be a data race SQLite's own safety net would normally have caught.
Fix: one comment on `db::open` stating "default flags include NO_MUTEX; every handle must be externally serialised (see `Engine::with_db`)". No code change.

## What is correct / well done
- **The fork is minimal and exactly scoped**: `git diff --stat 842bc447e..0ae30235f` touches 9 files, all in `gix-filter` (+270/−12); tests-first split, `Client::id()` for observability, mutation-checked. The manifest comment block (`Cargo.toml:195-232`) is exemplary pin documentation, including why `[patch.crates-io]` on gix-filter alone would double-build `gix-hash` and fail.
- **notify handling beats the crate's own defaults**: `NoCache` instead of `RecommendedCache` avoids the FileIdMap full-tree stat at `watch()` time on macOS (`watch.rs:455-470` documents the 154 765-entry / ten-minute measurement; verified `RecommendedCache = FileIdMap` on non-Linux, `cache.rs:62-65`, and `NoCache::add_path` is a no-op, `cache.rs:50-55`). `Flag::Rescan` (FSEvents `MustScanSubDirs`, inotify overflow) is both handled per-event (`watch.rs:331-334`) and backstopped by the 15-min sweep (`watch.rs:97-115`). `EventKind::Other` → `Interest::Touch` (`watch.rs:262-265`), so FSEvents' vague kinds are never dropped. Volume detach/reattach re-arm observed working in the hesperia log.
- **Double-delay question answered: not a defect.** Debouncer timeout = 500 ms (`DEFAULT_DEBOUNCE_MS`, `watch.rs:88-92`), deliberately below the shortest quiescence (settle) window so tier-2 owns pacing; worst-case detection latency is debounce + settle + poll tick, by design. The known FSEvents remove-swallowing bug (notify-rs/notify#900, filed 2026-04-18) is fixed in debouncer-full 0.7.0 (2026-05-02), which keeper already has.
- **HTTP timeout design is the right shape** for a file-sync client: connect 15 s, read 60 s (silence), transfer read 30 min (LFS), pool idle 20 s — each constant justified with field measurements in `http.rs:44-107`, and the "read timeout, emphatically not total" reasoning is correct for 2 GB uploads. Two clients only, built once, shared by clone (Arc) into every `BatchClient` (`engine.rs:7953, 10180, 10345`) — no TLS handshake per request on the LFS paths.
- **`SizedFileBody` is a correct `http_body::Body`**: `size_hint()` returns `SizeHint::with_exact(self.remaining)` (`lfs/basic.rs:1129-1132`), `is_end_stream()` is `remaining == 0` (`:1125-1127`), reads go through `tokio::fs` so `poll_frame` never blocks the reactor (`:1017-1018`), and tests assert exactness, end-stream and multi-frame streaming (`:1523-1545`). This keeps `Content-Length` on pre-signed S3 PUTs without buffering.
- **rusqlite**: bundled SQLite 3.50.2 (`libsqlite3-sys-0.35.0/sqlite3/sqlite3.h:149`), WAL + `synchronous=NORMAL` (`db.rs:44-46`), and the 5 s busy timeout story is pinned by a test (`db.rs:48-57`). Two processes share the file safely.
- **No known advisories**: OSV/RustSec queries for all 15 locked crate@version pairs returned zero advisories (checked 2026-09-08). `cargo audit` not installed, per task constraints.
- **globset 0.4.19, sha2 0.10.9, tokio 1.52.3, http-body 1.0.1**: all current-or-patch-behind, no misuse found; sha2's `asm` feature deliberately off for a documented reason (`Cargo.toml:258-261`).
- **gix status pathspec support exists and is used**: `Platform::into_iter(patterns)` — "Optional patterns to use to limit the paths to look at. If empty, all paths are considered" (`gix/src/status/iter/mod.rs:33-45`); keeper uses it for the unreadable-path exclusion retry (`repo.rs:1019-1021, 1696-1740`). The full-tree walk is inherent to the job (any path can change), so not pathspec-limiting is correct.

## Open questions I could not settle
- Whether a mid-fetch stall (post-connect) has ever actually occurred in the field — the mechanism is certain from source, the frequency is not (needs the full 895 MB log correlated with wedged fetch threads).
- Whether a long-lived `gix::ThreadSafeRepository` per profile would measurably cut walk time, given the stats write invalidates the snapshot each tracked walk — needs an on-hesperia A/B this read-only lane could not run.
- The exact feature set keeper's `bundled` SQLite build enables — not audited because no FTS/extension usage was found in `db.rs`.
- Whether upstream will ship the reap fix as gix-filter 0.34.1 or fold it into 0.35.0 (no release milestone visible on the merged PR at query time).
