# Epic 75 — The floating window keeps what you gave it

created: '2026-09-19'
source: the owner's four notes on the quick-capture window, sent against the installed build at `237c2d8`, with one screenshot (the window showing two stacked header rows). Triaged claim-by-claim by three read-only lanes before a line of this was written.

## What the triage found

## The one sentence

**A padlock that resizes your window, a panel that decides for itself to float above everything, and two header rows where the design already has one: the window keeps its own preferences and discards yours.**

## Decisions this epic takes

- **AD-257 — A lock freezes what is there; it does not impose what keeper would have chosen.** `Placement::window_size`'s locked arm returns the remembered size rather than `CAPTURE_DEFAULT_SIZE`. The old rule ("a locked window is keeper's to place and size") is rescinded for size and kept for nothing: the whole point of the padlock, to the person pressing it, is *stay exactly as you are*. The original reading of this decision was that a window never resized keeps `None` and is left alone — that was written before the spec for 75.1 refined it, and the refinement is deliberate: the `None` that rule meant to protect is the **unlocked** arm (`(false, None) => return None`), which did not move and still means *do not touch the window at all*. A **locked** window with nothing remembered is a different case: the person pressed a padlock, and a lock has to freeze the window at a size — so that window answers `CAPTURE_DEFAULT_SIZE`, keeper's own 560×340, which is what the shipped `window_size` does (`(true, None) => CAPTURE_DEFAULT_SIZE`). The "never resized" versus "resized to something of your own" distinction `window_size` documents stays load-bearing; what changed is which side of it a locked window falls on.
- **AD-258 — The lock is off at every open.** It is a gesture for the capture in front of you, not a preference: it freezes geometry and (until AD-257) silently resized the window. `locked` is still stored — position and size ride in the same row and must survive — but the open path forces it false, so a window that was locked when it was dismissed comes back movable. This overrules spec-46-15's acceptance step 12, deliberately and at the owner's request. One consequence is accepted with it: since every capture window is unlocked at every open, `plan_show_position` answers "leave it where it is" for every window that can say whether it is resizable, so keeper's own pointer-following placement (DW-198: "a fifth of the way down the monitor holding the pointer") is no longer reached by a window that answers. A fresh machine gets the window centred on the monitor it was created on, and the first blur freezes that position in the stored row. That is the compensation being retired, not lost functionality: pointer-following existed because a locked window could not be moved by hand, and nothing arrives locked any more — a panel that jumps to the pointer's monitor on every press is exactly the "keeps its own preferences and discards yours" this epic is named after. The placement path remains reachable for a window whose backend refuses to report resizability: a window that will not answer must still be placed, exactly as it always was.
- **AD-259 — Floating above other applications is off until asked for.** The shipped default becomes `false`, in the `Placement` default and in the draft window's birth state (`tauri.conf.json`), so a machine that has never touched the pin gets an ordinary window. Unlike the lock this **stays persisted**: it is a preference about how this window behaves, the owner's words for it were "by default", and discarding an explicit pin on every open would be the same disrespect in the other direction. The asymmetry is deliberate and is written here so the next reader does not "fix" it.
- **AD-260 — One header, and it is `PaneHeader`'s.** The window controls become the header's **frame group** (Story 50.1's mechanism, built for exactly this) rather than a strip above it. The drag region and DW-199's Rust-measured corner inset move with the close button — they are properties of the window, not of the strip. Where the row cannot hold everything, the **status caption gives first** (it is transient and repeated in the `…` menu) and the identity title truncates second; no action is dropped and no floor is raised silently: if the arithmetic says the minimum window width can no longer host the row, `CAPTURE_MIN_SIZE` moves in the same change with the derivation rewritten beside it.

## Stories

### 75.1 — A lock freezes the size you chose
AD-257. One arm of `Placement::window_size` (`capture.rs:531-533`), the three sites that record the old rule (`notes_ipc.rs:5392-5398`, `capture-window.tsx:71-75`, spec-46-15's edge-case table), the pinning test at `capture.rs:1556` flipped to the new rule, and mutation M9 re-recorded against it.
**Acceptance:** a `Placement` that is locked with a remembered size answers that size; locked with **no** remembered size answers `CAPTURE_DEFAULT_SIZE` — the epic's earlier wording said such a window "keeps `None` and is left alone", and the spec for 75.1 deliberately refined that: the `None` that must not move is the *unlocked* one, while a locked window has to be locked *at* a size, so it gets keeper's own. The clamp to the work area still applies to both; the flipped test fails if the arm is reverted (mutation-proved). The end-to-end sequence — resize, lock, and the window stays — is a macOS-gate step, because the shell crate does not build here.
**binds:** FR-560, AD-257

### 75.2 — The lock is off when it opens, and nothing floats until asked
AD-258, AD-259. The open path forces `locked: false` (at show, not only at create — the hotkey reveals a hidden window rather than building one, `hotkey.rs:186-198`); `Placement::default()` and `tauri.conf.json`'s draft window birth `top: false`; the stored row keeps carrying both, because position and size live there too.
**Acceptance:** a stored row that says locked comes back unlocked and **keeps its position and size** — the reset is one field, not a wipe; a fresh machine opens unpinned and unlocked; a pin the owner sets is still there on the next open (the deliberate asymmetry with the lock); the boot adoption path (`lib.rs:517-548`) and the hotkey reveal path both go through the same reset, so which one opened the window cannot change the answer.
**binds:** FR-561, AD-258, AD-259

### 75.3 — One header row
AD-260. The chrome becomes `PaneHeader`'s frame group in capture hosts, via `NoteEditor`'s documented-but-unused `frame` prop; the conditional drag region and the corner inset travel with it; the tests that pin the two-row structure move rather than being deleted; the width arithmetic is recomputed and `CAPTURE_MIN_SIZE`'s derivation comment rewritten if the floor has to move.
**Acceptance:** one header row holds title, save caption, the three document actions and the three window controls, measured in a real browser at the default 560 px width **and** at whatever the minimum width ends up being — no element narrower than its own content, nothing outside the window, no second row; the close button still sits clear of the platform's corner (DW-199's inset, asserted as it is today); dragging the header still moves the window where it did; the four structural tests named in the triage (`capture-window.test.tsx:189,209,224`, `capture-document.test.tsx:581`) pass against the merged header.
**binds:** FR-562, AD-260, AD-93, DW-199

## What stays out

- **The `…` menu's contents.** Merging the rows moves the button, not what it opens.
- **Any change to what the lock means for POSITION.** A locked window still cannot be dragged; only the size rule changes.
- **The capture window's default size.** 560×340 stays the size a never-resized window gets; it simply stops being imposed on one that was.
