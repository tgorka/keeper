Grounding pass

5 insightsBEFORE ANY IDEA

Grounded first: three read-only scouts mapped recording, sync and archive/notes before ideating. Everything below is anchored to a seam that already exists in the codebase — which is why the MUST list is reachable rather than aspirational.

SCOUT 1 recordingSCOUT 2 syncSCOUT 3 archive / notesMODE read-only
HOST-SIDE

Session folder is created host-side in Rust (keeper/src/ipc.rs recording_start); the Swift sidecar only derives sibling segment paths from the one absolute path it is handed — so naming and nesting are a pure Rust change

SETTINGS K/V

recording.destination_dir already exists end to end (keeper.db settings k/v -> RecordingSettingsVm.destinationDir -> RecordingDestinationControls); the configurable ROOT is done, the NAME PATTERN is not

THE SEAM

SegmentClosed{index,path,bytes,track,ptsStart,ptsEnd} lands in the driver sink in ipc.rs after the Swift writer's finishWriting; nothing is notified — that closure is the one seam for sync-on-finalize

PRECEDENT

SyncProfile already carries notes: Option<NotesConfig>{subfolder, journal_template, cadence} and Engine::watch_tap already fans watcher events out to notes_vault::start — recordings should copy that shape, not invent one

THE GAP

No 'this path is finished, sync it now' API exists: StabilityGate::is_stable is the only gate, note_close_write (1s window) is private and Linux-only

Job to Be Done

15 ideasRETRIEVAL FRAME

Fifteen jobs on a strip of tape. Nobody hires a folder name for tidiness — they hire it to never lose a recording, and to find it later by what it was about.

WHAT THE JOB LOOKS LIKE ON DISK — ONE TEMPLATE RENDERS ALL OF IT
~/Recordings/                              ← recording.destination_dir  (ships today)
└── 2026/                               ← {yyyy} — the branch the default template grows
    └── 2026-08-05 1432 standup/        ← {yyyy}-{mm}-{dd} {HH}{MM} {slug}   no colon, exFAT-safe
        ├── segment-000.mp4             finished forever — assert, commit, push
        ├── segment-001.mp4.partial     still being written — invisible to sync
        ├── segments.ndjson             append-only ledger, one line per rotation
        ├── manifest.json               written once at finalize, versioned, no absolute paths
        └── 2026-08-05 1432 standup.md  note stub, tags, the post-meeting minute
FRAME 0100:00:14:00
THE REAL JOB

The job is not tidiness: it is never losing a recording and finding it later by what it was about — naming and placement are retrieval features

FRAME 0200:00:51:07
SORT WITHOUT METADATA

Date-first folder names (2026-08-05 1432 standup) sort chronologically in Finder, ls and Files.app alike, with no metadata read

FRAME 0300:01:28:14
ROOT HYGIENE

A year folder keeps the root listing small; Finder and any git status slow down long before a heavy recorder's tenth year

FRAME 0400:02:05:21
DEPTH IS A CHOICE

Month nesting should be available but not default — 2026/08/ is right for someone recording daily, wrong for someone recording monthly

FRAME 0500:02:42:04
TEMPLATE NOT FLAG

Express naming as a token template, not a boolean: {yyyy}/{yyyy}-{mm}-{dd} {HH}{MM} {slug} makes year nesting fall out of the default template

FRAME 0600:03:19:11
ONE VOCABULARY

Steal the token vocabulary already shipped in keeper-sync: DEFAULT_JOURNAL_TEMPLATE = journal/{yyyy}/{yyyy}-{mm}-{dd}.md — one convention across notes and recordings

FRAME 0700:03:56:18
FILESYSTEM LAW

Time as 1432 or 14-32, never 14:32: a colon is illegal on exFAT, and removable-volume sync makes a FAT pendrive a real destination

FRAME 0800:04:33:01
EMPTY TOKEN

An untitled session must collapse the {slug} token cleanly — no trailing separators, no 'Untitled' litter

FRAME 0900:05:10:08
JOB 2 · IS IT SAFE?

Second job: 'is this recording safe off my laptop yet?' — a per-session sync state (local / staged / pushed / verified) answers it

FRAME 1000:05:47:15
JOB 3 · HAND IT OVER

Third job: 'get the last hour to a colleague now' — that is a push-only lane and a URL, not a full bidirectional sync

FRAME 1100:06:24:22
THE METRIC

The user's real deadline is 'before the laptop is lost': the metric to optimise is time-to-durable per segment, not throughput

FRAME 1200:07:01:05
JUMP TO A MOMENT

Reviewing later means jumping to a moment — the ledger already stores ptsStart/ptsEnd per segment, so chapters are almost free

FRAME 1300:07:38:12
NAME IT AFTERWARDS

Nobody names a folder before a meeting starts: naming must be editable afterwards, and the rename must move the folder, rewrite the manifest and git mv in one operation

FRAME 1400:08:15:19
NO SECOND TOGGLE

If the destination is inside a synced tree, syncing must be automatic — a second 'also sync this' toggle is a job the user did not hire us for

FRAME 1500:08:52:02
JOB 4 · LATER-ME

Job for later-me: 'what did we decide?' — that is a note keyed to the recording, not another video player

Morphological Analysis

16 ideasPARAMETER MATRIX

Eight axes, one grid. Every cell is a shippable configuration; the highlighted cells are the path through the matrix this session recommends.

Parameters of the design space: root location x path template x year/month depth x per-session subfolder shape x sync profile x subfolder in repo x LFS mode x retention
ROOT LOCATIONwhere the tree is rooted
ARoot option A: a plain folder outside any repo (today) — simplest, syncs nothing
BRoot option B: root IS a sync profile's local_path — recordings become just files in the repo, zero extra wiring
CRoot option C: root is a subfolder of a profile (profile.recordings.subfolder, exactly like NotesConfig.subfolder) — the recommended shape
DRoot option D: two roots — a fast scratch volume for live writing and a synced root the finished session is moved into on stop
TEMPLATE DEPTHhow far the path nests
0Template depth 0: flat {yyyy}-{mm}-{dd} … — fine to year 3, painful after
1Template depth 1: {yyyy}/ — the default we want
2Template depth 2: {yyyy}/{mm}/ — an opt-in for daily recorders
PER-PROFILETemplate depth by profile: a synced root may want {yyyy}/{mm} while a local scratch root stays flat — so the template belongs to the destination, not to the app
SESSION FOLDER SHAPEwhat sits beside the media
ASession folder shape A: one folder per session holding segments + manifest (today)
BSession folder shape B: session folder plus a sidecar .md note file next to it — the note is the thing notes-sync already knows how to render
CSession folder shape C: session folder inside, note file in a notes vault, linked by session id — better for note search, worse for a single self-contained artifact
SYNC MAPPINGwhich profile takes it
A / BSync mapping A: whole recordings root in one profile; mapping B: per-recording routing by tag (client work to one repo, personal to another)
LFS MODEhow bytes travel
POINTER-ONLYLFS axis: mp4 segments are always over the 4 MiB threshold, so lfs::stage::applies auto-tracks *.mp4 — the interesting cell is lfs_mode = PointerOnly on the laptop so old bytes can be pruned locally but stay on the remote
RETENTIONwhat survives locally
VERIFIED-ONLYRetention axis crossed with sync state: prune locally only what is verified present on the remote — the matrix cell that makes a 500 GB/year habit survivable
◆ UNTRIED CELL WORTH NAMINGUntried configuration worth naming: synced manifest.json + notes, LFS-pointer-only video — the searchable archive travels everywhere, the bytes stay where there is room
T3

TRIZ Contradiction

15 ideasOPPOSING FORCES

Six contradictions. Each is two forces pulling the design apart, and the move that makes both of them true at once.

CONTRADICTION 01The contradiction: syncing sooner improves durability but breaks the completeness gate, which exists precisely because a file being written must not be committed
FORCE ASYNC SOONER
durability rises with every second saved
→←
FORCE BWAIT FOR QUIESCENCE
the completeness gate exists for a reason

SEGMENT IN TIMEResolve it by segmenting in time, not by weakening the gate: a rotated segment is immutable forever, so it is not 'quiescent yet', it is FINISHED — a different fact

ASSERT, DON'T SHORTENSo add an assertion API, not a shorter timer: StabilityGate::note_finished(path) marks a path complete from an authoritative producer and skips the settle window

NARROW AUTHORITYAuthority must be narrow: only a producer that owns the writer may assert, so the API takes a path the recording driver just closed, never user input

GENERALISE THE SIGNALThe Linux IN_CLOSE_WRITE fast path already encodes this idea (note_close_write, 1s) — generalise it from an OS signal to a first-class producer signal, macOS included

CONTRADICTION 02Second contradiction: the user wants the file safe immediately, but pushing a 2 GB LFS object mid-meeting eats the uplink the meeting is running on
FORCE ASAFE IMMEDIATELY
the laptop could be lost at any minute
→←
FORCE BUPLINK IS IN USE
the meeting is running on it right now

TWO SPEEDSWin both with a two-speed policy: commit + LFS-stage locally at once (cheap, durable on the same disk), defer the push to a bandwidth window or session end

CONTRADICTION 03Third contradiction: one manifest.json per session must be re-written on every rotation, but rewriting the file the sync engine just committed causes churn and self-echo
FORCE AALWAYS-CURRENT MANIFEST
one file, rewritten every rotation
→←
FORCE BNO CHURN, NO SELF-ECHO
sync must not chase its own commit

APPEND-ONLYResolve by append-only: segments.ndjson grows by one line per rotation and never rewrites; manifest.json is written once at finalize

CONTRADICTION 04Fourth contradiction: the archive wants everything indexed, the drive wants nothing wasted — index metadata (tiny, always synced) separately from media (huge, optionally pointer-only)
FORCE AINDEX EVERYTHING
the archive wants total recall
→←
FORCE BWASTE NOTHING
the drive wants none of it

RESOLVED IN PLACEthe statement carries its own move: index and media are separated, not traded off.

CONTRADICTION 05Fifth contradiction: a recording must survive a crash, but crash recovery scans orphaned segments AFTER restart, while sync may have already committed a half-written file
FORCE ASURVIVE A CRASH
recovery scans orphans after restart
→←
FORCE BSYNC IS ALREADY RUNNING
it may commit a half-written file first

IN-PROGRESS MARKERResolve with an in-progress marker: write segments under a .partial suffix that tier-0 name exclusion already ignores, and rename on close — atomic rename is the completeness signal

SUFFIX RULEA rename is also exactly what git sees as add+delete, so the exclusion pattern must be the SUFFIX rule, cheap and total

CONTRADICTION 06Sixth contradiction: the user wants a friendly editable title, git wants stable paths — resolve with an immutable session id inside the manifest and a mutable display title
FORCE AA FRIENDLY, EDITABLE TITLE
humans rename things later
→←
FORCE BSTABLE PATHS
git wants identity to hold still

ID INSIDE, TITLE OUTSIDEThen a rename is a git mv of a folder whose identity never changed, and the archive row keeps pointing at the same session

Chaos Engineering

15 ideasFAULT INJECTION

Fifteen faults fired into a running recorder. Each card is graded by what the system does when it lands — contained by design, needs a mitigation, or genuinely untested.

CONTAINED
FAULT 01 · KILL -9

SIGKILL DURING ROTATION

BLAST RADIUS & RESPONSE

kill -9 during rotation: the .partial segment is never renamed, so sync never sees it and startup recovery finalises or discards it — the failure is contained by naming alone

MITIGATE
FAULT 02 · ENOSPC

DISK FULL MID-SEGMENT

BLAST RADIUS & RESPONSE

Disk full mid-segment: the existing disk-space guard stops and finalises; the sync assertion must fire for what WAS written, not for the segment that failed

MITIGATE
FAULT 03 · VOLUME ABSENCE

PENDRIVE UNPLUGGED MID-PUSH

BLAST RADIUS & RESPONSE

Pendrive unplugged mid-push: absence semantics already pause without deleting — but a recording still writing into an absent volume must fail loudly, not silently buffer

MITIGATE
FAULT 04 · PROTECTED BRANCH

REMOTE REJECTS THE PUSH

BLAST RADIUS & RESPONSE

Remote rejects the push (protected branch): the session must still be marked locally durable, and the tray must say 'recorded, not pushed' rather than a generic error

UNTESTED
FAULT 05 · 40 GB DAY

LFS UPLOAD DIES AT 90%

BLAST RADIUS & RESPONSE

LFS object upload dies at 90%: resumable download exists, but a resumable UPLOAD is the untested leg for a 40 GB day

INTERLOCK
FAULT 06 · ID COLLISION

TWO MACHINES, ONE FOLDER

BLAST RADIUS & RESPONSE

Two machines recording into the same synced folder at once: session ids must be device-scoped or the folder names collide on the same minute

MITIGATE
FAULT 07 · WRONG YEAR

CLOCK SKEW ACROSS DEVICES

BLAST RADIUS & RESPONSE

Clock skew across devices: a date-first name from a machine with a wrong clock sorts into the wrong year — stamp the manifest with both local time and a monotonic device sequence

MITIGATE
FAULT 08 · TREE CHANGES UNDER WRITER

.gitattributes LANDS MID-RECORDING

BLAST RADIUS & RESPONSE

The sync engine's own commit touches .gitattributes when the first mp4 appears; if that lands mid-recording the working tree changes under the recorder — write the LFS rule at session start, not at first segment

INTERLOCK
FAULT 09 · INODE DRIFT

FINDER RENAME WHILE RECORDING

BLAST RADIUS & RESPONSE

A user renames the session folder in Finder while recording: the driver holds absolute paths, so writes keep landing in the moved folder while the UI shows the old one — detect via inode and refuse or follow, but never silently split a session

INTERLOCK
FAULT 10 · DESTRUCTIVE PULL

REMOTE DELETES AN ACTIVE SESSION

BLAST RADIUS & RESPONSE

Sync pulls a remote deletion of a session the laptop is recording into — pause and warn; never let a pull delete an active session folder

MITIGATE
FAULT 11 · 48 COMMITS / 24 GB

4 HOUR SOAK × SYNC

BLAST RADIUS & RESPONSE

The 4 h soak crossed with sync: 4 hours of 500 MB segments is ~48 commits and ~24 GB of LFS; the journal must not grow unbounded and the push must be batched

MITIGATE
FAULT 12 · COLD BOOT

BATTERY DIES, PUSH OUTSTANDING

BLAST RADIUS & RESPONSE

Battery dies with segments committed but not pushed: on next boot the outstanding-upload gate (lfs_uploads_outstanding) must resume before any new pointer is published

MITIGATE
FAULT 13 · TIER-4 VERIFY

CORRUPTED SEGMENT

BLAST RADIUS & RESPONSE

A corrupted segment (verify-on-read tier 4 catches it) must not be silently synced — quarantine it and mark the session degraded in the manifest

MITIGATE
FAULT 14 · WEBCAM VS SCREEN

TRACKS FINALISE OUT OF STEP

BLAST RADIUS & RESPONSE

The webcam file and the screen file finalise at different instants; asserting each independently is right, but the session is only 'complete' when the ledger says every track closed

INTERLOCK
FAULT 15 · DELIBERATE ABUSE

ROOT AIMED AT THE NOTES VAULT

BLAST RADIUS & RESPONSE

Deliberate abuse: a user points the recordings root at the notes vault subfolder — validate for overlap the way NotesConfig::validate already refuses .obsidian and escaping subpaths

Ecosystem Thinking

15 ideasTROPHIC MAP

The players arranged by trophic level. Producers make bytes at a furious rate; nothing currently eats them, nothing decomposes them, and the richest niche is completely unoccupied.

PRODUCERSwho makes the bytes
Map the players: the Swift recorder produces, the ledger accounts, the sync engine transports, the notes vault interprets, the archive remembers, the tray narrates
Nobody currently eats the recorder's output — the manifest is written and never read back except for meta.title; that dead end is the whole opportunity
MISSING GUILDthe decomposers nobody built
The decomposer is missing: nothing prunes, nothing summarises, nothing ages a recording out — an ecosystem without decay fills up and dies
Decay policy as a first-class citizen: keep media 90 days locally, keep metadata and notes forever — the archive stays complete while the disk stays sane
SYMBIOSIStwo species, one vocabulary
The obvious symbiosis: notes/tags.rs already has a hierarchical tag tree and a tag: search predicate scoped to markdown vaults; recording tags are a raw comma-split string with no vocabulary
Unify the vocabulary: one tag tree, two producers — a recording tagged client/acme shows up in the same TagTree sidebar as a note tagged client/acme
The join key is a session id; a note referencing it makes the recording searchable by the note's full text, which the archive already indexes with FTS5 trigram
A recording session and a Matrix room are natural partners — record a call, attach the session id to the room, and the archive can put transcript, chat and video on one timeline
HABITAT & EMERGENCEwhere a session comes to live
Feed the archive a new row kind: a recordings table beside events, sharing the db and the FTS pattern rather than a second search engine
Emergent surface: a Recordings browser that is really an archive query — filter by tag, participant, date range, sync state
SIGNALLINGhow the colony narrates itself
Cross-pollination: the sync engine's provenance trailer already names the device that made a change; a recording commit therefore self-documents which machine recorded it
The tray is the shared nervous system: recording state already wins the icon over sync state; extend the same composition to say 'recording, 2 segments awaiting push'
PREDATIONwhat eats the archive
Predator: disk pressure. Prey: old local bytes. Defence: LFS pointer-only + prune verified objects, which the ecosystem can do because the remote is the durable copy
EMPTY NICHEthe unoccupied minute
Niche nobody fills: the post-meeting minute — the moment the user is most willing to type two sentences of context, and the only moment they ever will
So the finalize event should also open a tiny note stub prefilled with title, date, participants and tags, saved next to the session and synced with it

Thirteen assumptions turned over. The struck line is what everyone believes; the bright line is what turns out to be true once you look at the seams.

ASSUMPTION 01
recordings live in one root
⟲
REVERSED
routing per session by tag — a client recording lands in the client's repo, personal ones stay local
ASSUMPTION 02
the recorder chooses the path
⟲
REVERSED
the DESTINATION chooses the layout, and the recorder asks it for a path — which is what makes per-profile templates work
ASSUMPTION 03
sync happens after recording
⟲
REVERSED

ASSUMPTION 04
a session is a folder
⟲
REVERSED

ASSUMPTION 05

⟲

ASSUMPTION 06

⟲

ASSUMPTION 07

⟲
REVERSED

ASSUMPTION 08
everything must sync
⟲
REVERSED

ASSUMPTION 09

⟲

ASSUMPTION 10

Time Horizon Ladder

12 ideasCLIMB, THEN BACKCAST

Climb the rungs to the anthropologist's view, then walk the conclusion back down to the very first thing to build.

YEAR 1200 sessions / 400 GB

Year 1: 200 sessions, 400 GB — a flat root already hurts; the year folder and pointer-only mode are enough

Year 1 risk: the first 40 GB day teaches the user that a push during a meeting is unacceptable — the bandwidth window must exist early

YEAR 31.5 TB / archive is the product

Year 3: 1.5 TB and the laptop can no longer hold it; local prune of verified objects becomes mandatory, and 'which sessions are local?' becomes a real UI question

Year 3: the archive is now the product — 'find the call where we agreed the API shape' matters more than any recording feature

YEAR 55000 commits of media

Year 5: the repo has 5000 commits of pure media; git gc and shallow clones matter, and a second peer joining must be able to fetch metadata only

YEAR 10formats rot

Year 10: formats rot — HEVC of 2026 is fine, but the manifest must record codec, resolution and fps so a future transcoder knows what it has (the recording settings already carry all three)

Year 10: the tag tree is the only navigation left that still works; folder names are archaeology

100 YEARSthe anthropologist

100 years / the anthropologist's view: what survives is the ndjson ledger and the markdown notes — plain text outlives every container format, which argues for writing metadata as text beside the media, not only in a database

↓ BACKCAST — WHAT THE 100-YEAR VIEW DEMANDS OF THE FIRST COMMIT
Backcast from that: the very first move is to make the session folder self-describing in plain text, because everything later reads it
Near-term corollary: manifest.json must be stable, documented and versioned from day one, since it becomes the migration surface
Ten-year corollary: never bake absolute paths into the manifest — a synced archive is opened on another machine by definition
Retention as policy text in the profile, not code: keep_media_days, keep_metadata_forever, prune_only_if_verified

● CLOSING SYNTHESIS

the four asks are one idea wearing four hats — a recording session must stop being a folder the app writes and forgets, and become an addressable, self-describing record whose path, durability, searchability and meaning are all derived from the same session identity. Naming is retrieval; sync binding is durability; the assert-finished seam is what makes durability prompt; the tag/note/archive layer is what makes the pile usable in year three.

The non-obvious link: immutability is the key that unlocks the completeness gate — a rotated segment is not 'probably done', it is finished forever, which is a stronger claim than any quiescence timer can make, and it is the reason this can be safe rather than a hack.
